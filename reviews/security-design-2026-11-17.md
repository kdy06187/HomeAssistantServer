# 보안 점검 (설계 단계) — 2026-11-17

대상: `docs/02_설계.md`, ADR-005~009(010은 종료 순서라 보안과 무관, 훑기만 함), `docs/api-contract-v2.0-초안.md`, 참고로 NFR-03·REQ-14~16과 `analysis/문제점.md`의 A-xx.
방식: 설계 문서만 읽음(코드 실행·빌드 없음). 코드는 `src/ApiAuth.cpp` 토큰 비교 부분만 확인. 비밀 파일·외부 라이브러리는 읽지 않음.
전제: 1인·집 LAN, 외부 접속은 Tailscale, HTTP는 127.0.0.1:8000 + `tailscale serve`, TCP 8080은 무인증(A-06 범위 밖).
"확인 필요"는 문서만으로는 알 수 없는 것이다.

| S-01 | **인증 전에 본문을 읽는다.** 기존 pre-routing은 본문을 읽기 전에 거부했지만, 새 구조는 인증 안 된 요청도 최대 16KiB를 읽고 스레드를 쓴다. 느리게 보내는 연결(Slowloris형)을 여러 개 열면 httplib 작업 풀이 차서 정상 앱 요청도 막힌다. 16KiB는 크기만 막고 시간·동시 연결은 안 막는다. 읽기 타임아웃·풀 크기·헤더 크기 한도는 설계에 없다(C-9도 풀 크기만 언급). 공격자는 tailnet 안의 다른 기기이거나, 전환기·비상용 `HAC_HTTP_BIND=0.0.0.0`일 때 LAN 기기다. | 중 | 3.7, ADR-009, C-9 | 읽기·쓰기 타임아웃과 keep-alive 한도를 설계에 명시한다(`set_read_timeout` 등, 값은 통합 테스트로 확정). 작업 풀 크기를 정하고, 느린 본문 연결이 있어도 정상 요청이 처리되는지 테스트를 추가한다. 헤더 크기 한도는 확인 필요. |
| S-02 | **토큰 강도·무차별 대입.** 시도 제한을 안 만드는 것은 "VPN 안에서만 접근"이 전제다. 하지만 tailnet 안의 다른 기기(공유받은 노드, 침해된 기기)는 serve에 닿고, 실패 요청은 모두 127.0.0.1로 보여 IP별 차단도 못 한다. 토큰의 최소 길이·생성 방법은 설계에 없다. 토큰 파일 권한(0600)도 설계에 없다. 비교 자체는 `CRYPTO_memcmp`(`src/ApiAuth.cpp:37-39`)로 상수 시간이다. 길이가 다를 때 먼저 반환하는 것은 길이가 비밀이 아니므로 허용된다. | 중 | 3.7, ADR-005·009, REQ-15 | (1) 토큰은 암호학적 난수 32바이트 이상(예 `openssl rand -hex 32`)이라고 `06_배포.md`에 명시하고, 시작 시 너무 짧으면 경고한다. (2) Tailscale ACL로 서버의 443 접근을 휴대폰 기기만 허용한다(사용자 설정, 문서화). (3) 시도 제한은 안 만들더라도, 실패 N회/분을 세어 경고 로그를 남기는 지점만 래퍼에 둔다. (4) `config/api_token` 권한 0600과 실행 계정 소유를 시작 시 점검한다. |
| S-03 | **인증 실패 로그의 신뢰성과 인젝션.** 로그에 `remote_addr`, 경로, `X-Forwarded-For`를 그대로 쓴다. 공격자가 XFF를 위조하거나 경로·헤더에 개행·긴 문자열을 넣어 로그를 위조·폭주시킬 수 있다(`%0A` 같은 디코딩 후 문자 포함). serve 뒤에서는 `remote_addr`가 항상 127.0.0.1이라 "누가 시도했는지"가 로그에서 사라진다. serve가 XFF를 실제로 붙이는지도 모른다(C-8). `tailscale funnel`을 잘못 켜면 인터넷에 공개되는데, 그때는 제한도 없고 IP도 못 본다. | 중 | 3.7, ADR-005, C-8 | (1) 로그에 쓰는 외부 입력(경로, 헤더, deviceId)은 제어문자 제거·길이 제한(예 200자)한다. (2) XFF는 `remote_addr`가 loopback일 때만 참고용으로 기록하고, 판정(차단·허용)에는 쓰지 않는다. serve가 붙이는 Tailscale 신원 헤더가 있다면 그것이 XFF보다 낫다(확인 필요). (3) 배포 문서에 `tailscale serve status`로 funnel이 꺼져 있음을 확인하는 점검 항목을 넣는다. (4) 127.0.0.1 출처를 "신뢰"하는 코드를 만들지 않는다는 규칙을 한 줄 적는다(모든 serve 요청이 loopback이라 무의미). |
| S-04 | **ARP 기반 ID의 위조·오탐.** (a) 같은 LAN의 공격자가 기존 기기의 MAC을 위조해 8080에 접속하면 `TCP_<그 MAC>`으로 인식된다. 3.4·REQ-05는 "재접속 시 이전 연결 close"라서 정상 연결을 끊고 공격자가 그 자리를 차지할 수 있다. 공격자는 이후 그 기기에 가는 제어 메시지를 받고, 가짜 상태 응답을 보낸다. 반면 ADR-006의 "서로 다른 IP가 같은 MAC이면 뒤 연결 거부"는 재접속 규칙과 충돌한다. 어느 규칙이 우선인지 문서에 없다. (b) DHCP로 IP가 다른 기기에 넘어간 직후 ARP 표에 이전 소유자의 stale 항목이 남아 있으면 다른 기기의 ID로 식별될 수 있다. ADR-006은 "보통 이웃 항목이 있다"고만 쓴다. 항목 플래그(0x2 완료)는 보지만 상태·시각은 안 본다. (c) 서버와 다른 서브넷에서 접속하면 모든 연결이 공유기 MAC으로 보인다. 설계는 이를 "지원 안 함"으로만 적고 차단 규칙은 없다. 8080이 무인증이라 LAN 내 접속 자체는 A-06 범위 밖이다. 하지만 "접속 = 기존 기기 ID 점유"가 되는 것은 새 설계가 만드는 효과다. | 중 | ADR-006, 3.1(TCPDriver), 3.4, C-1~C-3 | (1) 같은 ID의 연결이 이미 살아 있으면 새 연결을 바로 교체하지 말고 기존 연결의 생존을 확인(짧은 ping 또는 소켓 오류 확인)한 뒤에만 교체한다. 교체가 일어나면 경고 로그에 IP 변화를 남긴다. 위 "충돌" 규칙과 순서를 문서에 하나로 정한다. (2) 접속 IP가 서버와 같은 서브넷이 아니거나 게이트웨이 MAC과 같으면 식별 실패로 처리한다. (3) ARP 항목은 접속 직후 값만 쓰고, 가능하면 이웃 상태(REACHABLE 등)를 확인한다. 실기 항목 C-1에 "IP 재할당 직후 stale 항목" 시험을 추가한다. (4) MAC 위조 자체는 막을 수 없다(8080 무인증이 전제)는 위험을 `06_배포.md`의 "LAN 한정 위험"에 명시한다(NFR-03). |
| S-05 | **커미셔닝 창에서의 신규 등록·복구 오귀속.** 커미셔닝 중(최대 120초 초안) "시작 이후 접속 + 활성 ID 아님"이면 신규로 채택된다. 이 창에 LAN 안의 다른 기기나 공격자가 접속하면 다른 기기가 신규로 등록된다(N-10 일부만 해소). 공격자가 90일 안에 삭제된 기기의 MAC을 흉내 내면 숨김 기록이 자동 복구되어 그 기기가 이전 이름·드라이버·누적값을 이어받는다. 또 ADR-007은 "활성 기기 ID가 다시 나오면 덮어쓰기(이름·드라이버 갱신)"라고 해서 5.2의 "활성 ID 아님" 판정과 모순된다. 활성 기기를 덮어쓰면 `driverTypes`(예: PC 종료 지연 드라이버)가 바뀔 수 있다. 영향은 1인 환경에서 크지 않지만 부착 드라이버가 바뀌는 점은 가볍지 않다. | 중 | ADR-006·007, 5.2, REQ-10·13 | (1) 활성 기기와 같은 ID가 커미셔닝 결과로 나오면 덮어쓰지 말고 `COMMISSION_FAILED`(이미 등록됨)로 처리한다(ADR-007 문구 정정). (2) 복구(`restored=true`)는 응답에 알리는 것에 더해, 앱이 사용자에게 확인을 받는 흐름을 계약에 고려한다(최소: 복구된 기기의 이름·ID를 작업 결과에 표시). (3) 커미셔닝 창 동안 접속은 BLE로 설정을 준 기기와 대응시킬 수 있으면 BLE 주소와 MAC 관계(C-4)를 검증용으로 쓴다(확인 필요, 보드 의존). |
| S-06 | **레거시 `ARD_<ip>` → `TCP_<MAC>` 이전의 오귀속.** 이전 조건이 "같은 IP에서 첫 접속"뿐이다. 기존 기기가 오프라인인 사이 DHCP로 같은 IP를 받은 다른 DIY 기기, 또는 공격자가 접속하면 이전 기기의 이름·통계·이력·드라이버를 가져간다. 이전이 3개 테이블 `device_id` 이름 변경이라 되돌리기도 쉽지 않다. | 중 | 4.2 단계 4~5, ADR-006 | (1) 이전 전에 이전 DB 백업이 있는지 확인한다(4.2 단계 1이 있으므로 문서에 연결). (2) `ARD_<ip>` 기기가 **현재 연결 중이 아닐 때만** 이전하고, 이전 후 로그와 첫 E1 응답에 이전 사실을 알린다. 가능하면 확정 전 사용자가 앱에서 확인한다. (3) 이전 대상 `TCP_<MAC>`이 이미 있으면(숨김 포함) 병합하지 말고 이전을 건너뛰고 경고한다. 설계는 "없고"만 쓰고 숨김 케이스를 안 다룬다. |
| S-07 | **8080 입력 상한 없음.** (8080 무인증 자체는 A-06 범위 밖이지만, 새 `TcpConnection`의 줄 버퍼와 "미식별 연결로 보관"은 설계로 정할 수 있다.) 줄 구분자 없이 계속 보내면 줄 버퍼가 무한히 커지고, 미식별 연결을 닫지 않고 보관하므로 연결 수·fd도 무한이다. LAN 기기 하나가 서버를 메모리·fd 고갈로 죽일 수 있다. 같은 프로세스에 HTTP도 있어 앱까지 같이 죽는다. | 중 | 3.1(TcpConnection), ADR-006(미식별 연결) | 줄 최대 길이(예 4KiB, 초과 시 close), 연결 수 상한(예 32)과 미식별 연결 유지 시간 상한(예 30초)을 설계에 넣고 TCP 루프백 테스트에 추가한다. |
| S-08 | **chip-tool 출력·stdin 비밀값의 누출 경로.** (a) `ProcessResult.output`이 `run()`의 결과로 오래 살아 있다. 실패 시 로그 또는 오류 메시지에 그대로 붙이면, chip-tool이 명령줄을 에코(readline/interactive)하거나 PIN을 출력할 경우 비밀번호·PIN이 로그와 `COMMISSION_FAILED` 메시지로 나간다. 기존은 "실패 로그에만 마스킹"(A-03)이었는데 새 설계에는 이 규칙이 안 이어져 있다. 3.2는 `CommissionRequest`의 password·payload 로그 금지만 쓴다. (b) 작업 상태 표(메모리)가 요청 구조체를 보관하면 비밀값이 오래 남는다. (c) chip-tool이 다른 위치(예: `/tmp`)에 상태·키를 쓰는지 확인된 바 없다(확인 필요). | 중 | ADR-008, 3.2, REQ-16, NFR-03 | (1) 모든 chip-tool 출력은 로그 전에 `str:` 뒤 값·PIN·설정 코드를 마스킹하는 함수를 거치게 하고(`ChipToolRunner` 쪽에서 한 번에), 오류 본문의 `message`에는 chip-tool 출력을 넣지 않는다. | S-09 | **E3 입력 검증 누락(stdin 명령 주입).** 기존 argv 방식은 `execv`라 인자 경계가 안전했다. 새 방식은 비밀값을 한 줄 텍스트(`pairing ble-wifi ... str:<ssid> str:<pw> ...\nquit\n`)에 이어 붙여 stdin으로 보낸다. TCP_DIY의 `payload`(서버 IP)도 형식 검증이 없다. | 중 | ADR-008, API E3, 3.5 | E3 검증 규칙을 설계에 명시한다: ssid 1~32바이트, password 0~63바이트(WPA2), 제어문자(`\r \n \0` 등)·Tab 거부, 개행이 하나라도 있으면 400 `INVALID_REQUEST`. MATTER `payload`는 숫자 11/21자리 또는 `MT:` + 허용 문자만, TCP_DIY `payload`는 IPv4 형식(또는 빈 문자열)만 허용한다. `driverTypes`는 알려진 enum 값만. 따옴표 이스케이프가 불가능한 문자는 거부 쪽으로 정한다(C-6 결과 반영). |
| S-10 | **E7 파라미터·SQL 처리.** 설계는 형식(YYYY-MM-DD, `period` enum, limit 1 이상)과 범위(366일, `from ≤ to`)를 정하지만, (a) 파싱 실패(숫자가 너무 큼, `limit=abc`, `2026-02-30` 같은 존재하지 않는 날짜)가 400이 되는지 예외(500)가 되는지 정해져 있지 않다(N-14 계열). (2) 파서는 예외 없이 `Result`로 400을 돌려주고 단위 테스트에 경계값(빈 값, 음수, 0, 2^63, 윤일, `2026-13-01`, 366/367일)을 넣는다. (3) 집계는 SQL로 구간 합산하거나 스트리밍으로 처리하고, 동시 집계 요청을 1~2개로 제한하는 것을 구현 시 검토한다(필수 아님). |
| S-11 | **오류 본문 정보 노출.** 오류 본문의 `message`는 `Error.message`(3.2)에서 오는데, 이 문자열이 SQLite 오류, 파일 경로, chip-tool 출력, `e.what()`일 수 있다. 3.5 예시는 고정 문구이지만 "고정 문구만 쓴다"는 규칙은 없다. `COMMISSION_FAILED`의 `error.message`는 작업 결과로 앱에 간다(S-08과 연결). 없는 기기 404와 숨김 기기 404를 같게 한 점(I-02)은 좋다. | 중 | 3.5, ADR-003, API 오류 표 | 외부 응답의 `message`는 `ErrorCode`별 고정 한국어 문구로만 만들고(`ErrorMapping`에서), `Error.message`(상세)는 로그에만 쓴다. 500은 `INTERNAL_ERROR` + 고정 문구. 통합 테스트에 "DB 오류를 일으켜도 응답에 경로·SQL이 없다"를 넣는다. |
| S-12 | **마이그레이션 백업 방식.** 4.2 단계 1은 DB 파일을 "복사"한다. DB가 WAL 모드이거나 열린 연결·`-wal` 파일이 있으면 단순 파일 복사는 일관성 없는 백업이 될 수 있다. 기본 저널 모드는 확인 필요. 백업 파일 권한은 umask를 따르므로 0644로 만들어질 수 있고(사용 이력이 담긴 파일), `.bak-v<n>`이 정리되지 않고 쌓인다. 전체 트랜잭션·롤백 설계는 적절하다(`user_version`도 트랜잭션 안에서 롤백된다). | 중 | 4.2, NFR-06 | 백업은 SQLite 온라인 백업 API 또는 `VACUUM INTO`로 만들고, 만든 뒤 열어서 `PRAGMA integrity_check`를 확인한다. 백업 파일은 0600으로 만들고 보관 개수 상한을 정한다. 기본 저널 모드를 확인한다(확인 필요). |
| S-13 | **정리 작업과 시계 이상 → 데이터 손실.** 정리는 `utcNow - 90일`을 기준으로 이력을 지운다. 시스템 시계가 미래로 잘못 설정되면(NTP 미동기, RTC 오류) 한 번에 이력과 숨김 기기 기록이 전부 사라지고 복구가 안 된다. 정리가 시작 시 즉시 실행되므로 마이그레이션 직후 문제가 생기면 백업도 이미 최신 상태일 수 있다. | 중 | 4.3, PeriodicTasks, ADR-007 | 정리 전에 시계 점검(현재 시각이 빌드·마지막 DB 기록 시각보다 앞서 있지 않고, 마지막 기록보다 90일 넘게 앞서지 않음)을 하고 이상하면 정리를 건너뛰고 경고한다. 한 번에 삭제하는 비율에 상한(예: 이력 50% 초과면 중단)을 둔다. 시작 시 정리는 마이그레이션 직후가 아니라 다음 주기에 하도록 순서를 정하는 것도 검토한다. |
| S-14 | 토큰 비교 | 하(양호) | 3.7 | `ApiAuth`는 `CRYPTO_memcmp`를 쓴다(상수 시간). 설계상 추가 조치 없음. 단 `Authenticator` 래퍼가 토큰을 로그·예외 메시지에 넣지 않는지는 구현 단계 검토 항목. |
| S-15 | **deviceId 경로 패턴.** deviceId는 파일 경로로 쓰이지 않으므로 경로 조작 위험은 낮다. 하지만 라우트 패턴이 느슨하면 `/`가 든 문자열이 캡처되거나, 로그·오류에 그대로 찍힌다(S-03). Matter 시리얼의 허용 문자 집합이 문서에 없다(확인 필요). | 하 | API E5~E7, 3.5 | 라우트 패턴을 `[A-Za-z0-9_-]{1,64}`로 제한하고 불일치는 404. 허용 집합은 실제 시리얼로 확인. |
| S-16 | **삭제 후 90일 보관.** 사용 패턴(기기별 전력 이력)이 삭제 후에도 90일 남는다. 사용자가 즉시 영구 삭제할 수단이 없다(1인 사용이라 위험은 작음). Matter `unpair` 실패 시 기기는 여전히 fabric에 남지만 서버에는 숨김만 있다(`unpaired:false`로 알림은 있음). | 하 | ADR-007, 5.3 | 영구 삭제 옵션(예: E4의 `permanent=true`)은 필요해지면 추가. `unpaired:false`일 때 앱이 경고를 보이도록 계약에 한 줄 추가. |
| S-17 | **실행 계정·파일 권한(배포 단계).** 설계에 서버 실행 계정, `config/api_token`·DB·백업·`registered_devices.txt` 권한, systemd 하드닝 항목이 없다. BLE 때문에 root로 실행하는 유혹이 생길 수 있다. `.gitignore`는 `config/api_token`을 이미 제외한다(확인함). | 하 | 3.9, `06_배포.md`(구현 단계) | `06_배포.md`에 전용 일반 계정 실행, 토큰·DB 0600, 데이터 디렉터리 0700, BLE는 `CAP_NET_RAW` 등 필요한 권한만(또는 bluetooth 그룹), 코어 덤프 비활성(비밀값이 메모리에 있음)을 넣는다. 배포 전 서버 점검에서 읽기 명령으로 확인한다. |
| S-18 | **비상 바인딩 `HAC_HTTP_BIND=0.0.0.0`과 전환기.** 의도된 예외이지만 켜 둔 채 잊으면 LAN 평문 토큰 노출(I-06)이 되살아난다. | 하 | ADR-005, 3.9 | 비-loopback 바인딩으로 시작하면 시작 로그에 눈에 띄는 경고(`[HTTPServer] 경고: 평문 HTTP가 LAN에 열림`)를 남긴다. 전환 끝나면 되돌리는 항목을 배포 체크리스트에 넣는다. |
| S-19 | **413·RST의 응답 전달.** 16KiB 초과 시 httplib가 응답한 뒤 연결을 닫을 때 N-03과 같은 RST가 생길 수 있다(C-9). 정상 앱은 크기를 넘지 않아 보안 영향은 작고, 계약에도 확인 필요로 적혀 있다. | 하 | ADR-009, API 413 | 통합 테스트(C-9)로 확인하고, 앱은 413이면 본문 없이도 처리하도록 계약에 이미 적힌 대로 둔다. |
| S-20 | **구버전 복귀 시 숨김 기기 부활.** 마이그레이션 v1 이후 이전 바이너리로 되돌리면 구버전은 `deleted_at`을 몰라 숨김 기기를 활성으로 로드한다. 칸 추가만이라 열리긴 한다. | 하 | 4.2, 폴더 구조의 롤백 요구(CLAUDE.md) | `06_배포.md`에 "롤백은 백업 DB(`.bak-v0`)로 되돌리는 것"과 그 이후 기록 손실을 명시한다. |

## 3. 설계 반영 필요(상·중)

상(높음)은 없다. 중 항목은 다음과 같다.

1. **S-01** 읽기·쓰기 타임아웃, keep-alive, 작업 풀 크기를 3.7·ADR-009에 명시하고 느린 연결 테스트를 추가한다.
2. **S-02** 토큰 최소 길이·생성 방법·파일 권한(0600) 점검, Tailscale ACL 권고, 실패 횟수 경고 로그 지점을 3.7에 추가한다.
3. **S-03** 로그에 쓰는 외부 입력의 정제·길이 제한, XFF는 참고용 기록만(판정에 사용 금지), funnel 꺼짐 확인 점검 항목을 추가한다.
4. **S-04** 재접속 시 교체 규칙을 하나로 정한다(기존 연결 생존 확인 후 교체, 충돌 규칙과 순서 정리). 서브넷·게이트웨이 MAC 거부와 stale ARP 시험(C-1)을 넣는다.
5. **S-05** ADR-007의 "활성 ID 덮어쓰기" 문구를 정정한다(활성이면 실패 처리). 복구 시 사용자에게 알리는 방식을 정한다.
6. **S-06** 레거시 이전 조건을 강화한다(이전 대상이 연결 중이 아닐 때만, 대상 `TCP_<MAC>`이 숨김으로 있으면 건너뜀, 사용자에게 알림).
7. **S-07** `TcpConnection`의 줄 최대 길이, 연결 수 상한, 미식별 연결 유지 시간 상한을 설계에 넣는다.
8. **S-08** chip-tool 출력 마스킹을 `ChipToolRunner` 한 곳에서 처리한다. 작업 상태 표에는 요청을 보관하지 않는다. C-6에 "비밀값이 출력·파일에 남는지" 항목을 추가한다.
9. **S-09** E3 입력 검증 규칙(ssid·password 길이, 제어문자 거부, payload 형식)을 API 계약과 설계에 명시한다. 이것이 stdin 방식 도입 시 새로 생기는 주입 경로를 막는다.
10. **S-10** "DB 질의는 바인딩만" 규칙, E7 파싱 실패는 예외 없이 400, 경계값 테스트를 넣는다.
11. **S-11** 외부 오류 `message`는 코드별 고정 문구만 쓰고 상세는 로그에만 쓴다는 규칙을 3.5에 추가한다.
12. **S-12** 백업을 SQLite 백업 API 또는 `VACUUM INTO`로 하고, 무결성 확인·권한 0600·보관 개수 상한을 4.2에 추가한다.
13. **S-13** 정리 작업 전 시계 점검과 삭제 비율 상한을 4.3에 추가한다.

위 항목 중 반영하지 않기로 하는 것이 있으면 이유를 `02_설계.md` 9절 리뷰 반영 표에 기록한다.
