### 0.8 셸 도우미 (원래 터미널)
```bash
B=http://$SERVER_IP:8000; AUTH=$T/config/auth.header
poll() { for i in $(seq 1 105); do R=$(curl -s -H @$AUTH $B/api/commission/$1); printf '%(%T)T %s\n' -1 "$R"; case "$R" in *SUCCEEDED*|*FAILED*|*JOB_NOT_FOUND*) return;; esac; sleep 2; done; echo "210초 지남 → E1로 확인"; }
```
- `poll <jobId>`: E8을 2초마다(최대 210초 = 계약 K3) 찍는다.
- E3 접수 응답에서 jobId 꺼내기: `JOB=$(… | sed -n 's/.*"jobId":"\([^"]*\)".*/\1/p')`.

## 1. 확인 항목

### K-1 Matter 페어링 실제 시간 (C-7 → 계약 K2 190초 재계산) — 5회
목적: 실제 `pairing ble-wifi` 시간을 재서 제한 시간을 "최댓값×2, 상한 180"으로 정하고, 작업 상한(페어링 + 시리얼 10초)을 다시 계산한다. 함께 E3 202 → E8 폴링·`restored`를 본다.

1. 🔒 **플러그 공장 초기화**(P-1). LED가 등록 대기 상태인지 확인.
2. 비밀값 입력(화면에 안 보임):
   ```bash
   read -rs -p 'Matter 설정 코드: ' CODE; echo; read -r -p 'Wi-Fi SSID: ' SSID; read -rs -p 'Wi-Fi 비밀번호: ' PW; echo
   ```
3. 1회차 등록(PC_DRIVER 붙임 — K-15에 씀):
   ```bash
   R=$(printf '{"protocolType":"MATTER","deviceName":"시험 플러그","payload":"%s","ssid":"%s","password":"%s","driverTypes":[1]}' "$CODE" "$SSID" "$PW" | curl -s -X POST -H @$AUTH -H 'Content-Type: application/json' -d @- $B/api/commission); echo "$R"; JOB=$(echo "$R" | sed -n 's/.*"jobId":"\([^"]*\)".*/\1/p'); poll $JOB
   ```
   기대: 즉시 `202` 본문 `{"jobId":"c-…","state":"PENDING"}` → 폴링 `PENDING`/`RUNNING` → `SUCCEEDED`, `"deviceId":"<시리얼>"`, `"restored":false`, `"error":null`. → `PLUG_SERIAL=<그 deviceId>`.
   로그: `[MatterController] chip-tool pairing ble-wifi 끝: … 걸린 시간 N.N초` → **N 기록**. 출력에 SSID(4바이트 이상)·비밀번호·코드가 `***`로만 보이는지 `grep -c -- "$PW" $T/server-*.log`(기대 `0`)·`grep -c -- "$CODE" $T/server-*.log`(기대 `0`).
4. 2~5회차(복구 경로도 함께):
   ```bash
   curl -s -X POST -H @$AUTH -H 'Content-Type: application/json' -d "{\"deviceId\":\"$PLUG_SERIAL\"}" $B/api/devices/delete; echo
   ```
   기대: 200 `{"deviceId":…,"deletedAt":…,"restorableUntil":…,"unpaired":true}`(플러그 fabric에서 시험 노드 제거). 🔒 플러그가 등록 대기 상태로 돌아가지 않으면 **공장 초기화**. 그다음 3의 등록 명령을 다시(같은 `CODE`·`PW` 변수).
   기대: `SUCCEEDED`, **`"restored":true`**, 이력·통계 이어받음(`sqlite3 -readonly $T/db/home_assistant.db "SELECT device_id, deleted_at FROM devices;"` → `deleted_at` 빈칸).
5. 판정: 걸린 시간 5개 최댓값 M초 → 페어링 제한 = `min(M×2, 180)`초, 작업 상한(K2) = 그 값 + 10초. 앱 확인 시간(K3) = 작업 상한 + 20초. 180 그대로면 계약 K2·K3 문구 그대로(190·210초). 줄이면 `MatterController::kPairingTimeout` 한 줄 + 계약 K2·K3 갱신(총괄 승인 뒤 커밋).
6. 되돌리기: 없음(시험 DB·시험 fabric 사본만 바뀜). 운영에서의 플러그는 1회차 초기화 때 이미 운영 fabric에서 빠졌다 → 2.5.

### K-1b (선택) 활성 Matter 기기 재페어링 → `ALREADY_REGISTERED` (D6)
목적: 등록된(활성) 플러그를 초기화해 다시 등록하면 덮어쓰지 않고 거절하는지, **새 노드만** 해제하는지.
1. 🔒 플러그 공장 초기화(시험 DB에는 활성으로 남아 있음) → 3의 등록 명령.
2. 기대: `FAILED`, `"error":{"code":"ALREADY_REGISTERED","message":"이미 등록된 기기입니다."}`. 로그 `커미셔닝 결과를 등록하지 않음(이미 등록된 기기)` → `등록되지 않은 새 노드(<새 번호>) 페어링 해제 중...`. `cat $T/config/registered_devices.txt`의 그 시리얼 줄이 **전 노드 번호 그대로**.
3. 되돌리기: 이 뒤 플러그는 시험 fabric에서도 빠져 있다. K-15를 하려면 먼저 E4 삭제 → 🔒 초기화 → 3의 등록(복구)으로 다시 붙인다.

### K-12 TCP 비동기 등록 + BLE 1초×5 발견율 (빈 payload = `local_addr`)
목적: E3 202 → E8, 서버 주소를 앱이 접속한 주소로 쓰는지, BLE 스캔이 몇 초 안에 찾는지.
1. 🔒 **스위치 초기화**(P-4, BLE 등록 모드).
2. 등록(빈 payload, **LAN 주소로 접속**):
   ```bash
   read -rs -p 'Wi-Fi 비밀번호: ' PW; echo; R=$(printf '{"protocolType":"TCP_DIY","deviceName":"시험 스위치","payload":"","ssid":"%s","password":"%s"}' "$SSID" "$PW" | curl -s -X POST -H @$AUTH -H 'Content-Type: application/json' -d @- $B/api/commission); echo "$R"; JOB=$(echo "$R" | sed -n 's/.*"jobId":"\([^"]*\)".*/\1/p'); poll $JOB
   ```
   기대: 202 → `SUCCEEDED`, `"deviceId":"TCP_<12자>"` → `SWITCH_ID=<그 값>`. 로그: `TCP 등록 서버 주소 = 접속 주소 <SERVER_IP>`, `BLE 스캔 시작...` → `기기 발견!` 사이 초 수(=스캔 회차, 1~5) 기록, `와이파이 설정 전송 완료` → `커미셔닝 완료 : 시험 스위치 (TCP_…, N초)`. E1(`curl -s -H @$AUTH $B/api/devices`)에 `"ip":"<스위치 IP>"`.
3. 루프백 거절(같은 본문을 `127.0.0.1`로):
   ```bash
   printf '{"protocolType":"TCP_DIY","deviceName":"x","payload":""}' | curl -s -o /dev/null -w '%{http_code}\n' -X POST -H @$AUTH -H 'Content-Type: application/json' -d @- http://127.0.0.1:8000/api/commission
   ```
   기대: `400`(기기 등록 시도 없음 — 로그 `접속 주소가 LAN IPv4가 아님`).
4. 발견율: K-14·K-16의 BLE 등록까지 합쳐 "찾음 / 시도"와 회차(초)를 3절에 적는다. `TCPDevice_DIY 기기를 찾지 못했습니다`가 나오면 그 회차를 실패로 센다(E8 `COMMISSION_FAILED`).
5. 되돌리기: 없음(시험 DB).

### K-13 등록 중 종료 (TCP 접속 대기 중 SIGTERM)
목적: 등록 작업이 진행 중이어도 5초 안에 끝나고, 재시작하면 옛 jobId는 404인지.
1. 🔒 스위치 초기화 → K-12의 2 등록 명령을 보내되 `poll` 대신 로그를 본다. `와이파이 설정 전송 완료. TCP 접속 대기 중...`이 뜨면 **바로**:
   ```bash
   date +%T; kill -TERM $(pgrep -f '^./HomeAssistantCore')
   ```
   (스위치가 1~2초 만에 붙으면 대기 전에 끝나 버린다 → 스위치 전원을 뽑아 둔 채 BLE 쓰기 직후 종료하는 방법도 됨: 그때는 BLE 단계 취소 로그)
2. 기대: 로그 `종료 신호 수신(SIGTERM)` → `서버 종료로 TCP 접속 대기를 중단했습니다` → `[Main] 종료 완료`가 **5초 안**(시각 비교). 그 사이 스위치가 붙었다면 `커미셔닝 결과를 등록하지 않음(종료·취소)` + `아두이노 연결 해제 완료`(RESET) 가능.
3. 0.7 마지막 줄로 시험 서버 재시작 → `poll $JOB` → `JOB_NOT_FOUND`(404). E1에 그 스위치 없음.
4. 되돌리기: 스위치는 Wi-Fi 설정을 받은 상태(또는 RESET로 BLE 모드)일 수 있다 → 다음 항목 전에 🔒 초기화.

### K-14 삭제 → 재등록 `restored:true`, 등록된 스위치 초기화 → `ALREADY_REGISTERED` (D5)
1. (K-12로 `SWITCH_ID`가 활성인 상태) 숨김 삭제:
   ```bash
   curl -s -X POST -H @$AUTH -H 'Content-Type: application/json' -d "{\"deviceId\":\"$SWITCH_ID\"}" $B/api/devices/delete; echo
   ```
   기대: 200, `"unpaired":true`(RESET 전송 → 스위치가 BLE 모드로). 들어가지 않으면 🔒 초기화.
2. K-12의 2 등록 → `SUCCEEDED`, 같은 `SWITCH_ID`, **`"restored":true`**.

### R-1 SIGTERM 종단 (11번: 종료 코드 0, 5초 안, 지연 OFF 취소)
목적: 지연 OFF(45초)가 대기 중일 때 SIGTERM을 받으면 5초 안에 종료 코드 0으로 끝나고, 대기 중인 OFF는 실행되지 않는지(플러그의 **전등**이 꺼지지 않음). tmux 파이프 안에서는 종료 코드를 못 받으므로 이 항목과 K-4는 원래 터미널에서 **백그라운드로** 띄운다.
1. 먼저 원본 `pc_client.pyw`가 메인 PC에서 안 도는지 다시 확인한다(K-15 2와 같음). 시험 사본 에이전트 창도 닫혀 있어야 한다.
2. tmux 시험 서버 종료: `tmux attach -t hac-test` → `Ctrl+C` → `[Main] 종료 완료` → `exit`. `ss -ltnp | grep -E ':(8000|8080) '` → 없음.

### K-4 재시작 겹침 (09 2절 b, `kill -TERM $PID; ./HomeAssistantCore` 5회)
목적: 옛 서버가 끝나기 전에 새 서버가 뜨면 8080이 `EADDRINUSE`로 실패(종료 코드 1)하는지 본다. 겹치면 09 b의 "1초×6 재시도"를 다시 검토하는 자료가 된다(이번에는 기록만).
1. 🔒 R-1에 이어 원래 터미널에서(서버가 하나도 안 떠 있는 상태로 시작한다):
   ```bash
   ( cd $T/build && umask 077 && export HAC_PC_AGENT_MAC=$AGENT_MAC
     up() { for i in $(seq 1 60); do ss -ltn | grep -q ':8000 ' && return 0; sleep 0.5; done; return 1; }
     ./HomeAssistantCore > $T/k4-0-$TS.log 2>&1 & PID=$!; up || echo "처음 시작 실패"
     for n in 1 2 3 4 5; do
       kill -TERM $PID; ./HomeAssistantCore > $T/k4-$n-$TS.log 2>&1 & NEW=$!
       wait $PID; echo "$n회: 옛 서버 exit=$?"
       sleep 3; if kill -0 $NEW 2>/dev/null && up; then echo "$n회: 새 서버 실행 중(겹침 없음)"; PID=$NEW
       else wait $NEW; echo "$n회: 새 서버 exit=$? (겹침)"; ./HomeAssistantCore > $T/k4-$n-retry-$TS.log 2>&1 & PID=$!; up || echo "다시 시작 실패"; fi
     done
     kill -TERM $PID; wait $PID; echo "마지막 exit=$?" )
   ```
2. 기대: 회마다 옛 서버 `exit=0`. 새 서버는 "실행 중" 또는 "exit=1 (겹침)". 겹친 회차의 로그(`grep -h '바인딩 실패\|열 수 없습니다' $T/k4-*-$TS.log`)에 `[TCPDriver] 에러 : 주소 … 포트 8080 바인딩 실패 (errno=98 Address already in use)` → `❌ TCP 포트 8080을 열 수 없습니다 … 서버를 종료합니다.` 5회 중 겹친 횟수를 3절에 적는다.
3. 끝 확인: `pgrep -af '^./HomeAssistantCore'; ss -ltnp | grep -E ':(8000|8080) '` → 없음. 남아 있으면 `kill -TERM <그 PID>`(🔒, PID를 먼저 확인).
4. 되돌리기: 없음(시험 DB만 열고 닫음). 그다음 2.1은 "시험 서버가 이미 꺼짐"이므로 확인 명령만 실행한다.

## 4. 위험·질문
- **경로 정정(2026-11-28 확인)**: 운영 PC 에이전트 원본은 메인 PC `Desktop\Agent\projects\home-assistant-drivers\pc-agent\pc_client.pyw`(drivers `5666c1f`, `pythonw`, 시작 프로그램 등록 없음)다. `Desktop\HomeAssistant`에는 시험 사본 `pc_client_test.py`만 있다. 이 절차서와 12b 절차서의 "원본 `pc_client.pyw`" 확인은 이 경로로 읽는다.
