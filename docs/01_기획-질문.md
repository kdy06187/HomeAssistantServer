## 질문

### Q1. 이번 작업의 큰 방향은?
- A) 현재 구조 유지, 결함만 수정
- B) 구조 유지 + 동시성이 약한 부분(TCP 소켓 계층, MatterController 상태)만 다시 만들기
- C) 핵심 계층(DeviceManager, 드라이버 인터페이스)까지 재설계
- D) 전체 재작성
- 추천: B. P1 결함 대부분이 소켓·락 계층에 몰려 있어(N-01, N-02, N-03, B-04, B-05) 거기만 재설계하면 효과가 크고, 앱·펌웨어 호환(G-4)도 지키기 쉽다.

### Q2. 누가, 어떤 환경에서 쓰나요? (보안·운영 우선순위가 갈림)
- A) 본인 집 LAN, 사용자 1명, 서버 PC 단독 사용
- B) 가족 등 소수가 집 LAN에서 사용
- C) 외부 인터넷에서도 접속(포트포워딩·VPN 등)
- D) 여러 사용자가 공유하는 서버
- 추천: A 또는 B. 현재 구성(평문 HTTP, 토큰 1개)은 LAN 한정이 전제여야 안전하다. C·D면 A-05(TLS), N-07 등이 필수로 올라간다.

### Q3. 0단계 P1 결함 중 이번 범위에 넣을 묶음은? (복수 선택)
- A) 서버 중단 방지: N-01 락 순서 역전, N-02 MatterController 맵 무락, B-01 stoi 예외
- B) 데이터 정확성: B-02 전력량 이중 집계, N-04 미등록 ID가 DB 행 생성, B-08 insert 이중 step
- C) TCP 소켓 계층 재정비: N-03 응답 512B 1회 읽기, B-04 ALL 브로드캐스트 무락, B-05 기기별 락·fd 누수
- D) 응답성: B-07 전력 조회 중 전역 락 유지(최대 약 10초 정지)
- E) 일부만 (원하는 항목 번호를 적어 주세요)
- 추천: A+B+C+D 전부. P1은 서버 중단·데이터 오염이고, N-03·B-04·B-05는 같은 파일(TCPDriver)이라 묶어 고치는 편이 중복 작업이 적다. 범위가 크면 A+B를 필수, C+D를 선택으로 한다.

### Q4. 보안 잔여 항목(A-05 TLS 없음, A-06 TCP 8080 무인증, A-08 BLE 이름만 보고 비밀번호 전송, N-07 ps에 비밀번호 노출)은?
- A) 이번엔 모두 제외하고 "LAN 한정 사용" 전제를 문서에 명시
- B) A-05만: 코드 변경 없이 리버스 프록시(TLS) 설정 가이드 문서화
- C) A-06/A-08까지: TCP 기기 인증·BLE 검증 추가(펌웨어 수정 필요)
- D) 전부 구현
- 추천: B. A-05는 코드 변경 없이 줄일 수 있다. C는 펌웨어가 저장소에 없어 검증이 불가능하므로 다음 회차로 미룬다.

### Q5. 새로 추가하거나 동작을 바꿀 기능은? (복수 선택, 안 고른 것은 "범위 밖"으로 기록)
- A) 지연 OFF(45초) 취소·중복 방지(B-06) 및 종료 경로 정상화(N-12, SIGTERM 처리)
- B) 커미셔닝 비동기화(N-09): 요청은 즉시 반환, 진행 상태는 조회
- C) 오류 응답 규약 통일(N-17): 상태코드·본문 형식 변경, 앱 영향 있음
- D) 에너지 이력 조회 limit 파라미터, 보관 정책·인덱스(N-06), 삭제 시 통계 정리(N-05)
- E) 새 기기 종류(TV/TIMER 드라이버 등)
- 추천: A와 D. 사용자 눈에 보이는 동작 오류(취소 불가)와 DB 팽창을 막는다. B, C는 앱 수정이 필요할 수 있어 Q6 답에 따라 결정하고, E는 이번 범위 밖으로 둔다.

### Q6. 앱과 기기 펌웨어를 수정할 수 있나요?
- A) 둘 다 수정 불가: 기존 REST·TCP 형식 100% 유지
- B) 앱만 수정 가능(코드는 별도 저장소에 있음)
- C) 펌웨어만 수정 가능
- D) 둘 다 수정 가능
- 추천: A로 시작. 호환을 유지한 채 고치고, 호환이 깨지는 개선(Q5-C, Q4-C)은 B/D일 때만 선택으로 승격한다.

### Q7. 제약: 시험용 하드웨어와 기한은?
- 하드웨어: Matter 플러그, Arduino류 TCP 기기, BLE 지원 서버 PC를 지금 실제로 쓸 수 있나요? (예: "Matter 플러그 1개, ESP32 1개, BLE 가능")
- 기한: A) 약 2주  B) 약 1개월  C) 학기 말까지  D) 정해진 기한 없음
- 추천: 기한은 B(1개월)로 가정하고 필수 5개 안팎으로 맞춘다. 실기가 없으면 실기 의존 항목(B-03, F-05, F-06)은 "가짜 드라이버로 검증"으로 완료 기준을 바꾼다.

### Q8. "완료"를 어떻게 판단할까요? (테스트 N-15 포함)
- A) 순수 로직 단위 테스트(전력량 보정, 응답 파싱 등) + 빌드 경고 0
- B) A + 가짜(Fake) 드라이버를 쓴 통합 테스트(락·교착·예외 재현)
- C) 사용자가 수동으로 따라 하는 시험 절차서(명령 + 기대 응답)만
- D) B + CI(GitHub Actions)
- 추천: B + C. 동시성 결함은 실기 없이 가짜 드라이버로 재현해야 하고, 실기 확인은 G-5에 따라 절차서로 안내한다. 테스트 프레임워크(예: GoogleTest) 도입은 승인 요청 대상이다. CI는 선택이다.
