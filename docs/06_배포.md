# home-assistant-core — 배포

> 서비스로 실행되는 프로젝트만 사용한다. 비밀번호·키·서버 IP 같은 민감 정보는 적지 않는다(별칭만).
> 상태: **1차 배포 절차 확정안 — 사용자 승인 대기**(2026-11-20). 이 문서를 쓰는 동안 서버 상태를 바꾸는 명령은 실행하지 않았다.

## 1. 배포 환경
| 항목 | 값 |
|---|---|
| 서버 (SSH 별칭) | `KdyServer` |
| 운영 체제 | Ubuntu 26.04 LTS (커널 7.0.0-38) |
| 설치 위치 | `$REPO/build`에서 실행 (`$REPO` = `~/Agent/projects/home-assistant-core`). **개발 저장소와 운영 위치가 같다** → 배포 중에는 이 저장소에서 다른 개발 작업(빌드·브랜치 전환·`git pull`)을 하지 않는다 |
| 실행 방식 | 사용자가 터미널에서 직접 실행(systemd 아님). 터미널을 닫으면 서버도 꺼지므로 `tmux` 세션 안에서 실행한다(설치돼 있음) |
| 서비스 이름 | 없음(프로세스 이름 `HomeAssistantCore`) |
| 실행 계정 | `kdy` (root 아님. 이 서버의 유일한 로그인 계정, `sudo`·`docker` 그룹 소속) |
| 사용 포트 | 8000(REST, 앱), 8080(DIY 기기 TCP) |
| 필요한 환경 변수 | 없음. 토큰은 `config/api_token`(600) |
| 로그 | 표준 출력. `~/hac-logs/server-<UTC>.log`로 `tee`(600) |

> **결정 26(2026-11-20)**: 1차 배포는 **새로 설치하듯** 한다 — 기존 운영 DB(v0)·`registered_devices.txt`를 이어받지 않고 새 DB로 시작해 기기를 다시 등록한다. 실기 때 뜬 chip-tool 저장소 사본(`~/hac-field/kvs-backup`)은 되돌리지 않는다.
> **사용 조건(08 SEC-1차-01)**: 8000은 `0.0.0.0` 평문 HTTP다. **신뢰하는 집 LAN 전용**으로 쓰고, 게스트망·공용 Wi-Fi·포트 포워딩으로 열지 않는다. 외부 접속은 REQ-14(보류) 뒤에.

> ✅ **D-1 해결(9c, 37aa713)**: chip-tool 저장소가 `/tmp`(tmpfs, 재부팅 때 지워짐)에 있던 문제 → 서버가 모든 chip-tool 실행에 `--storage-directory ../config/chip-tool`을 넘기고, 시작 때 그 폴더를 0700으로 만든다. fabric 저장소(`chip_tool_config*.ini`)·KVS(`chip_tool_kvs`)·history가 이 폴더로 간다. chip-tool의 플랫폼 설정 3개(`/tmp/chip_config.ini`·`chip_counters.ini`·`chip_factory.ini`)는 SDK에 `/tmp`로 고정돼 옮겨지지 않는다 — 재부팅 뒤 다시 만들어지며 페어링 정보는 들어 있지 않다(첫 재부팅 뒤 제어 1회로 확인, 4절).

## 2. 배포 순서 (1차, 새로 설치) — 🔒 = 승인 필요(`rules/server.md`)

> 비밀값(토큰)은 화면에 띄우지 않는다. 각 단계는 앞 단계가 성공했을 때만. 터미널에서 먼저 `REPO=~/Agent/projects/home-assistant-core; TS=$(date -u +%Y%m%dT%H%M%SZ)`를 정해 둔다(같은 터미널에서 진행).

**A. 확인(읽기만, 승인 불필요)**
1. 서버·시험 프로세스가 없는지: `pgrep -a HomeAssistantCore; pgrep -a chip-tool; ss -ltn | grep -E ':(8000|8080) '` → 아무것도 없음.
2. 배포할 커밋: `git -C $REPO log --oneline -1; git -C $REPO status --short` → 최신 main, 변경은 서브모듈 `m`뿐.
3. 방화벽(sudo 필요, 읽기만이지만 **사용자가 직접 실행**): `sudo ufw status numbered` → 8000·8080이 집 LAN 대역에서만 허용되는지 확인(규칙 바꾸기는 아래 B-0, 필요할 때만).

**B. 되돌릴 지점 만들기**
- B-0 🔒(필요할 때만) 방화벽 규칙을 집 LAN 대역으로 한정: `sudo ufw allow from <집 LAN 대역>/24 to any port 8000 proto tcp`, 같은 방식으로 8080. 기존에 `8000`·`8080`을 모든 곳에서 허용하는 규칙이 있으면 `sudo ufw delete <번호>`. 바꾸기 전 `sudo ufw status numbered` 출력을 보관.
4. 🔒 되돌림 폴더 만들고 옛 실행 파일 백업: `( umask 077; mkdir -p ~/hac-rollback && cp -p $REPO/build/HomeAssistantCore ~/hac-rollback/HomeAssistantCore.old && sha256sum $REPO/build/HomeAssistantCore > ~/hac-rollback/HomeAssistantCore.old.sha256 )`
   - 옛 실행 파일은 2026-11-15 빌드(1차 구현 전, 정확한 커밋은 기록 없음 — 해시 앞자리 `68f888ba`로 식별). 배포 커밋은 `git -C $REPO rev-parse --short HEAD >> ~/hac-rollback/deploy-commit.txt`로 기록.
5. 🔒 옛 운영 데이터 보관(이름만 바꾸고 지우지 않음):
   - `mv $REPO/db/home_assistant.db $REPO/db/home_assistant.db.old-v0-$TS`
   - `mv $REPO/config/registered_devices.txt $REPO/config/registered_devices.txt.old-$TS`
   - `cp -p $REPO/config/api_token ~/hac-rollback/api_token.old-$TS` (옛 토큰으로 되돌릴 때용, 600 유지)
6. 🔒 옛 chip-tool 저장소 보관(새 서버는 `../config/chip-tool`을 쓰므로 `/tmp`의 것은 쓰지 않는다. 옛 서버 롤백용으로 보관하고, 실기 입력이 남은 history도 `/tmp`에서 치운다): `ls -la /tmp/chip_tool_*`로 목록 확인 → `( umask 077; mkdir -p ~/chip-tool-old-$TS ) && mv /tmp/chip_tool_* ~/chip-tool-old-$TS/`
   - 옮기는 대상(2026-11-20 기준 4개): `chip_tool_config.ini`, `chip_tool_config.alpha.ini`, `chip_tool_kvs`, `chip_tool_history`. `/tmp/chip_config.ini`·`chip_counters.ini`·`chip_factory.ini`(600)는 SDK가 `/tmp`로 고정한 플랫폼 설정이라 그대로 둔다.
   - 새 저장소 `$REPO/config/chip-tool/`은 서버가 처음 켤 때 만든다(미리 만들 필요 없음).

**C. 빌드와 확인 — 새 폴더에서 먼저(운영 `build/`는 성공 뒤에만 바꿈)**
7. 빌드(서버 상태 불변): `cmake -S $REPO -B $REPO/build-release -DHAC_BUILD_TESTS=OFF -DCMAKE_BUILD_TYPE= && cmake --build $REPO/build-release -j"$(nproc)"` → `[100%] Built target HomeAssistantCore`.
8. 같은 커밋 테스트(서버 상태 불변): `cmake --build $REPO/build-dev -j"$(nproc)" && ctest --test-dir $REPO/build-dev` → 전부 통과(2026-11-20 기준 242).
9. 🔒 운영 위치로 옮김: `cp $REPO/build-release/HomeAssistantCore $REPO/build/HomeAssistantCore`
   - 판단: `build/`에서 바로 다시 빌드하면 빌드가 중간에 실패할 때 옛 실행 파일까지 망가진다. 새 폴더에서 빌드·테스트가 성공한 것만 옮기는 편이 안전하다. 실행 위치를 `build/`로 유지하는 이유는 상대 경로(`../config` 등)와 기존 운영 습관.

**D. 권한·토큰**
10. 🔒 폴더 권한 소유자만: `chmod 700 $REPO/config $REPO/db` (지금 775 — 08 6절). `config/chip-tool/`은 서버가 700으로 만든다.
11. 🔒 새 토큰(값을 출력하지 않음): `( umask 077; openssl rand -hex 32 > $REPO/config/api_token.new && mv $REPO/config/api_token.new $REPO/config/api_token )` → 확인 `stat -c '%a %s' $REPO/config/api_token` → `600 65`.

**E. 시작**
12. 🔒 `tmux new -s hac` 안에서 서버 시작(로그는 소유자만 읽게):
    `( umask 077; mkdir -p ~/hac-logs ); cd $REPO/build && ( umask 077; ./HomeAssistantCore 2>&1 | tee ~/hac-logs/server-$TS.log )`
    - 포트를 못 열면 종료 코드 1로 바로 끝난다(로그 `❌ … 포트 … 열 수 없습니다`) → 3절로.
    - tmux에서 빠지기: `Ctrl+b` → `d`. 다시 붙기: `tmux attach -t hac`.

**F. 앱·기기**
13. 앱 토큰 교체(아래 2.1).
14. 기기 재등록(아래 2.2). 등록 뒤 4절 확인.

**G. 정리 — 배포 성공을 4절로 확인하고, 1~2일 써 본 뒤 별도 승인**
15. 🔒 시험 흔적 삭제(목록을 다시 보여 주고 승인받은 뒤): `rm -rf ~/hac-field $REPO/build-field` 
    - 대상: `~/hac-field/`(옛 운영 DB 사본·백업 사본, **옛 토큰 사본 `config/api_token`**, 등록 파일 사본, 실기 로그 8개, KVS 사본, 링크 2개), `$REPO/build-field/`(시험 빌드).
    - 옛 운영 데이터(`*.old-*`, `~/chip-tool-old-*`, `~/hac-rollback/`)는 2차 배포 전까지 보관하고 그때 따로 지운다.

### 2.1 앱 토큰 교체(새 토큰을 화면 기록에 남기지 않기)
- 권장: 서버 터미널(직접 또는 SSH)에서 `less $REPO/config/api_token` → 화면을 보며 앱 설정의 토큰 칸에 입력 → `q`로 닫는다. `less`는 별도 화면(alternate screen)을 써서 닫으면 터미널 스크롤에 남지 않고, 명령 자체에는 토큰이 없어 셸 기록(`history`)에도 남지 않는다.
- 64자를 손으로 치기 어려우면: PC의 SSH 터미널에서 같은 `less`로 띄워 복사해 앱(폰)으로 옮긴다. 복사한 뒤 PC 클립보드를 비운다. 메신저·메모 앱으로 보내지 않는다.
- `cat`을 썼다면 바로 `clear && printf '\033[3J'`로 화면과 스크롤을 지운다.
- 옛 토큰은 무효가 되므로 앱은 첫 요청에서 401 → 토큰 화면(앱 F-01: 첫 시도만 이동하는 문제 있음 — 설정 화면에서 직접 바꿀 것).

### 2.2 기기 재등록 순서(결정 26: 새 DB라 앱에 옛 기기가 없다)
1. **Matter 플러그**: 플러그 공장 초기화(제조사 방법) → 앱 기기 추가 → QR 스캔 → PC가 연결된 플러그면 **PC 드라이버 선택**(`driverTypes [1]`) → 등록 성공 → 목록에 보이고 켜기/끄기 1회.
2. **TCP 스위치(아두이노)**: 서버에 옛 기기가 없으므로 스위치를 공장 초기화(**2번 핀 버튼 5초**) → BLE 광고 상태 → 앱 기기 추가(TCP) → 등록 성공 → 켜기/끄기 1회. 등록 대기 15초가 빠듯하므로(실기) 실패하면 1회 더 시도.
3. PC 에이전트(PC `.103`)는 서버에 붙기만 하면 된다(등록 대상 아님). 종료 메시지 시험은 하지 않는다(T5: 모든 연결에 감).

## 3. 되돌리는 방법 (롤백)
> 조건: 시작 실패, 4절 확인 실패, 앱·기기 동작 이상. 모두 🔒(서버 상태 변경). `$TS`는 2절에서 쓴 값(`ls ~/hac-rollback`, `ls $REPO/db`로 확인).

1. 서버 끄기: tmux 창에서 `Ctrl+C`(또는 `pkill -INT -x HomeAssistantCore`) → `pgrep -a HomeAssistantCore` 없음 확인.
2. 옛 실행 파일: `cp -p ~/hac-rollback/HomeAssistantCore.old $REPO/build/HomeAssistantCore && sha256sum -c ~/hac-rollback/HomeAssistantCore.old.sha256`
3. 새 데이터 치우기(지우지 않고 보관): `mv $REPO/db/home_assistant.db $REPO/db/home_assistant.db.new-$TS; mv $REPO/config/registered_devices.txt $REPO/config/registered_devices.txt.new-$TS`
4. 옛 데이터 되돌리기: `mv $REPO/db/home_assistant.db.old-v0-$TS $REPO/db/home_assistant.db; mv $REPO/config/registered_devices.txt.old-$TS $REPO/config/registered_devices.txt`
5. 옛 토큰(앱이 옛 토큰을 계속 쓰게 할 때): `cp -p ~/hac-rollback/api_token.old-$TS $REPO/config/api_token`
6. chip-tool 저장소: 옛 서버는 `/tmp`를 쓴다 → `cp -p ~/chip-tool-old-$TS/* /tmp/`. 새 저장소 `$REPO/config/chip-tool/`은 그대로 둔다(옛 서버는 읽지 않음, 다시 새 버전으로 갈 때 재사용).
7. 옛 서버 시작: `cd $REPO/build && ./HomeAssistantCore` (옛 코드는 포트 실패에도 계속 돎 — 4절로 꼭 확인).
- 주의: 옛 코드도 `../db/home_assistant.db`를 쓰므로 3~4 순서를 지킨다. 새 코드가 만든 v1 DB를 옛 코드로 열어도 동작은 하지만(3번 시험에서 확인) 이번 롤백은 v0 원본으로 되돌린다.
