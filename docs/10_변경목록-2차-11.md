### 11a. `DelayedCommandScheduler` (REQ-08, ADR-010 B, e2)
| 구분 | 내용 |
|---|---|
| 파일 | 신규 `include/DelayedCommandScheduler.hpp`, `src/DelayedCommandScheduler.cpp`(→ `hac_core`), `CMakeLists.txt`, 신규 `tests/unit/DelayedCommandSchedulerTest.cpp` |
| 인터페이스 | 설계 3.2 그대로: `schedule(id, command, delay, task)`(기기당 1개, 있으면 false) / `pending(id)` → `{command, remaining}` / `cancel(id)` / `tick(now)` / `start()` / `stopAndCancelAll()` |

| 시간 | 타이머는 `Clock::steadyNow()`. 테스트는 스레드를 켜지 않고 `FakeClock.advance` + `tick` 직접 호출 |
| 로그(e2) | `[Scheduler] 지연 OFF 예약: <id>, 실행 예정 HH:MM:SS(45초 뒤)` / `… 실행: <id>, HH:MM:SS` / `… 취소: <id>, HH:MM:SS (사유: 다른 명령·삭제·서버 종료)`. 시각은 `Clock::utcNow()`를 순수 함수 `formatClockTime(time_point)`로(형식은 결정 D3) |
| 테스트 | 만기 전 미실행·만기 실행 1회 / 같은 기기 두 번째 `schedule` false / `cancel` 뒤 미실행 / `pending` 남은 초(올림) / `stopAndCancelAll` 뒤 `schedule` false·미실행·로그 / 작업이 다시 `schedule`을 불러도 교착 없음(락 밖 실행 확인) / 실제 스레드로 짧은 지연(수십 ms) 1건 + tsan / 시각 형식 함수 |

### 11d. SIGTERM·종료 순서 (REQ-09, ADR-010 b, V7 이후 정상 종료)
| 구분 | 내용 |
|---|---|
| 파일 | `src/main.cpp`, `src/ProcessChipToolRunner.cpp`(자식 쪽 몇 줄) |
| 신호 | `main` 첫머리(어떤 스레드보다 먼저)에서 `SIGTERM·SIGINT`를 `pthread_sigmask`로 막음 → 이후 생기는 모든 스레드가 물려받음. 조립이 끝나면 `for(;;) pause()` 대신 `sigwait` |
| 두 번째 신호 | 첫 신호를 받은 뒤 main 스레드만 두 신호를 다시 풂 → 종료가 늦어질 때 한 번 더 Ctrl+C/`kill`하면 기본 동작으로 즉시 끝남(결정 D5). 코드 1~2줄 |
| 자식 마스크(새 발견) | fork한 자식은 신호 마스크를 물려받고 `execv`해도 유지된다. 지금 자식 쪽 코드는 마스크를 되돌리지 않음(`ProcessChipToolRunner.cpp:184~196`) → 그대로 두면 chip-tool이 SIGTERM을 무시해 **제한 시간·`cancelAll`이 항상 1초 뒤 SIGKILL**로만 끝남. 자식에서 `execv` 전에 `sigprocmask`로 빈 마스크 복원(async-signal-safe). `SIGPIPE`의 `SIG_IGN`도 자식에 물려가므로 `SIG_DFL`로 되돌림(1차부터 있던 문제, 함께 처리 제안) |
| 종료 순서 | 아래 표. 설계 3.6과 다른 점은 **스케줄러·주기 작업을 4단계 → 0단계로 당김**(설계와 다른 점 ①) |
| 테스트 | 러너: SIGTERM을 막은 스레드에서 `run` → 자식이 SIGTERM으로 끝남(`exitCode == 128+15`, SIGKILL 아님) / 순서는 main에 있어 단위 시험 불가 → 각 부품의 stop 시험 + 사용자 실기(아래 R-1) |
| 위험 | 신호 마스크가 스레드 생성 뒤에 걸리면 그 스레드가 SIGTERM을 받아 기본 동작으로 죽음 → 첫 줄 배치를 리뷰 항목으로 |

**종료 순서(11 구현안)**
| 순서 | 동작 | 상한 | 설계 3.6과 비교 |
|---|---|---|---|
| 0 | 신호 로그 → `manager.beginShutdown()` → `chipToolRunner.cancelAll()` → `scheduler.stopAndCancelAll()`(기기별 취소 로그) → `periodicTasks.stop()` | 약 1초 | 스케줄러·주기 작업을 4→0으로. 이유: 1~3단계 사이(최대 수 초)에 45초 만기가 오면 **종료 중인데 PC 플러그가 꺼짐**(Fail-safe 위반). 주기 작업도 취소된 chip-tool로 헛점검하지 않게 |
| 1 | `httpServer.stop()`(진행 중 핸들러가 끝날 때까지 대기) | 보통 ~1초, **TCP 등록 중이면 최대 약 21초**(아래) | 같음 |
| 2 | (커미셔닝 서비스 — 13번에서) | — | 13번 전에는 없음 |
| 3 | `tcpDriver.stopServer()` | <1초 | 같음 |
| 4 | (비움 — 0으로 옮김) | — | — |
| 5 | `database.close()` → `return 0` | <1초 | 같음 |

- 소멸 순서: main 지역 객체의 선언 순서를 `database → scheduler → manager → …`로 두어 역순 소멸이 위 순서와 맞게 함. `MatterController::shutdown()`은 지금 로그만 — 그대로.

**11~13 사이 TCP 등록 중 종료(5초 초과 여부)**: **넘을 수 있다.** 동기 E3(TCP_DIY)는 HTTP 작업 스레드에서 BLE 스캔 5초 + 연결 0.8초 + 쓰기 + 접속 대기 최대 15초(`TCPDriver.cpp:57~117`)를 돌고, `httpServer.stop()`은 그 핸들러가 끝나길 기다린다 → 최악 약 21초. Matter 페어링은 0단계 `cancelAll`로 약 1초 안에 끝남. **13번 취소 플래그(CommissioningService)로 해소 예정**(02 3.6 인용 줄·09 2절 3과 같음). 그때까지는 위험 수용 + 두 번째 신호로 즉시 종료 가능(D5).

## 4. K-4 재시작 겹침 실기 계획 (사용자 실행)
- 전제(코드 확인): 운영 서버는 이 저장소의 `build/`에서 돌고 `../db`·`../config`를 쓴다. 포트 8000·8080은 하드코딩이라 운영이 켜져 있으면 시험 서버는 무조건 `EADDRINUSE`로 끝나 **겹침 시험이 성립하지 않는다**. 같은 폴더 깊이에서 시험 빌드를 돌리면 운영 DB·토큰을 쓰게 된다.
- 선택지:
  - (가) 지금(11번 뒤): 1차 실기처럼 별도 사본(`~/hac-field` 방식)에서, **운영 서버를 잠시 중지**하고 시험 → 🔒 운영 영향(rules/server.md 승인). 끝나면 운영 재시작
  - (나) **2차 배포 전 실기(14번 뒤, 어차피 운영을 바꾸는 창)에 함께** — 결과가 필요한 곳은 "재시도 B 도입 여부"뿐이라 배포 전에만 알면 됨
  - (다) 포트 환경 변수 추가로 운영과 병행 — 설계에 없는 범위 추가
- 추천: **(나)**. 절차는 ADR-010 K-4 그대로 + 11번 확인 항목 R-1: `kill -TERM` 뒤 5초 안에 종료 코드 0, 로그에 단계별 종료 줄과 `[Scheduler] … 취소` 줄. 지연 OFF 대기 중 종료 시 플러그가 꺼지지 않는지(전등으로 시험, 09 K-10 안전 메모와 같음).

## 5. 확인하지 못한 것 (총괄에게)
- **V5·V8·V12②**(Gemini 1차 검증)의 원문·요약이 이 저장소에 없다(원문: 총괄 PC `projects/home-assistant-collab/reviews/gemini-server-verify1-2026-11-20.md`, 이 PC에 없음 확인). 번호 배정만 11번이라 위 목록에 **반영하지 못했다** — 내용을 받으면 해당 하위 단계에 추가한다.
- **G1·G4·G5·G9·G15** 원문(`gemini-server-locks-2026-11-19.md`)도 이 PC에 없다. 진행현황 요약("detach·포인터 수명·지연 중 삭제·테스트 누수")으로 G1·G4 = unpair `detach`(11c), G5 = 지연 중 삭제(11b), G9 = 포인터 수명(11b·11d), G15 = 테스트 누수(11b J5)로 **추정 배정**. 원문과 다르면 정정 필요.
- httplib `stop()`이 진행 중 핸들러를 기다리는 방식은 외부 라이브러리 내부라 읽지 않았다(작업 풀 `shutdown`이 join한다는 선언만 확인). 11d 구현 때 테스트로 확인: 7초 핸들러 중 `stop()` → 핸들러 끝난 뒤 반환.
