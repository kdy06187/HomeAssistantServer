# ADR-002: 동시성 — "한 번에 락 하나" 규칙과 스냅샷 복사

- **날짜**: 2026-11-17
- **상태**: 제안
- **관련 요구사항**: REQ-01, REQ-05, REQ-06, NFR-01, NFR-02, N-01, N-02, B-04, B-07

## 배경
- N-01: `removeDevice`(DeviceManager 락 → TCP 소켓 락)와 TCP 커미셔닝(TCP 소켓 락 → DeviceManager 락)이 반대 순서로 락을 잡는다.
- B-07: chip-tool(최대 약 10초) 동안 전역 락을 쥐어 모든 요청이 멈춘다.
- N-02: MatterController의 맵 3개에 락이 없다. B-04: "ALL" 순회 중 삭제.

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 전역 락 하나로 모든 공유 상태 보호 | 규칙이 가장 단순, 교착 없음 | 느린 하드웨어 작업이 전부를 막음(NFR-02 위반) — 락 밖으로 빼면 결국 B와 같아짐 |
| B. 컴포넌트별 락 + **한 번에 하나만** + 상태 락 안에서는 메모리만 + 스냅샷 복사 후 락 밖 실행 | 교착이 구조적으로 불가능(중첩이 없으니 순환 대기 없음), 느린 작업이 다른 요청을 막지 않음 | 메모리와 DB 갱신이 원자적이지 않아 드문 경쟁 상태를 감수해야 함 |
| C. 단일 작업 큐(Actor/이벤트 루프): 모든 상태 변경을 한 스레드에 전달 | 락이 거의 없음 | 구조 변경 가장 큼, 느린 작업은 결국 다른 스레드 필요, 학습 난도 높음 |
| D. 락 순서(계층) 규칙만 두고 중첩 허용 | 기존 코드 모양 유지 | 규칙 위반을 사람이 지켜야 함, 블로킹 문제(B-07)는 따로 해결 필요 |

## 결정
B. 락을 **상태 락**(메모리만)과 **자원 락**(한 자원의 입출력 직렬화: `TcpConnection::ioMutex_`, `DatabaseManager::mutex_`, 매핑 파일)으로 나누고, 어느 락이든 쥔 채 다른 락을 잡지 않는다. 연결 객체는 `shared_ptr`로 복사해 순회한다. 규칙 L-1~L-7은 `docs/02_설계.md` 3.4.

## 이유
- REQ-01의 "락 순서 규칙 문서화"를 "중첩 금지"라는 가장 강한 규칙으로 만족한다. 지키는지 리뷰하기 쉽다(락 범위 안의 함수 호출만 보면 됨).
- REQ-06·NFR-02: 느린 작업이 모두 락 밖으로 나간다.
- 자원 락은 같은 기기 요청끼리만 기다리게 하므로 REQ-05(b)의 기기별 직렬화와 같다.

## 감수하는 단점과 영향
- 같은 기기의 두 상태 갱신이 DB에 역순으로 기록될 수 있다(`is_active` 1칸, 60초 헬스체크가 바로잡음).
- 삭제와 같은 기기 재등록이 동시에 일어나면 마지막 쓰기가 이긴다(드묾, 로그로 추적).
- 나중에 중첩이 꼭 필요하면 L-7의 고정 순서를 쓰고 설계서를 갱신해야 한다.
- 검증은 TSan과 교착 반복 시험(제한 시간)으로 한다(ADR-004).

## 학습 포인트
- 교착의 4조건(특히 순환 대기), 락 계층(lock hierarchy), 임계 구역 최소화, 스냅샷(copy-then-release), RAII `lock_guard`, `shared_ptr`로 수명 보장.
