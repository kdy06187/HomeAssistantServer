## Q-01 테스트 프레임워크 (REQ-17)

| 대안 | 장점 | 단점 | 관련 REQ |
|---|---|---|---|
| A. GoogleTest(+GoogleMock) | 실무 표준. Mock으로 가짜 드라이버 작성 쉬움. CMake `gtest_discover_tests`로 `ctest` 한 번에 실행 | 외부 라이브러리 추가(승인 필요). 빌드 시간 증가 | REQ-17, REQ-07, NFR-05 |
| B. Catch2 v3 | 문법 간단(`TEST_CASE`/`REQUIRE`), 학습 부담 적음 | Mock 없음(가짜 드라이버는 직접 작성). 국내 실무 사용 빈도 낮음 | REQ-17 |
| C. 자체 assert + `ctest` | 외부 의존 0 | 실패 메시지·테스트 선택·픽스처를 직접 만들어야 함. 테스트가 늘면 유지비 큼 | REQ-17 |

- **GoogleTest 소개**: Google이 만든 C++ 단위 테스트 라이브러리(BSD-3). `TEST(묶음, 이름)` + `EXPECT_EQ` 형태, GoogleMock은 인터페이스의 가짜 구현을 자동 생성.

- **추천: A + FetchContent(버전 고정)**. 근거: REQ-07의 가짜 드라이버 주입을 GoogleMock으로 표준 방식(Test Double 패턴)으로 익힐 수 있고, 다른 PC에서도 같은 버전으로 재현됨.
- 가짜 드라이버는 Mock 자동 생성과 손으로 쓴 Fake(시간 지연·예외 재현용)를 함께 쓴다(설계에서 확정).

선택: ☑ A ☐ B ☐ C / 도입 방식: ☑ FetchContent ☐ 서브모듈 ☐ 시스템 패키지

## Q-02 TLS 프록시와 외부 노출 방식 (REQ-14, I-06)

> **2026-11-18 결정 변경: 보류(나중).** 사용자 결정 "VPN(Tailscale)은 일단 빼고 집 LAN에서 잘 되게 하는 것이 먼저". 아래 Q-02a·b 선택은 외부 접속을 다시 다룰 때의 기록으로만 남긴다. 지금은 LAN `0.0.0.0:8000` 평문(ADR-011), ADR-005는 보류.

### Q-02a 외부 노출·인증서 방식

| 대안 | 장점 | 단점 | 관련 REQ |
|---|---|---|---|
| A. VPN(Tailscale 등, 외부 포트 개방 없음) | 공유기 포트포워딩 불필요, 공격 표면 최소. 1인 사용에 적합. Tailscale은 자체 HTTPS 인증서 발급 기능도 있음 | 앱 기기에 VPN 앱 상시 필요. 외부 서비스 의존 | REQ-14, REQ-15, NFR-03 |
| B. Let's Encrypt + DDNS + 포트포워딩 | 어디서나 표준 HTTPS, 신뢰된 인증서(앱 설정 간단) | 인터넷에 서버 노출 → REQ-15(시도 제한·로그) 구현이 사실상 필수. 도메인·DDNS 관리 필요 | REQ-14, REQ-15 |
| C. 사설 CA/자체 서명(LAN 전용) | 외부 의존 없음 | 앱에 인증서 고정(pinning)·신뢰 등록 필요. 외부 접속 문제는 해결 못 함 | REQ-14 |

- **추천: A**. 근거: 1인·집 LAN에서 외부 노출 없이 외부 접속을 얻는 가장 단순한 방법이라 REQ-15 구현 범위를 작게 유지할 수 있음. 나중에 B로 바꿔도 서버 코드는 같음(프록시 뒤 구조 동일).

선택: ☑ A(Tailscale 개인용 무료) ☐ B ☐ C — 외부 포트는 열지 않는다

### Q-02b 프록시 종류

| 대안 | 장점 | 단점 | 관련 REQ |
|---|---|---|---|
| A. Caddy | 설정 몇 줄, 인증서 자동 발급·갱신 내장 | nginx보다 자료 적음 | REQ-14 |

선택: ☐ A ☐ B ☐ C → **결정: 프록시 미사용.** HTTPS가 필요하면 `tailscale serve`. 집 Wi-Fi 직접 접속 허용 여부와 바인딩 주소는 02_설계에서 비교·추천

### Q-03d 앱 요청: E7 기간(from/to)·집계(day/week/month)

`totalEnergy_mWh`는 누적값이므로 구간 사용량 = 구간 끝 값 − 구간 시작 값(카운터 리셋 시 보정 필요).

| 대안 | 장점 | 단점 | 관련 REQ |
|---|---|---|---|
| A. 서버 집계: `?from&to&bucket=day\|week\|month&tz=Asia/Seoul` → 구간별 사용량 반환 | 앱 단순, 전송량 작음, 리셋 보정 로직 한 곳 | 서버에 타임존 경계 계산 필요(C++17 표준엔 타임존 DB 없음 → 고정 오프셋 사용) | REQ-12, APP-REQ |
| B. 서버는 원본 시계열(`from/to`+limit)만, 앱이 집계 | 서버 변경 최소 | 월 단위면 원본이 limit을 넘음 → 결국 다운샘플링 필요. 앱마다 로직 중복 | REQ-12, APP-REQ |
| C. 서버가 `bucket`별 구간 첫·끝 누적값만, 차이는 앱 계산 | 중간 | 리셋 보정이 앱으로 감 | APP-REQ |

- 타임존: 저장은 UTC 유지. 경계는 (a) 서버 설정의 고정 오프셋(+09:00) 또는 (b) 요청 `tz` 파라미터. 한국은 서머타임이 없어 (a)로 충분.
- 주 경계: 월요일 시작(ISO 8601) 권장.
- **추천: A + 고정 오프셋 +09:00, 주는 월요일 시작**. 근거: 리셋 보정·경계 계산을 서버 한 곳에 두는 편이 정확하고, 인덱스(device_id, timestamp)로 구간 조회가 빠름. 계약 변경은 MINOR(새 파라미터 추가, 없으면 기존 동작).

선택: ☑ A ☐ B ☐ C / 경계: ☑ 고정 +09:00 ☐ 요청 tz

## Q-04 chip-tool 비밀값 노출 (REQ-16, N-07)

조사 결과(chip-tool 소스 읽기 전용, 실행 안 함): 파일/환경변수로 SSID·비밀번호를 받는 옵션 없음. 값 접두사는 `hex:`, `str:`만. `interactive start`는 표준 입력(readline)에서 명령을 읽음. `interactive server`(WebSocket) 모드도 있음.

| 대안 | 장점 | 단점 | 관련 REQ |
|---|---|---|---|
| A. `interactive start` + stdin 파이프로 명령 전달 | 비밀값이 argv(`/proc/<pid>/cmdline`)에 안 나타남 | 출력 파싱·종료 감지 방식이 바뀜, readline 프롬프트 처리 필요. 동작은 **실기 확인 필요** | REQ-16, REQ-10 |
| B. 현 방식 유지 + 위험 문서화 | 변경 없음 | 같은 PC의 로컬 계정이 `ps`로 볼 수 있음(1인 PC면 실제 위험 낮음). REQ-16 기준 미충족 → 범위 제외 재협의 | REQ-16, NFR-03 |
| C. `interactive server`(WebSocket) 상주 프로세스로 명령 | argv 노출 없음, 매번 프로세스 기동 비용 없음 | 상주 프로세스 수명·재접속 관리 추가, 구조 변경 큼. 실기 확인 필요 | REQ-16, REQ-06 |

- 금지: chip-tool 소스 수정(서브모듈 수정)은 대상 아님.
- 보조책(모든 대안 공통 가능): `/proc`의 `hidepid=2` 마운트로 다른 사용자가 남의 프로세스 인자를 못 보게 함(OS 설정, 서버 코드 무관).
- **추천: A(실기 시험 통과 시), 실패하면 B로 후퇴**. 근거: 코드 변경이 커미셔닝 실행 함수 한 곳에 국한되고 REQ-10 비동기화와 함께 고치면 중복이 적음. 먼저 사용자가 실기로 stdin 방식 동작을 확인.

선택: ☑ A(실기 확인 뒤) ☐ B(A 실패 시) ☐ C

| N-02 | 코드는 최신 50건을 오름차순 반환. 계약서 예시는 내림차순으로 보임 → 계약 설명 오류. 11-04 이후 기록 없음은 원인 미확인(서버 미실행 기간 가능, 실기 확인 필요) | REQ-12, Q-03b·d. 계약서 순서 설명 정정 | 없음(설명 정정만, 동작 불변) |

| APP-REQ | E7 기간·집계 | Q-03d, REQ-12(인덱스) | MINOR(선택 파라미터 추가) |

### N-03 상세 (원인은 코드 근거 기반 추정, 실기 확인 필요)

- 추정 원인: 인증이 `set_pre_routing_handler`에서 본문 읽기 전에 실행 → 401 + `Connection: close` 후 소켓 닫음 → 수신 버퍼에 남은 POST 본문 때문에 리눅스가 RST 전송 → 클라이언트가 401을 못 읽음. GET은 본문이 없어 정상. `set_pre_request_handler`도 본문 읽기 전이라 그대로는 해결 안 됨.

| 대안 | 장점 | 단점 |
|---|---|---|
| a. 라우트 핸들러를 감싸는 인증 래퍼(Decorator 패턴): 본문을 읽은 뒤 인증 | httplib 수정 없이 확실. Q-05 A의 `Authenticator`와 자연스럽게 결합 | 모든 라우트 등록에 래퍼 적용 필요(누락 위험 → 등록 함수 하나로 강제) |
| b. 401에서도 연결 유지해 httplib가 본문을 소비하게 함 | 기존 구조 유지 | httplib 내부 동작에 의존, 가능 여부 미확인(라이브러리 수정 불가) |
| c. 401 응답 전 남은 본문을 직접 읽어 버림 | 변경 작음 | pre-routing 단계에서 소켓 접근 수단이 있는지 미확인, 본문 크기 제한과 충돌 |

- 추천: a. 단, 본문을 먼저 읽으므로 인증 전 본문 크기 제한(REQ-15)을 같이 둔다.
