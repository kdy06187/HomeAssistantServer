# ADR-011: LAN 우선 — HTTP 바인딩 `0.0.0.0` 기본 + 환경 변수, 외부 접속은 보류

- **날짜**: 2026-11-18
- **상태**: 제안 (상위 결정 "VPN은 일단 빼고 집 LAN 먼저"는 사용자 결정 2026-11-18). ADR-005의 바인딩 결정을 **대체**한다
- **관련 요구사항**: REQ-14(보류), REQ-15, NFR-03, I-06(보류)

## 배경
- 사용자 결정(2026-11-18): Tailscale·`tailscale serve`는 일단 뺀다. 집 LAN에서 앱이 잘 되는 것이 먼저다. 외부 접속(REQ-14·Q-02)과 평문 HTTP(I-06)는 나중에 다룬다.
- 그래서 ADR-005의 `127.0.0.1` 바인딩은 쓸 수 없다(앞에 TLS 종단이 없으면 앱이 닿지 않음).
- 나중에 TLS 종단(VPN·리버스 프록시)을 붙일 때 서버 코드를 크게 고치지 않아야 한다.

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. **`0.0.0.0:8000` 기본, `HAC_HTTP_BIND`로 변경 가능** | 지금 동작 그대로(설정 0). 서버 IP가 DHCP로 바뀌어도 시작 실패 없음. 나중에 `127.0.0.1`로 바꾸기만 하면 프록시 뒤 구성 | PC의 모든 네트워크 카드(다른 NIC·Docker 브리지 등)에 열림. 평문 토큰 노출(I-06) 그대로 |
| B. LAN IP 지정(`HAC_HTTP_BIND=192.168.x.y` 필수) | 지정한 카드에만 열림 | 서버 IP가 바뀌면 바인딩 실패 → 고정 IP 설정 필요. 네트워크보다 먼저 뜨면 실패(시작 순서 의존). 설정 없으면 시작 불가 |
| C. `127.0.0.1` + 앞단 TLS 종단(ADR-005) | 평문 노출 없음 | 앞단을 지금 안 두기로 함 → 보류 |

## 결정
A. 기본 `0.0.0.0:8000`, 환경 변수 `HAC_HTTP_BIND`(주소만)로 바꿀 수 있다. TCP 8080은 `0.0.0.0` 고정(LAN 기기용).
나중을 위해 구조만 둔다(지금 기능은 추가하지 않음):
- 바인딩 주소는 `main`이 환경 변수에서 읽어 `HTTPServer` 생성자로 넘긴다(한 곳).
- 요청자의 주소 판정은 `HTTPServer::clientAddressOf(req)` 한 함수에서만 한다. 지금은 `remote_addr` 그대로. 프록시를 붙이면 이 함수만 "프록시에서 온 요청이면 `X-Forwarded-For` 참고"로 바꾼다.
- 시작 로그에 바인딩 주소와 "평문 HTTP" 표기를 남긴다.

## 이유
- 사용자 목표(LAN에서 먼저 잘 됨)를 코드·설정 변경 없이 만족한다.
- B의 이점(카드 제한)은 1인 집 PC에서 작고, IP 변경·시작 순서 위험이 더 크다.
- 바인딩 설정과 주소 판정을 한 곳에 모아 두면 C로 갈 때 바뀌는 곳이 둘뿐이다(Open-Closed에 가까운 확장 지점).

## 감수하는 단점과 영향
- **평문 HTTP**: 같은 LAN에서 토큰을 엿볼 수 있다(I-06 보류). 집 Wi-Fi 비밀번호가 사실상 경계다. `06_배포.md`의 "LAN 한정 위험"에 적는다.
- 서버 PC에 다른 네트워크 카드가 있으면 거기에도 열린다. 필요하면 B처럼 주소를 지정한다(같은 변수).
- 다시 볼 조건: 집 밖에서 접속이 필요해지면 ADR-005를 다시 열어 C(또는 다른 TLS 종단)를 정하고 REQ-14·Q-02를 재개한다.

## 학습 포인트
- 바인딩 주소의 의미(0.0.0.0 / 특정 IP / 루프백), 확장 지점(seam)을 미리 한 곳에 모으기, YAGNI(필요할 때 기능 추가).
