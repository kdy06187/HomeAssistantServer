# ADR-010: 지연 명령 스케줄러와 SIGTERM 종료 순서

- **날짜**: 2026-11-17
- **상태**: 제안 (수치·정책은 사용자 결정 Q-06 B: 응답 1초, 종료 5초, 대기 중 지연 OFF는 취소·로그)
- **관련 요구사항**: REQ-08, REQ-09, NFR-02, B-06, N-12, N-13

## 배경
- 지연 OFF(45초)는 명령마다 `detach` 스레드가 sleep 후 실행한다. 취소 수단이 없고(B-06), 같은 OFF를 두 번 보내면 종료 메시지·타이머가 중복되며, 종료 시 수명 보장이 없다(N-13).
- `svr.stop()`을 부르는 곳이 없고 `accept`가 블록돼 종료 코드에 도달하지 못한다(N-12).
- REQ-08은 "작업 스케줄러 도입 여부는 2단계 결정"으로 남겨 두었다.

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 명령마다 스레드 + 취소 플래그(`shared_ptr<atomic<bool>>`) 맵 | 기존 모양과 비슷 | 스레드 수 증가, join 관리가 흩어짐, 가짜 시계 시험이 sleep에 묶임 |
| B. 스케줄러 1개(스레드 1개, 기기당 대기 작업 1개, 조건변수 대기), `tick(now)`를 공개해 테스트는 직접 호출 | 취소·중복 방지·종료 정리가 한 곳, FakeClock으로 45초를 즉시 시험 | 만기 작업이 순차 실행(한 작업이 chip-tool 5초면 다음 작업이 밀림) |
| C. 범용 스레드풀 + 타이머 라이브러리 | 확장성 | 요구 대비 과함, 외부 의존 |

종료 신호 처리:
| 선택지 | 장점 | 단점 |
|---|---|---|
| a. `signal()` 처리기에서 플래그만 세움 + main 폴링 | 흔한 방식 | 폴링 지연, 처리기 안 제약(async-signal-safe) 신경 써야 함 |
| b. 시작 시 모든 스레드에서 신호를 막고 main이 `sigwait` | 신호를 평범한 코드 흐름으로 받음, 제약 없음 | 리눅스/POSIX 전용(현재 환경과 같음) |

## 결정
B + b.
- 스케줄러 규칙: 같은 기기·같은 명령이 대기 중이면 새로 만들지 않고 남은 시간을 돌려줌(드라이버 재실행 없음 → 종료 메시지 1회), 다른 명령이 오면 대기 작업 취소 후 진행, 기기 숨김 삭제 시 취소. 작업은 락 밖에서 실행.
- 종료 순서(5초): 0 chip-tool 전체 취소 → 1 HTTP 정지 → 2 커미셔닝 취소 → 3 TCP 정지 → 4 지연 명령 취소(기기별 로그)·주기 작업 정지 → 5 DB 닫기 → 종료 코드 0. 상세는 `docs/02_설계.md` 3.6.
- 취소로 끝난 하드웨어 호출은 `Cancelled`로 구분해 상태를 OFFLINE으로 바꾸지 않는다(종료 직전 DB 오염 방지).

## 이유
- REQ-08의 두 완료 기준(지연 중 ON이면 꺼지지 않음, OFF 2회에 메시지 1회)과 REQ-09의 수명 보장을 한 구성요소로 해결한다.
- 대기 작업이 기기당 최대 1개이고 기기 수가 적어 순차 실행의 지연은 무시할 만하다.
- Q-06 B(취소)는 서버 종료가 PC 전원 차단을 일으키지 않는 Fail-safe 쪽이다.

## 감수하는 단점과 영향
- 종료 직전에 OFF를 보낸 경우 종료 메시지는 PC에 갔는데 전원은 안 꺼진다(로그로 남김, 사용자가 다시 OFF).
- 지연 작업은 메모리에만 있어 재시작하면 사라진다(재시작 = 취소와 같은 정책).
- 진행 중 HTTP 요청이 1초 넘게 걸리면 5초 목표를 넘을 수 있다 → 0단계에서 chip-tool을 먼저 끊어 상한을 줄인다. httplib `stop()`의 대기 방식은 확인 필요(C-9).

## 학습 포인트
- 타이머 큐/스케줄러, 조건변수 `wait_until`, 테스트 가능한 시간(Clock 주입), 정상 종료(graceful shutdown)와 POSIX 신호 처리.

### (b) 8080 바인딩 실패 처리 — 이 ADR에 두는 근거
서버 **수명 주기**(시작·종료)를 다루는 ADR이 이것뿐이고, 재시도 간격은 이 ADR의 "종료 5초 상한"에서 나온다(재시작 때 이전 인스턴스가 아직 종료 중이면 포트가 겹침). ADR-011은 8000 **주소** 선택만 다루므로 맞지 않는다.

**현재 동작(1차 9b, b8df9f4)**: `main`이 8080을 **8000보다 먼저** 열고, 실패하면 오류 로그 후 종료 코드 1. 8000은 `waitUntilReady(5초)` 실패 시 종료 코드 1. → 실기에서 본 "8000만 켜진 반쯤 켜짐"은 **이미 해소**. 2차 10번에 남은 것은 "즉시 종료로 충분한가"와 httplib `SO_REUSEPORT`(같은 계정 두 인스턴스가 8000을 함께 열 수 있음, `08_검증-1차.md` 5절 관찰)뿐이다.

| 대안 | 장점 | 단점 |
|---|---|---|
| **A. 현재 유지: 즉시 종료(코드 1), Fail-fast** | 코드 0, 원인이 바로 보임, 보안상 fail-closed(SEC-1차-04) | 이전 인스턴스가 SIGTERM 종료 중(최대 5초)일 때 바로 다시 켜면 실패 → 사람이 다시 켜야 함 |
| B. 짧은 재시도 후 종료: 1초 간격 최대 6회(= 종료 상한 5초 + 여유 1초), 그래도 실패면 코드 1 | 재시작 직후 겹침을 흡수. 결과는 A와 같은 Fail-fast | 시작이 최대 6초 늦어짐. 다른 프로그램이 포트를 계속 쥐고 있으면 6초 뒤 같은 결과 |
| C. 8000만 유지 + 상태 표시(Degraded mode) | 앱 조회·Matter는 됨 | 바로 그 "반쯤 켜짐". 상태 API·앱 표시 추가 필요(요구 없음, YAGNI), 9b 결정과 반대 |
| (운영) systemd `Restart=on-failure` | 코드 없이 재시도 | 지금은 서비스가 아님(07 P-2). 4.5 배포 방식 결정 사항 |

- **추천: A 유지 + 10번에서 httplib `SO_REUSEPORT` 끄기**(두 번째 인스턴스가 8000에서도 실패하게, HTTP 래퍼 안 한 곳). 11번(SIGTERM)이 들어온 뒤 재시작 실패가 실제로 보이면 B로 바꾼다(재시도는 `TcpServer`가 아니라 `main`의 시작 단계 한 곳에).
