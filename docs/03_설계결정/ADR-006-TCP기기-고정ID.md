# ADR-006: TCP_DIY 기기의 고정 ID — 커널 ARP 표의 Wi-Fi MAC

- **날짜**: 2026-11-17
- **상태**: 제안 (상위 결정 "고정 ID, IP는 별도 칸"은 사용자 채택 Q-03c, 2026-11-17). **실기 확인 C-1~C-3 통과가 전제**
- **관련 요구사항**: REQ-13, REQ-05, NFR-04, NFR-06, N-10

## 배경
- 지금 ID는 `ARD_<접속 IP>`(`src/TCPDriver.cpp:221`). DHCP로 IP가 바뀌면 다른 기기가 되고, 통계·이력이 끊기며 숨김 삭제 후 복구(ADR-007)도 불가능하다.
- 펌웨어 수정 불가(NFR-04): 기기는 접속 때 ID를 보내지 않는다. 서버가 가진 정보만 써야 한다.
- 커미셔닝 때 SimpleBLE로 BLE 이름 `TCPDevice_DIY`를 찾는다(`TCPDriver.cpp:75~`). 보드는 ESP32/Arduino류로만 문서화(확정 아님).

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. **TCP 접속 IP로 커널 ARP 표(`/proc/net/arp`)에서 Wi-Fi MAC을 읽어 `TCP_<MAC12>`로 ID** | 펌웨어 변경 0, 접속마다 같은 기기를 알아봄(IP가 바뀌어도), 권한 불필요·읽기 전용 | 서버와 기기가 같은 L2 LAN일 때만 의미(라우터 너머면 라우터 MAC). 중계기의 MAC 변환, 펌웨어의 MAC 변경·무작위화가 있으면 깨짐 → 실기 확인 필요 |
| B. 커미셔닝 때 BLE 주소를 저장하고 Wi-Fi MAC과 대응 | 커미셔닝 시점의 기기를 확실히 특정 | 재접속 때는 BLE 정보가 없어 결국 Wi-Fi 쪽 식별(A)이 필요. BLE→Wi-Fi MAC 관계(ESP32는 흔히 +2)는 보드 의존, BLE 무작위 주소 가능 → 단독으로는 불가 |
| C. 서버 발급 UUID + 마지막 IP 매핑 | ID는 바뀌지 않음 | 접속한 소켓이 어느 UUID인지 IP로만 판단 → IP가 바뀌면 연결이 끊긴 것과 같음(지금 문제와 동일) |
| D. 공유기 DHCP 고정 할당 + `ARD_<IP>` 유지 | 코드 변경 0 | 공유기 설정 의존, "고정 ID" 결정과 다름, 공유기 교체 시 깨짐 |

## 결정
A를 주 방식으로 쓰고, B는 진단용 로그로만 쓴다(커미셔닝 로그에 BLE 주소 기록 — 실기에서 관계 확인용, 판정에는 쓰지 않음).

| 규칙 | 내용 |
|---|---|
| ID 형식 | `TCP_` + MAC 16진 대문자 12자(콜론 없음, URL 경로에 안전). 예 `TCP_A1B2C3D4E5F6` |
| 조회 시점 | `accept` 직후. TCP 핸드셰이크에서 서버가 이미 상대에게 응답을 보냈으므로 보통 이웃 항목이 있다. 없거나 미완성(플래그 0x0, MAC 00:..:00)이면 100ms 간격 3회 재시도 |
| 식별 거부(S-04, 2026-11-18) | 접속 IP가 서버 수신 주소와 같은 서브넷이 아니거나, 얻은 MAC이 기본 게이트웨이(`/proc/net/route`)의 MAC과 같으면 식별 실패(라우터 너머 접속) |
| 그래도 없음 | 등록된 TCP 기기 중 `ip`가 접속 IP와 같은 기기가 **정확히 1개**면 그 ID로 연결하고 경고 로그. 아니면 "미식별 연결"(제어 불가, 로그). 미식별 연결은 30초 뒤 닫는다(S-07, 펌웨어 재접속 동작은 C-5) |
| 같은 ID 연결이 이미 있음(교체 규칙 하나, S-04) | IP가 같든 다르든 같은 규칙: 기존 연결에 상태 요청 1회(1초, 기존 메시지)로 생존 확인 → 응답 있으면 **새 연결 거부**(오류 로그, MAC 위조·중계기 변환 의심) / 응답 없으면 기존 연결 close 후 새 연결로 교체(IP가 바뀌었으면 경고 로그). 확인은 그 연결의 `ioMutex_`만 잡고 수행(락 규칙 L-3) |
| 8080 입력 상한(S-07) | 한 줄 최대 4KiB(넘으면 close), 동시 연결 최대 32(넘으면 새 연결 즉시 close), 미식별 연결 30초 |
| IP | `devices.ip`에 마지막 접속 IP 저장, 접속마다 갱신. E1 응답에 `ip` 필드 |
| ~~레거시 이전~~ **(2차 보완 ③으로 삭제 — 승인 2026-11-21. 결정: 사용자 11-21)** | `ARD_<ip>` 기기는 그 IP에서 첫 접속이 올 때 `TCP_<MAC>`으로 3개 테이블을 한 트랜잭션에서 이름 변경(`docs/02_설계.md` 4.2). 조건(S-06): `TCP_<MAC>`이 활성·숨김 어느 쪽으로도 없음, `ARD_<ip>`가 지금 연결 중이 아님, 마이그레이션 백업(`.bak-v0`)이 있음. 하나라도 아니면 건너뛰고 경고 로그 |
| 커미셔닝 신규 판정 | 커미셔닝 시작 이후 접속 + 활성 기기 ID 아님. 숨김 기기 MAC이면 복구(ADR-007). 결과 ID가 활성 기기면 덮어쓰지 않고 `ALREADY_REGISTERED`(S-05) |
| ARP 오래된 항목(stale) | 이웃 상태(REACHABLE 등)는 `/proc/net/arp`에 없고 netlink가 필요해 보지 않는다. 기기는 접속 전에 서버에 ARP 요청을 보내므로 커널 항목이 그때 갱신된다고 보고, 실기 C-1에 "IP 재할당 직후" 시험을 추가해 확인한다 |

## 이유
- NFR-04를 지키면서 "IP와 무관한 ID"를 얻는 유일한 서버 측 정보다. 같은 집 LAN 구성(서버·기기가 같은 공유기 아래)과 맞는다.
- ESP32 계열은 보통 공장에서 정한 고유 MAC으로 Wi-Fi에 접속하고, 휴대폰·PC 운영체제의 "개인 MAC 무작위화"는 일반적으로 해당하지 않는다. 다만 펌웨어가 MAC을 바꿀 수 있으므로 단정하지 않고 실기 확인(C-1·C-3)을 전제로 한다.
- 커널이 이미 가진 표를 읽기만 하므로 추가 권한·패킷 전송이 없다.

## 감수하는 단점과 영향
- **실기 확인 필요**: C-1 접속 직후 ARP 항목 존재·재부팅 후 MAC 동일, C-2 중계기 MAC 변환 없음, C-3 펌웨어 MAC 고정, C-4 BLE 주소 관계(참고). 하나라도 실패하면 이 ADR을 다시 연다(후퇴안: D + `ARD_<IP>` 유지, 위험 문서화).
- 서버가 VPN·다른 서브넷 너머의 TCP 기기를 받는 구성은 지원하지 않는다(현재 요구 없음).
- 기기 ID가 바뀌므로 REST v2.0 MAJOR 변경이다. 앱은 ID를 불투명 문자열로 다뤄야 한다.
- IPv4만 다룬다(현재 수락 소켓이 `AF_INET`).
- 8080은 무인증이라(A-06 범위 밖) 같은 LAN에서 MAC을 위조하면 막을 수 없다. 교체 규칙은 "살아 있는 정상 연결을 빼앗기지 않게"만 줄인다. `06_배포.md` "LAN 한정 위험"에 적는다(S-04).
- 생존 확인 동안(최대 1초) 수락 스레드가 다음 접속을 받지 못한다. 충돌은 드물어 감수한다.
- N-10(범위 밖)이 일부 해소된다: 커미셔닝 중 "아무 새 소켓"이 아니라 "새로 접속한, 활성이 아닌 MAC"을 채택.

## 학습 포인트
- L2(MAC)와 L3(IP) 식별자의 차이, ARP/이웃 표, 자연 키 vs 대리 키(Natural vs Surrogate key), 지연 마이그레이션(lazy migration).

### (d) T5 — PC 종료 메시지를 PC 에이전트에게만 — 12b(11번에서 옮김, 결정: 사용자 11-21)
현재: `PCDriver`가 `IMessageSender::broadcast` → `TCPDriver::broadcast`가 연결 목록을 **순차** `sendCommand`(각 1초 마감). 실기: 스위치는 SYSTEM에 응답하지 않아 1초 뒤 실패·연결 닫힘(곧 재접속), PC 에이전트(`.103`)는 즉시 success. 무응답 기기 수 × 1초 뒤에 PC가 받는다.

**판별 근거 검토**
| 근거 | 쓸 수 있나 | 이유 |
|---|---|---|
| `DriverType`(PC_DRIVER) | 아니오 | PC_DRIVER는 **전원 플러그(Matter 기기)**에 붙는다(실기 2.4). 그 플러그와 8080의 어느 연결이 같은 PC인지 알려 주지 않는다 |
| 등록 정보(devices) | 지금은 없음 | PC 에이전트는 등록 대상이 아니다(`06_배포.md`). 등록하려면 새 칸·API가 필요 |
| 핸드셰이크(접속 직후 첫 줄) | 예(실기 필요) | PC 에이전트는 접속하자마자 INIT 줄(45B)을, 스위치는 재접속 직후 상태 줄(68~69B)을 보낸다(실기 4.1·4.4). 지금은 둘 다 "요청 전 남은 입력"으로 버려진다 |

**현재 코드 정정(코드 확인, Gemini 지적 — 총괄 판정)**
- `PCDriver::handleCommand`(`PCDriver.cpp:14~31`)는 `broadcast`(반환 `void`)의 결과를 보지 않고 **무조건 `{true, 45}`**를 돌려준다. 에이전트 응답(success 여부)은 판단에 쓰이지 않는다 → "가짜 success로 전원 차단" 경로는 없고, (가)에서 실제 위험은 **"진짜 에이전트가 메시지를 못 받은 채 45초 뒤 차단"**이다.
- 상태가 `OFF`/`OFFLINE`이면 `{false, 0}`을 돌려주는데, `DriverManager::executeDriversForDevice`(`DriverManager.hpp:42~59`)는 `proceed_hardware=false`를 하나라도 받으면 막고, `DeviceManager::executeCommand`(`DeviceManager.cpp:136~137`)가 `Failed(CommandBlocked)`로 응답한다. 즉 지금도 **"이미 꺼짐" OFF는 통과가 아니라 차단(v2.0이면 409)**이다. 앞 제안의 (나) 설명 "OFF/OFFLINE이면 기존처럼 통과"는 틀렸으므로 아래처럼 고친다.
