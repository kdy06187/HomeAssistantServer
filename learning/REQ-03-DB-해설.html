REQ-03 해설

DB를 스레드에 안전하게, 스키마를 버전으로, 업그레이드 전에는 백업 (3단계 3번, 학습 강도: 균형)

1. 한눈에 보기

  • 무엇: DatabaseManager에 뮤텍스를 달고, PRAGMA user_version 기반 마이그레이션(v0 → v1)과 안전한 백업을 넣었다. insertDevice가 INSERT를 두 번 실행하던 버그도 고쳤다.
  • 왜: sqlite3 연결 하나를 HTTP 스레드와 헬스체크 스레드가 동시에 쓴다. 또 devices에 ip·deleted_at 열을 추가해야 하는데, 사용자의 실제 DB를 잃으면 안 된다.
  • 안전: 이미 v1이면 아무것도 안 한다. 실패하면 되돌리고 서버 시작을 멈춘다.

2. 흐름 그림 (init)

백업(backupLocked) 4단계

단계동작왜
1open(O_CREAT|O_EXCL, 0600)으로 빈 파일 생성같은 이름이 있으면 실패해 덮어쓰기를 막는다. 처음부터 0600이라 남이 읽을 수 있는 순간이 없다
2VACUUM INTO로 스냅샷 기록단순 파일 복사는 쓰는 중에 복사하면 깨진 파일이 될 수 있다
3백업을 읽기 전용으로 열어 PRAGMA integrity_check = ok 확인검증하지 않은 백업은 백업이 아니다
4오래된 백업 정리(3개 보관)디스크가 무한히 차지 않게

어느 단계든 실패하면 만든 백업 파일을 지우고 false를 돌려준다(failAndRemove).

3. 코드 해설

(a) 뮤텍스와 *Locked 패턴

- bool DatabaseManager::updateDeviceState(...) {
-     const char* sql = "UPDATE devices SET is_active = ? ...";
+ bool DatabaseManager::updateDeviceState(...) {
+     const char* sql = "UPDATE devices SET is_active = ? ...";
+     std::lock_guard<std::mutex> lock(mutex_);   // 이 함수가 끝날 때까지 다른 스레드는 DB 접근 대기

// init()은 락을 잡은 채 아래를 부른다 - 락을 또 잡지 않는 버전
+ bool initEnergyTableLocked();   // 호출자가 mutex_를 이미 잡았다고 가정
+ bool initEnergyTable() { lock_guard lock(mutex_); return initEnergyTableLocked(); }  // 바깥에서 부르는 용
무엇: sqlite3 연결(db_)을 한 번에 한 스레드만 쓰게 한다.
왜: 연결 하나를 여러 스레드가 동시에 쓰면 데이터 경쟁(data race)이다. std::mutex는 재진입이 안 돼서, init이 락을 잡고 initEnergyTable(자기도 락을 잡음)을 부르면 자기 자신을 기다리며 영원히 멈춘다(자기 교착). 그래서 "락 안 잡는 *Locked 내부 함수 + 락 잡는 공개 함수" 쌍으로 나눴다.
빼면: 헬스체크가 쓰는 동안 HTTP 요청이 같은 db_를 건드려 드물게 깨지거나 죽는다. 재현이 어려운 버그라 TSan으로 잡는다.

(b) 락과 트랜잭션은 역할이 다르다 — updateEnergyStat

+ std::lock_guard<std::mutex> lock(mutex_);
+ if (!execLocked("BEGIN IMMEDIATE;", ...)) return false;
  ... SELECT → delta 계산 → INSERT OR REPLACE ...
- sqlite3_step(stmt);                      // 결과를 확인하지 않음
+ saved = (sqlite3_step(stmt) == SQLITE_DONE);
+ if (!saved || !execLocked("COMMIT;", ...)) { sqlite3_exec(db_, "ROLLBACK;", ...); return false; }
왜: 뮤텍스만으로 스레드 경쟁은 막지만, 저장이 실패했을 때 "일부만 바뀐" 상태를 되돌리진 못한다. 트랜잭션만으로는 같은 연결을 쓰는 두 스레드의 호출이 섞이는 걸 막지 못한다. 둘은 서로 보완한다.
빼면: 락을 빼면 위 그림처럼 갱신 손실, 트랜잭션을 빼면 저장 실패를 모른 채 true를 돌려준다.

(c) insertDevice의 이중 step 버그

- bool success = (sqlite3_step(stmt) == SQLITE_DONE);
- if (sqlite3_step(stmt) != SQLITE_DONE) {   // 한 번 더 실행!
+ bool success = (sqlite3_step(stmt) == SQLITE_DONE);
+ if (!success) {
무엇: 에러 로그 조건에서 step을 또 불렀다.
왜 문제: SQLite는 DONE 뒤에 step을 다시 부르면 문장을 자동으로 reset하고 처음부터 다시 실행한다. 그래서 INSERT가 두 번 실행됐다. INSERT OR REPLACE라 결과 데이터는 같아 보여서 안 들켰지만, 트리거나 행 번호에는 영향이 있다. 테스트는 INSERT 횟수를 세는 트리거로 "정확히 1번"을 확인한다.
교훈: 결과를 변수에 저장하고 그 변수를 쓴다. step은 부수효과가 있는 호출이다.

(d) 마이그레이션: 한 트랜잭션, 실패하면 시작 중단

"BEGIN IMMEDIATE;"
"ALTER TABLE devices ADD COLUMN ip TEXT;"
"ALTER TABLE devices ADD COLUMN deleted_at TEXT;"
"CREATE INDEX IF NOT EXISTS idx_history_device_time ON state_history_logs(device_id, timestamp);"
"UPDATE devices SET ip = substr(device_id, 5) WHERE protocol_type = 1 AND device_id LIKE 'ARD_%';"
"PRAGMA user_version = 1;"
"COMMIT;"
// 실패 시: sqlite3_exec(db_, "ROLLBACK;", ...) 후 false
왜 한 트랜잭션: SQLite는 DDL(ALTER, CREATE INDEX)도 롤백된다. 두 번째 ALTER에서 실패하면 첫 번째도 취소돼 v0 상태로 돌아간다(테스트 MidMigrationFailureRollsBackEarlierAlter). user_version을 맨 끝에 올리므로 "버전은 올랐는데 열이 없는" 상태가 생기지 않는다.
멱등성: user_version >= 1이면 이 코드에 들어가지 않으므로 몇 번을 시작해도 같다. 그래서 ALTER가 중복 실행될 일이 없다.
롤백 안전: 옛 실행 파일으로 돌아가도 v1 DB를 쓸 수 있다. 옛 코드는 INSERT ... (열 이름 나열), SELECT 열 이름처럼 열을 이름으로 지정하기 때문에 새 열이 있어도 영향이 없다(LegacySqlStillWorksOnV1Db). 만약 SELECT *나 열 이름 없는 INSERT였다면 깨진다.

(e) 백업 보관: "방금 만든 것은 항상 유지"

    ...
    if (name != keepName && name.compare(0, prefix.size(), prefix) == 0) names.push_back(name); // 방금 만든 것은 후보에서 제외

테스트가 찾은 버그 사례: 처음엔 파일명 시각순으로 정렬해 최신 3개만 남겼다. 그런데 시계가 뒤로 가서(예: 기존 백업이 2030년, 지금은 2026년) 방금 만든 백업이 "가장 오래된 것"이 되면 만들자마자 지워졌다. 마이그레이션 직전의 유일한 안전망이 사라지는 것이다. 그래서 방금 만든 이름을 후보에서 빼고 나머지 중 2개와 합쳐 3개를 유지한다(KeepsFreshBackupEvenIfOlderStampsLookNewer).
정렬 키도 파일명 끝의 시각(마지막 - 뒤)만 쓴다. v9와 v10처럼 자릿수가 달라도 시간순이 맞게 하려는 것이다.

4. 용어 풀이

  • 데이터 경쟁(data race): 두 스레드가 같은 데이터를 동시에 쓰는데 순서 장치가 없는 상태. 결과가 실행마다 달라진다.
  • read-modify-write: 읽고, 계산하고, 다시 쓰는 3단계. 중간에 끼어들면 갱신 손실이 난다.
  • 재진입 불가(non-recursive): 이미 잡은 락을 같은 스레드가 또 잡으면 영원히 멈춘다는 뜻.
  • PRAGMA user_version: SQLite 파일 헤더에 있는 정수 하나. 앱이 스키마 버전 표시용으로 자유롭게 쓴다.
  • 멱등성(idempotent): 여러 번 실행해도 한 번 실행한 것과 결과가 같은 성질.
  • fail-fast: 이상이 생기면 숨기지 않고 바로 멈춰서 더 큰 손상을 막는 설계.
  • VACUUM INTO: 현재 DB의 일관된 복사본을 새 파일로 만드는 SQLite 명령.
  • TSan(ThreadSanitizer): 실행 중 데이터 경쟁을 찾아내는 컴파일러 도구.

6. 이해도 질문

Q1. init에서 "파일이 원래 있었는지"를 CREATE TABLE 전에 확인하는 이유는?

정답: sqlite3_open은 파일이 없으면 만들어 버린다. 그 뒤엔 새 DB와 옛 DB를 구분할 수 없어, 새 DB도 백업하거나(불필요) 옛 DB를 새 DB로 오해할 수 있다. 사용자의 실제 데이터가 있는 경우만 백업한다.

Q2. pruneOldBackups에서 방금 만든 백업을 후보에서 빼지 않으면 어떤 상황에서 깨지나?

정답: 서버 시계가 뒤로 가서 기존 백업들의 시각이 방금 것보다 클 때. 시각순 정렬에서 방금 백업이 가장 오래된 것이 되어 만들자마자 삭제된다. 마이그레이션 실패 시 돌아갈 곳이 없어진다.

Q3. 헬스체크 스레드가 updateEnergyStat를 쓰는 중에 HTTP 스레드가 loadAllDevices를 부르면 어떻게 되나? 그리고 updateEnergyStat 안에서 insertEnergyLog(공개, 락 잡음)를 부르면?

정답: 앞은 같은 뮤텍스를 쓰므로 한쪽이 끝날 때까지 다른 쪽이 기다린다(데이터는 안전). 뒤는 같은 스레드가 이미 잡은 락을 또 잡으려 해서 자기 교착으로 멈춘다. 안에서 불러야 한다면 insertEnergyLogLocked 같은 내부 함수를 만들어 써야 한다.

원본은 건드리지 말고 새 브랜치(git switch -c practice-db)나 learning/exercise-db/에 사본을 만들어 하세요.

실습 1 (빈칸 구현): 마이그레이션 트랜잭션 흐름

목표: 한 문자열 대신 단계별로 BEGIN / COMMIT / ROLLBACK을 직접 다룬다. 고칠 파일: 사본 migrateToV1Locked. 완료 기준: FailedMigrationRollsBackAndReturnsFalse와 MidMigrationFailureRollsBackEarlierAlter가 통과한다.

bool DatabaseManager::migrateToV1Locked() {
    // (1) 트랜잭션 시작: ______
    // (2) 아래 문장들을 차례로 실행. 하나라도 실패하면 어떻게 할까?
    const char* steps[] = {
        "ALTER TABLE devices ADD COLUMN ip TEXT;",
        "ALTER TABLE devices ADD COLUMN deleted_at TEXT;",
        "CREATE INDEX IF NOT EXISTS idx_history_device_time ON state_history_logs(device_id, timestamp);",
        "UPDATE devices SET ip = substr(device_id, 5) WHERE protocol_type = 1 AND device_id LIKE 'ARD_%';",
        "PRAGMA user_version = 1;",
    };
    // (3) 모두 성공: ______   실패: ______ 후 false
}
힌트

이미 만들어 둔 execLocked(sql, 실패로그접두어)가 성공이면 true를 돌려준다. 실패 시에는 ROLLBACK을 보낸 뒤 return false. user_version은 왜 마지막인가?

정답 
if (!execLocked("BEGIN IMMEDIATE;", "[DB] 마이그레이션 시작 실패: ")) return false;
for (const char* sql : steps) {
    if (!execLocked(sql, "[DB] 마이그레이션 실패: ")) {
        sqlite3_exec(db_, "ROLLBACK;", nullptr, nullptr, nullptr);
        return false;
    }
}
if (!execLocked("COMMIT;", "[DB] 마이그레이션 커밋 실패: ")) {
    sqlite3_exec(db_, "ROLLBACK;", nullptr, nullptr, nullptr);
    return false;
}
return true;

원본은 문장들을 하나의 문자열로 sqlite3_exec에 넘긴다. 같은 결과이고 단계별 로그를 남기기 쉬운 것이 사본 방식의 장점이다.

실습 2 (응용 과제): v2 마이그레이션 — state_history_logs에 열 추가

목표: state_history_logs에 source TEXT 열(기록 출처)을 v2로 추가한다. 고칠 곳: 사본의 kSchemaVersion, 새 migrateToV2Locked, init의 버전 분기, 테스트 파일. 완료 기준: v0 → v2, v1 → v2, 이미 v2 세 경우가 모두 통과하고, v2 실패 시 v1로 남는다.

힌트
  • init은 지금 currentVersion < 1만 본다. if (currentVersion < 1) migrateToV1; if (currentVersion < 2) migrateToV2; 순서로 이어 붙인다.
  • 백업은 "업그레이드가 필요할 때 한 번만" 현재 버전 이름(bak-v1)으로 만든다. 단계마다 만들 필요는 없다.
  • 테스트는 v1 픽스처(v1_schema.sql)를 새로 만들고, v2 실패 유도는 source 열을 미리 추가한 DB로 한다.
정답 
// DatabaseManager.cpp
constexpr int kSchemaVersion = 2;

bool DatabaseManager::migrateToV2Locked() {
    // v1과 같은 틀: BEGIN IMMEDIATE → ALTER → user_version = 2 → COMMIT, 실패 시 ROLLBACK
    const char* sql =
        "BEGIN IMMEDIATE;"
        "ALTER TABLE state_history_logs ADD COLUMN source TEXT;"
        "PRAGMA user_version = 2;"
        "COMMIT;";
    ...
}

// init 안
if (currentVersion < kSchemaVersion) {
    if (hadDevicesTable) { /* 백업 */ }
    if (currentVersion < 1 && !migrateToV1Locked()) { closeLocked(); return false; }
    if (currentVersion < 2 && !migrateToV2Locked()) { closeLocked(); return false; }
}

테스트 3종: (1) v0 픽스처 → user_version=2 이고 source 열 존재 (2) v1 픽스처 → 2, 데이터 유지 (3) source 열이 미리 있는 v1 DB → init이 false, user_version=1. 기존 insertEnergyLog는 열 이름을 지정하므로 수정할 필요가 없다. 이게 롤백 안전의 이유와 같다.
