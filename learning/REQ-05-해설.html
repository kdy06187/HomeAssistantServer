REQ-07 해설

싱글톤을 없애고 생성자 주입으로 바꾼 변경 (3단계 4a, 학습 강도: 균형). 4b가 끝나면 아래에 "4b" 절을 덧붙인다.

REQ-05 해설

DIY 기기 TCP 소켓을 객체(TcpConnection)로 감싸고, 수락·연결 맵을 TcpServer로 분리한 변경 (3단계 7a, 학습 강도: 균형).

1. 한눈에 보기

  • 무엇: fd를 int로 맵에 넣고 여기저기서 close하던 구조를 "연결 객체 + shared_ptr"로 바꿨다. 응답은 줄 단위로 끝까지 읽고, 같은 기기 요청은 한 쌍씩 처리한다.
  • 왜: 512바이트 1회 수신, 재접속 때 fd 누수, "ALL" 순회 중 무락, 락 쥔 채 송신, 끊긴 소켓에 쓰면 SIGPIPE로 서버 종료 위험.
  • 그대로인 것: 기기가 받는 문자열(바이트 단위 테스트), 기기 ID ARD_<IP>, REST 응답, DB.

3-2. 정지가 실제로 되게

running_ = false;

예전 stopServer는 플래그만 바꿔, 다음 접속이 올 때까지 accept에서 깨어나지 못했다(join이 영원히 대기).

3-3. 이전 동작과 맞춘 세부 규칙

  • 줄바꿈 없이 끝나도 유효 JSON이면 인정 — 예전 getline은 마지막 조각도 해석했다.
  • 해석 불가 응답만 오면 실패지만 연결은 유지 — 예전에도 그 경우는 소켓을 지우지 않았다.
  • 요청 직전 남은 입력은 버림 — 늦게 온 이전 응답을 이번 답으로 오인하지 않게(새 규칙, 로그 남김).

3-4. 테스트에서 배운 것: TIME_WAIT

가짜 기기 소켓이 먼저 닫히면 그쪽 포트가 약 60초 TIME_WAIT로 묶인다. 테스트 수백 번이면 수천 개가 쌓여, 다른 테스트가 "빈 포트"로 고른 번호가 0.0.0.0 바인드에서 충돌했다. 가짜 기기에 SO_LINGER{1,0}(RST로 종료)을 줘서 해결했다. 실제 서버 코드는 바꾸지 않았다.

4. 용어 풀이

용어뜻

줄 프레이밍TCP는 바이트 흐름이라 "메시지 경계"가 없다. 줄바꿈을 경계로 삼아 조각을 모아 한 메시지로 만든다.

SIGPIPE끊긴 소켓에 쓰면 기본 동작이 프로세스 종료인 신호. MSG_NOSIGNAL로 막는다.

5. 이해도 질문

Q1. TcpConnection::shutdown() 안에서 close(fd_)까지 하면 어떤 일이 생길 수 있나?

정답다른 스레드가 같은 객체로 poll/recv 중일 수 있다. 그 사이 번호가 커널로 돌아가고 새 접속이 같은 번호를 받으면, 남은 스레드가 남의 소켓에서 읽거나 쓴다. 그래서 close는 아무도 객체를 쥐지 않을 때(소멸자)만 한다.

Q2. 같은 기기에 동시 요청 두 개가 올 때 ioMutex_가 없으면 왜 응답이 섞이나? 프로토콜에 요청 ID가 있었다면?

정답두 요청이 차례로 나가고 두 응답이 한 버퍼로 들어와, 각 스레드가 어느 응답이 자기 것인지 알 수 없다. 요청 ID가 있으면 응답을 짝지을 수 있어 동시 처리(다중화)가 가능하지만, 펌웨어를 바꿀 수 없어(NFR-04) 한 쌍씩 직렬화했다.

Q3. 33번째 연결은 거부하는데, 이미 있는 기기의 재접속은 왜 받아들이나?

정답재접속은 옛 연결을 교체하므로 연결 수가 늘지 않는다. 막으면 IP가 같은 실제 기기가 다시 붙지 못해 오프라인이 계속된다.

7b. IMessageSender: 마법 문자열 "ALL" 없애기

1. 무엇이 바뀌었나

-    virtual void SendCommandTo(const std::string& target_id, const std::string& command) = 0;
-    pc_messenger_->SendCommandTo("ALL", payload);+    virtual Status sendTo(const std::string& deviceId, const std::string& jsonLine) = 0;
+    virtual void broadcast(const std::string& jsonLine) = 0;
+    pc_messenger_->broadcast(payload);
  • "ALL"은 기기 ID 자리에 들어간 특별한 값(센티널)이었다. 받는 쪽이 문자열을 비교해 분기해야 했고, 이름이 "ALL"인 기기가 생기면 구분할 수 없다. 의도를 메서드 이름으로 드러내면 그런 분기가 사라진다.
  • sendTo는 Status를 돌려줘 성공·실패를 호출자가 알 수 있다(예전은 void). 지금 호출자는 없지만 2차 스케줄러(지연 명령)가 쓸 자리다.
  • 동작은 그대로: 브로드캐스트는 7a와 같이 연결 ID 사본을 돌며 기기마다 보낸다.

2. 이해도 질문 (7b)

Q4. 인터페이스를 바꿨는데 왜 FakeProtocolDriver·MockMessageSender·테스트까지 고쳐야 했나? 이것이 인터페이스 설계에서 주는 교훈은?

정답가짜·목은 인터페이스를 구현하므로 시그니처가 바뀌면 함께 바뀐다. 인터페이스는 구현체 수만큼 변경 비용이 커지므로, 처음 설계할 때 의도(한 기기 / 전체)를 메서드로 나눠 두는 편이 낫다. 반대로 기기 드라이버(PCDriver)는 인터페이스에만 의존해 TCPDriver 내부(7a 재작성)가 바뀌어도 영향이 없었다.

7c. 리뷰 반영: 읽기 상한 · CLOEXEC

1. 왜 읽기에도 상한이 필요한가

7a는 "한 줄 4KiB"와 "1초 마감"만 있었다. 그런데 두 곳이 기다리지 않고 읽는 반복이었다: 요청 전에 남은 입력 버리기, 유효 줄 뒤 이미 온 줄 더 읽기. 기기가 쉬지 않고 보내면 recv(MSG_DONTWAIT)가 매번 데이터를 돌려줘 반복이 끝나지 않는다 — 마감 시각을 확인하지 않는 반복은 1초 규칙도 소용없다.

위치상한넘으면
요청 전 버리기16KiB · 100ms연결 닫고 실패
유효 줄 뒤 더 읽기16KiB · 요청 마감 시각연결 닫음, 받은 유효 줄로 판단
한 요청의 줄 수64줄연결 닫음
한 줄4KiB연결 닫음

원칙: 외부 입력을 읽는 모든 반복은 "얼마나"와 "언제까지" 둘 다 상한을 둔다. 상한이 없으면 고장 난 기기 하나가 그 요청 스레드(HTTP 스레드 풀의 한 칸)를 계속 붙잡는다. 테스트: 끝없이 보내는 가짜 기기에서도 요청이 곧 실패하고, 다른 기기 요청은 1초 안에 끝난다.

덤: 응답은 JSON 객체만 인정한다. 1이나 null도 유효한 JSON이라 예전엔 "응답"으로 받아들여, 뒤에서 res["state"]를 읽다 형 오류 예외가 날 수 있었다.

2. CLOEXEC가 뭔가

서버는 chip-tool을 fork → exec로 실행한다. 리눅스에서 자식 프로세스는 부모의 열린 fd를 그대로 물려받는다. 그러면:

  • chip-tool이 도는 동안(최대 수 초) 8080 리슨 소켓·기기 소켓이 자식에도 열려 있어, 서버가 close해도 실제 연결이 안 닫힌다(기기가 끊김을 늦게 안다).
  • 서버를 재시작할 때 자식이 남아 있으면 8080 포트가 "사용 중"이 될 수 있다.

SOCK_CLOEXEC(만들 때)·accept4(…, SOCK_CLOEXEC)(받을 때)는 "exec하면 이 fd를 닫아라" 표시를 원자적으로 붙인다. 만든 뒤 fcntl로 따로 붙이면 그 사이에 다른 스레드가 fork할 수 있어 틈이 생긴다.

3. 이해도 질문 (7c)

Q5. 상한(32)에 닿았을 때 끊긴 연결을 정리하는 확인(poll POLLRDHUP)을 맵 락 안에서 하면 무엇이 문제인가?

정답poll은 시스템 호출이라 상태 락 안에서는 금지(L-2)다. 연결 32개를 확인하는 동안 맵 락을 쥐면 그동안 모든 요청이 연결을 찾지 못하고 기다린다. 그래서 맵 사본(shared_ptr)을 떠서 락 밖에서 확인하고, 지울 때는 "아직 같은 객체일 때만"(removeIfSame) 지운다.

Q6. 유효 응답을 받은 뒤 뒤따른 입력이 상한을 넘으면, 왜 실패 대신 "받은 응답은 쓰고 연결만 닫는" 쪽을 택했나?

정답요청의 답은 이미 왔다(제어가 실제로 실행됐을 수 있다). 그 뒤의 쓰레기 때문에 실패로 답하면 앱은 "명령 실패"로 보지만 기기는 이미 바뀐 상태가 된다. 연결은 닫아 오동작하는 기기가 다음 요청을 오염시키지 않게 한다.
