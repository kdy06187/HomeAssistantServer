3-1. 10a — 오류를 한 곳의 표로 결정 (ErrorMapping::describe)

이전 방식(현재 라우트에 남아 있는 방식)과 10a의 방식을 비교한다.

// before: 본문 문자열에 "error"가 들었는지 검사해서 상태를 정한다 (HTTPServer.cpp 178행)
if (jsonResponse.find("\"error\"") != std::string::npos) {
    res.status = 400;
}
// after: ErrorCode -> (HTTP 상태, 코드 문자열, 고정 문구) 를 switch 한 곳에서만 결정 (ErrorMapping.cpp)
case ErrorCode::DeviceNotFound:
    return {404, "DEVICE_NOT_FOUND", "등록되지 않은 기기입니다."};
case ErrorCode::CommissionBusy:
    return {409, "COMMISSION_BUSY", "다른 기기 등록이 진행 중입니다."};
무엇을
오류 종류(ErrorCode)를 넣으면 상태·코드·문구가 한 번에 나온다. buildErrorBody는 {"error":{"code","message"}}만 만든다.
왜
문자열 검사는 정상 응답에 우연히 "error"라는 글자가 들어가면(예: 기기 이름) 400으로 오판하고, 모든 오류가 400이 되어 404·409·502를 구분 못 한다. 표는 오류를 타입으로 다뤄 컴파일러가 누락을 잡아 주고, 시험 한 개(EveryRowMatchesTheDesignTable)가 설계 표와 1:1로 대조한다. 문구도 고정이라 SQL·경로·e.what() 같은 내부 정보가 응답에 새지 않는다(S-11).
빼면
상태 결정이 핸들러마다 흩어지고, 문구가 제각각이 되며, 내부 오류 문장이 그대로 노출될 수 있다.

덧붙임: ErrorCode::None은 오류가 아니므로 호출되면 안 되지만, 안전하게 500으로 처리한다(시험 NoneFallsBackToInternalError). 등록 작업(E8)의 COMMISSION_FAILED 등은 HTTP는 200이고 오류 정보는 본문 안에 들어간다.

3-2. 10b — 타임아웃은 "소켓 대기"만 센다 + 포트·풀 설정 (applyConnectionLimits)

server.set_read_timeout(5);       // 소켓에서 바이트가 안 올 때 기다리는 시간
server.set_write_timeout(5);      // 소켓에 쓸 수 없을 때 기다리는 시간
server.set_keep_alive_timeout(5); // 응답 뒤 다음 요청을 기다리는 시간
server.set_keep_alive_max_count(20);
server.new_task_queue = [] { return new httplib::ThreadPool(8); };   // 풀 크기 고정
server.set_socket_options([](socket_t sock) {
    httplib::set_socket_opt(sock, SOL_SOCKET, SO_REUSEADDR, 1);       // SO_REUSEPORT는 켜지 않는다
});
무엇을
느린 연결이 작업 스레드를 오래 붙잡지 못하게 상한을 건다. 풀은 8개로 고정하고, 소켓 옵션은 SO_REUSEADDR만 켠다.
왜
스레드가 8개뿐이라 "헤더 한 줄만 보내고 멈추는" 연결 8개면 서버가 멎는다(느린 연결 공격). 기본 풀은 요청이 몰리면 스레드를 늘려서 메모리를 먹는다. 기본 소켓 옵션은 SO_REUSEPORT라 같은 포트에 두 프로세스가 동시에 붙어 버린다.
빼면
상한이 없으면 느린 연결 몇 개로 서비스 거부가 되고, 스레드가 무한히 늘 수 있으며, 운영 8000에 실수로 서버를 두 번 띄워도 조용히 둘 다 떠서 요청이 반반 갈린다.

왜 타임아웃이 느린 핸들러를 건드리지 않나 (T-4 시험)

읽기·쓰기 타임아웃은 "소켓이 읽기·쓰기 가능해질 때까지 기다린 시간"만 잰다. 요청을 다 받은 뒤 핸들러가 실행되는 동안에는 소켓을 기다리는 것이 아니므로 5초 시계가 돌지 않는다. 시험 HandlerSlowerThanSocketTimeoutStillAnswersAndKeepsConnection은 핸들러를 일부러 7초 재워도(타임아웃 5초보다 길다) 200 응답이 오고 같은 연결로 두 번째 요청도 되는 것을 확인한다. 그래서 수동 새로고침처럼 기기에 직접 묻는 느린 요청이 안전하다.

관찰(느린 연결): 헤더를 일부만 보내고 멈추는 연결은 시험 StalledPartialHeaderConnection...에서 약 5초에 400과 Connection: close 응답을 받고, 소켓이 실제로 닫히는 건 그 뒤 keep-alive 대기 5초까지 끝난 약 10초 시점이다. 즉 "5초에 끊긴다"가 아니라 "5초에 응답, 10초에 닫힘"이다(시험은 4~7초 사이 첫 바이트, 12초 이내 종료를 확인). 또 SevenStalledConnectionsDoNotBlockANormalRequest는 풀 8개 중 7개가 묶여도 남은 1개로 정상 요청이 2초 안에 처리됨을 보인다.

SO_REUSEADDR vs SO_REUSEPORT

SO_REUSEADDRSO_REUSEPORT
하는 일종료 직후 남는 TIME_WAIT 상태 때문에 같은 포트가 "사용 중"으로 보이는 것을 피한다. 재시작이 바로 된다.같은 주소·포트에 여러 소켓(여러 프로세스)이 동시에 listen하게 허용하고 커널이 연결을 나눠 준다.
같은 포트 두 번째 서버listen 중인 소켓이 있으면 bind 실패(중복 실행이 막힘)둘 다 성공 → 요청이 두 서버로 갈림
위험거의 없음(재시작에 필요)유령·옛 프로세스가 같은 포트에서 계속 답하거나, 다른 프로그램이 포트를 가로챌 수 있음(같은 사용자 계정이면)

시험: SecondServerOnSamePortFailsToBecomeReady(두 번째 서버는 준비 안 됨), SamePortCanBeReusedRightAfterStop(중지 직후 같은 포트로 재시작 성공).

3-3. 10c — 생명주기 락 (start/stop)

// before(개념): 락 없이 서버 스레드를 만들고 끝낸다
//  - start 두 번 동시 호출 -> std::thread 두 개가 대입되어 std::terminate
//  - stop 두 번 동시 호출 -> 같은 스레드를 두 번 join
//  - stop이 bind 전에 불리면 서버가 멈추라는 신호를 놓침 -> join이 영원히 대기
bool HTTPServer::start(){
    std::lock_guard<std::mutex> lock(mLifecycleMutex);
    if (mServerThread.joinable()) {
        if (!mHasRunFinished) return false;   // 이미 실행 중
        mServerThread.join();                 // 바인딩 실패로 끝난 이전 실행 정리 후 재시작
    }
    mHasRunFinished = false;
    buildServer();                            // start마다 새 서버 객체
    mServerThread = std::thread(&HTTPServer::run, this);
    return true;
}
void HTTPServer::stop(){
    std::lock_guard<std::mutex> lock(mLifecycleMutex);
    if (!mServerThread.joinable()) return;    // 시작한 적 없거나 이미 멈춤
    while (!mHasRunFinished) { mServer->stop(); sleep 5ms; }  // run이 끝날 때까지 반복
    mServerThread.join();
}
무엇을
start/stop을 락 하나로 직렬화하고, "스레드가 살아 있나(joinable)"와 "run이 끝났나(mHasRunFinished)" 두 신호로 상태를 판단한다.
왜
G6(시작·종료 중복 호출 시 std::thread 예외·종료)와 T6(stop이 bind 전에 불려 무시되는 경합)을 막는다. mServer->stop()은 listen 전에 부르면 아무 효과가 없어서, run이 끝날 때까지 5ms마다 반복 호출한다. 시험: ConcurrentStartsLetExactlyOneWin, StopRightAfterStartRepeatedlyNeverHangs.
빼면
드물게 터지는 크래시나 영원히 안 끝나는 종료. 시험으로 재현해야만 보이는 "경합 조건" 버그다.

락 안에서 join까지 하므로 설계 주석대로 다른 락과 겹쳐 잡지 않는다(교착 방지). TcpServer(8080)도 같은 패턴을 적용했다(lifecycleMutex_, 스레드 생성 실패 시 running_ 되돌리기). 실패 로그는 errno를 close 호출 전에 cause로 저장한다(close가 errno를 덮어쓰기 때문). httplib는 실패 원인을 안 알려 주므로 diagnoseBindErrno가 같은 조건으로 소켓을 한 번 더 bind해 본다.

상황결과시험
1분 안에 11번째 실패경고 true(1회), 12·13번째는 falseWarnsOnceWhenMoreThanTenFailuresInAMinute

짚어 볼 점(비판적 시각): 모니터는 경고만 하고 차단은 안 한다. 8개 스레드가 동시에 recordFailure를 부르므로 mutex로 보호하지만, 락 안에서는 메모리 작업만 한다(느린 I/O를 락 안에 넣지 않는 원칙). 또 요청자 주소는 소켓 주소 그대로라(clientAddressOf) 프록시 뒤에서는 모두 같은 주소로 보일 수 있다(설계상 XFF는 보류).

4. 용어 풀이

  • keep-alive: 응답 뒤에도 TCP 연결을 닫지 않고 다음 요청을 받는 방식. 연결 비용을 아끼지만 놀고 있는 연결이 스레드를 잡을 수 있어 대기 시간·횟수 상한이 필요하다.
  • 작업 풀(ThreadPool): 미리 만든 스레드 N개가 요청을 나눠 처리하는 구조. 크기를 고정하면 자원 사용에 상한이 생긴다.
  • TIME_WAIT: 닫힌 TCP 연결의 흔적이 잠깐 남는 상태. SO_REUSEADDR 없이는 그 사이 같은 포트로 재시작이 막힐 수 있다.
  • 경합 조건(race condition): 스레드 실행 순서에 따라 결과가 달라지는 버그. 락과 상태 변수로 순서를 강제한다.
  • 의존성 주입: 객체가 쓸 부품(인증, 시계)을 안에서 만들지 않고 밖에서 넣어 주는 설계. 시험에서 가짜로 바꾸기 쉽다.
  • 상수 시간 비교(CRYPTO_memcmp): 비교가 어디서 틀렸는지에 따라 걸리는 시간이 달라지지 않게 해, 시간 차이로 토큰을 추측하는 공격을 막는다.

5. 이해도 질문

Q1. 읽기 타임아웃이 5초인데 핸들러가 7초 걸려도 응답이 정상으로 가는 이유는? 만약 핸들러 전체에 5초 제한을 걸고 싶다면 이 설정으로 될까?
정답읽기·쓰기 타임아웃은 소켓에서 바이트를 기다리는 시간만 센다. 요청을 다 받은 뒤 핸들러가 도는 동안은 소켓 대기가 아니므로 시계가 안 돈다. 핸들러 전체 제한은 이 설정으로 안 되고, 핸들러 안에서 별도 제한(예: 기기 호출 타임아웃)을 걸어야 한다.
Q2. 풀이 8개인데 느린 연결 8개가 헤더만 보내고 멈추면 어떻게 되나? 무엇이 이 상태를 풀어 주고, 얼마나 걸리나?
정답모든 작업 스레드가 묶여 새 요청이 대기한다. 읽기 타임아웃 5초에 연결이 400으로 응답되고, keep-alive 대기까지 합쳐 약 10초에 소켓이 닫혀 스레드가 풀린다. 그동안은 서비스가 막히므로 이 설정은 "완전한 방어"가 아니라 "피해 시간 상한"이다(그래서 풀 크기와 타임아웃을 함께 정한다).
Q3. stop()이 mServer->stop()을 한 번만 부르지 않고 mHasRunFinished가 될 때까지 반복하는 이유는? 락(mLifecycleMutex)을 빼면 어떤 호출 조합이 위험한가?
정답run()이 bind·listen에 들어가기 전에 stop이 불리면 httplib의 stop이 무시되어 신호를 놓치고 join이 영원히 대기한다(T6). 락이 없으면 start 동시 2회(스레드 대입 중복 → 비정상 종료), stop 동시 2회(같은 스레드 이중 join), start와 stop이 겹치는 경우가 위험하다(G6).
Q4. AuthFailureMonitor가 "10회까지는 false, 11번째 true, 이후 false"인데 mWarned = false로 되돌리는 코드는 어디서, 왜 필요한가? 이 줄을 빼면 어떤 시험이 깨지나?
정답실패 수가 10 이하로 내려간 호출(size() <= kThreshold 분기)에서 되돌린다. 안 그러면 한 번 경고한 뒤 영원히 경고가 없어서 "조용해진 뒤 다시 공격"을 알릴 수 없다. WarnsAgainAfterCalmingDown 시험이 깨진다.

실습 B (응용): "같은 포트 두 인스턴스" 시험을 직접 설계하기

목표: 10b의 포트 옵션 결정을 시험으로 증명하는 법을 익힌다.
할 일: 새 시험 파일 사본(learning/exercise-port/)에 아래 세 가지를 설계해서 써 본다(원본 HttpServerLimitsTest.cpp는 보기만 한다).
완료 기준: (1) 서버 A 실행 중 같은 포트에 서버 B start() 후 waitUntilReady가 false (2) A stop() 직후 B가 같은 포트에서 ready=true (3) 두 서버를 한 번 더 시도해도 매번 같은 결과(반복성 확인).
실행: build-dev에서 해당 시험만 필터로 실행한다. 포트는 findFreePort()로 얻고 8000·8080은 쓰지 않는다.

힌트원본 SecondServerOnSamePortFailsToBecomeReady를 읽어 보면 서버 두 개를 같은 port로 만들고 두 번째의 start()/waitUntilReady 결과를 본다. 두 번째 start() 자체는 true일 수 있다(스레드는 만들어지고 bind가 실패하므로). 실패는 waitUntilReady가 알려 준다는 점이 포인트다.
정답 스케치
port = findFreePort();
HTTPServer a(manager, kToken, port), b(manager, kToken, port);
ASSERT_TRUE(a.start());  ASSERT_TRUE(a.waitUntilReady(3s));
b.start();
EXPECT_FALSE(b.waitUntilReady(1s));   // SO_REUSEADDR만이라 bind 실패
a.stop();
ASSERT_TRUE(b.start());               // 바인딩 실패로 끝난 b를 다음 start가 정리 후 재시작
EXPECT_TRUE(b.waitUntilReady(3s));    // 중지 직후 재사용 가능(SO_REUSEADDR)
b.stop();
