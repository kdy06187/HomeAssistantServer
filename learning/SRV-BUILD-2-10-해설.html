왜
문자열 검사는 정상 응답에 우연히 "error"라는 글자가 들어가면(예: 기기 이름) 400으로 오판하고, 모든 오류가 400이 되어 404·409·502를 구분 못 한다. 표는 오류를 타입으로 다뤄 컴파일러가 누락을 잡아 주고, 시험 한 개(EveryRowMatchesTheDesignTable)가 설계 표와 1:1로 대조한다. 문구도 고정이라 SQL·경로·e.what() 같은 내부 정보가 응답에 새지 않는다(S-11).
빼면
상태 결정이 핸들러마다 흩어지고, 문구가 제각각이 되며, 내부 오류 문장이 그대로 노출될 수 있다.

덧붙임: ErrorCode::None은 오류가 아니므로 호출되면 안 되지만, 안전하게 500으로 처리한다(시험 NoneFallsBackToInternalError). 등록 작업(E8)의 COMMISSION_FAILED 등은 HTTP는 200이고 오류 정보는 본문 안에 들어간다.

3-2. 10b — 타임아웃은 "소켓 대기"만 센다 + 포트·풀 설정 (applyConnectionLimits)

server.set_read_timeout(5);       // 소켓에서 바이트가 안 올 때 기다리는 시간

무엇을
느린 연결이 작업 스레드를 오래 붙잡지 못하게 상한을 건다. 풀은 8개로 고정하고, 소켓 옵션은 SO_REUSEADDR만 켠다.
왜
스레드가 8개뿐이라 "헤더 한 줄만 보내고 멈추는" 연결 8개면 서버가 멎는다(느린 연결 공격). 기본 풀은 요청이 몰리면 스레드를 늘려서 메모리를 먹는다. 기본 소켓 옵션은 SO_REUSEPORT라 같은 포트에 두 프로세스가 동시에 붙어 버린다.
빼면
상한이 없으면 느린 연결 몇 개로 서비스 거부가 되고, 스레드가 무한히 늘 수 있으며, 운영 8000에 실수로 서버를 두 번 띄워도 조용히 둘 다 떠서 요청이 반반 갈린다.

왜 타임아웃이 느린 핸들러를 건드리지 않나 (T-4 시험)

읽기·쓰기 타임아웃은 "소켓이 읽기·쓰기 가능해질 때까지 기다린 시간"만 잰다. 요청을 다 받은 뒤 핸들러가 실행되는 동안에는 소켓을 기다리는 것이 아니므로 5초 시계가 돌지 않는다. 시험 HandlerSlowerThanSocketTimeoutStillAnswersAndKeepsConnection은 핸들러를 일부러 7초 재워도(타임아웃 5초보다 길다) 200 응답이 오고 같은 연결로 두 번째 요청도 되는 것을 확인한다. 그래서 수동 새로고침처럼 기기에 직접 묻는 느린 요청이 안전하다.

관찰(느린 연결): 헤더를 일부만 보내고 멈추는 연결은 시험 StalledPartialHeaderConnection...에서 약 5초에 400과 Connection: close 응답을 받고, 소켓이 실제로 닫히는 건 그 뒤 keep-alive 대기 5초까지 끝난 약 10초 시점이다. 즉 "5초에 끊긴다"가 아니라 "5초에 응답, 10초에 닫힘"이다(시험은 4~7초 사이 첫 바이트, 12초 이내 종료를 확인). 또 SevenStalledConnectionsDoNotBlockANormalRequest는 풀 8개 중 7개가 묶여도 남은 1개로 정상 요청이 2초 안에 처리됨을 보인다.

3-3. 10c — 생명주기 락 (start/stop)

// before(개념): 락 없이 서버 스레드를 만들고 끝낸다
//  - start 두 번 동시 호출 -> std::thread 두 개가 대입되어 std::terminate
//  - stop 두 번 동시 호출 -> 같은 스레드를 두 번 join
//  - stop이 bind 전에 불리면 서버가 멈추라는 신호를 놓침 -> join이 영원히 대기
bool HTTPServer::start(){
    std::lock_guard<std::mutex> lock(mLifecycleMutex);
    if (mServerThread.joinable()) {
        if (!mHasRunFinished) return false;   // 이미 실행 중
        mServerThread.join();                 // 바인딩 실패로 끝난 이전 실행 정리 후 재시작
    }
    mHasRunFinished = false;
    buildServer();                            // start마다 새 서버 객체
    mServerThread = std::thread(&HTTPServer::run, this);
    return true;
}
void HTTPServer::stop(){
    std::lock_guard<std::mutex> lock(mLifecycleMutex);
    if (!mServerThread.joinable()) return;    // 시작한 적 없거나 이미 멈춤
    while (!mHasRunFinished) { mServer->stop(); sleep 5ms; }  // run이 끝날 때까지 반복
    mServerThread.join();
}
무엇을
start/stop을 락 하나로 직렬화하고, "스레드가 살아 있나(joinable)"와 "run이 끝났나(mHasRunFinished)" 두 신호로 상태를 판단한다.
왜
G6(시작·종료 중복 호출 시 std::thread 예외·종료)와 T6(stop이 bind 전에 불려 무시되는 경합)을 막는다. mServer->stop()은 listen 전에 부르면 아무 효과가 없어서, run이 끝날 때까지 5ms마다 반복 호출한다. 시험: ConcurrentStartsLetExactlyOneWin, StopRightAfterStartRepeatedlyNeverHangs.
빼면
드물게 터지는 크래시나 영원히 안 끝나는 종료. 시험으로 재현해야만 보이는 "경합 조건" 버그다.
10e(H15) 이후 사실(8-7): start()가 bind_to_port를 직접 호출해 바인딩 결과를 바로 반환하고, stop()은 server.stop()+join 한 번이다(위 반복 루프는 없어짐).
10h에서 바뀐 점(7절): 위 코드는 10c 시점이다. 지금은 mServer·mHasRunFinished 대신 shared_ptr<RunState>를 쓰고(H2), 이미 실행 중이거나 포트가 범위 밖이면 false, 반환값은 mServerThread.joinable()이다. TcpServer::start도 재호출 시 true가 아니라 false를 돌려준다(H12). 시작 로그는 start()가 아니라 run()의 bind 성공 직후에 찍힌다(H9).

락 안에서 join까지 하므로 설계 주석대로 다른 락과 겹쳐 잡지 않는다(교착 방지). TcpServer(8080)도 같은 패턴을 적용했다(lifecycleMutex_, 스레드 생성 실패 시 running_ 되돌리기). 실패 로그는 errno를 close 호출 전에 cause로 저장한다(close가 errno를 덮어쓰기 때문). httplib는 실패 원인을 안 알려 주므로 diagnoseBindErrno가 같은 조건으로 소켓을 한 번 더 bind해 본다.

4. 용어 풀이

  • keep-alive: 응답 뒤에도 TCP 연결을 닫지 않고 다음 요청을 받는 방식. 연결 비용을 아끼지만 놀고 있는 연결이 스레드를 잡을 수 있어 대기 시간·횟수 상한이 필요하다.
  • 작업 풀(ThreadPool): 미리 만든 스레드 N개가 요청을 나눠 처리하는 구조. 크기를 고정하면 자원 사용에 상한이 생긴다.
  • TIME_WAIT: 닫힌 TCP 연결의 흔적이 잠깐 남는 상태. SO_REUSEADDR 없이는 그 사이 같은 포트로 재시작이 막힐 수 있다.
  • 경합 조건(race condition): 스레드 실행 순서에 따라 결과가 달라지는 버그. 락과 상태 변수로 순서를 강제한다.
  • 의존성 주입: 객체가 쓸 부품(인증, 시계)을 안에서 만들지 않고 밖에서 넣어 주는 설계. 시험에서 가짜로 바꾸기 쉽다.
  • 상수 시간 비교(CRYPTO_memcmp): 비교가 어디서 틀렸는지에 따라 걸리는 시간이 달라지지 않게 해, 시간 차이로 토큰을 추측하는 공격을 막는다.

Q3. stop()이 서버의 stop()(10h 이후 state->server.stop())을 10c 시점에는 mHasRunFinished가 될 때까지 반복했는데, 지금은 왜 한 번이면 되나(H15)? 락(mLifecycleMutex)을 빼면 어떤 호출 조합이 위험한가?

Q4. AuthFailureMonitor가 "10회까지는 false, 11번째 true, 이후 false"인데 mWarned = false로 되돌리는 코드는 어디서, 왜 필요한가? 이 줄을 빼면 어떤 시험이 깨지나?

빼면

"HTTP 서버 시작 ..." 로그를 start()가 아니라 bind가 성공한 뒤에 찍는다(10h 때는 run(), 10e 이후로는 start() 안, 스레드 생성 직전). 이제 바인딩이 실패하면 "시작" 로그가 아예 안 나오고(전에는 start()에서 무조건 찍혀 거짓말이었다), 로그는 항상 waitUntilReady가 true가 되기보다 앞선다. 또 logBindFailure는 "바인딩/리슨 실패"로 문구를 고쳐, 진단 bind가 성공해도 원인이 listen 단계일 수 있음을 밝힌다.

왜: 규약이 다르면 호출하는 쪽이 서버마다 다른 의미를 외워야 하고, "동시에 여러 번 start해도 한 번만 시작" 같은 성질을 시험하기도 어렵다. false를 "이미 실행 중이거나 시작 실패"로 뭉뚱그려도 main은 start를 한 번만 부르므로 false는 곧 실패로 읽으면 된다. 같은 변경에서 포트 범위 검사(HTTP 1~65535, TCP 0~65535, 0은 시험용 임의 포트)를 넣고, TcpServer::boundPort_를 atomic으로 바꿔 stop 후 0이 되게 했다(다른 스레드가 읽어도 안전). HTTPServer의 start()는 10e 이후 바인딩 성공·스레드 생성 성공일 때만 true를 돌려준다. 이 페이지 3-3의 코드 조각은 10c 시점이라 이 반환값 규칙 이전의 모습이다.

Q1. isValidIpv4Address("192.168.0.1\0x")가 NUL 검사 없이 true를 돌려주는 이유와, 이것이 "검증과 사용의 길이가 다르다"는 문제의 한 예인 이유를 설명하라. isdigit을 직접 비교로 바꾼 이유도 한 줄로.
정답inet_pton은 c_str()(NUL 종료 문자열)을 받아 첫 NUL에서 읽기를 멈추므로 "192.168.0.1"만 검사한다. 하지만 std::string은 13바이트 전체를 가진다. 이후 코드가 전체를 쓰면 검사하지 않은 바이트가 흘러든다. 검사 대상과 사용 대상이 달라진 것이 원인이고, 해결은 NUL 거부 또는 양쪽이 같은 길이를 보게 하는 것이다. isdigit은 로케일에 따라 결과가 달라질 수 있고 unsigned char 변환을 빼먹으면 정의되지 않은 동작이라, 입력 검증은 ASCII 범위를 직접 비교해 환경과 무관하게 같은 결과를 내게 했다.
Q2. waitUntilReady가 대기 루프 전체를 mRunStateMutex 안에서 돌리지 않고 포인터만 복사하는 이유는? 복사한 shared_ptr이 없다면 어떤 일이 생길 수 있나?
정답대기는 최대 수 초이므로 락 안에서 하면 그동안 start가 같은 락을 못 잡아 지연된다(락은 짧게, 대기는 락 밖). 대신 포인터를 복사해 쥐면, 그 사이 start가 새 RunState로 교체해도 내가 쥔 이전 RunState는 내가 놓을 때까지 해제되지 않는다. 복사본이 없으면 start가 서버 객체를 바꾸거나 소멸시키는 순간 대기 중인 스레드가 해제된 객체의 is_running()을 부를 수 있다(드물게 터지는 크래시).

8-5. E2 — controlResponseFor: 결과를 200/202/409/502로

ApiResponse controlResponseFor(const CommandResult& result, const std::string& deviceId, const std::string& command) {
    switch (result.outcome) {
        case CommandOutcome::Succeeded:  // 200 {deviceId, state}
            return ApiResponse::ok(json{{"deviceId", deviceId}, {"state", result.state}});
        case CommandOutcome::Accepted:   // 202: 지연 수락, state는 "바뀌기 전" 상태
            return ApiResponse::ok(json{{"deviceId", deviceId}, {"state", result.state},
                       {"pendingCommand", command}, {"delaySeconds", result.delaySeconds}}, 202);
        case CommandOutcome::Failed: break;
    }
    return ApiResponse::error(result.error.code);   // 409 COMMAND_BLOCKED / 502 DEVICE_UNREACHABLE / 404 ...
}
무엇을
DeviceManager가 돌려준 CommandResult(성공/수락/실패)를 상태 코드로 번역한다. 실패는 따로 분기하지 않고 8-4의 표에 맡긴다.
왜
"기기가 곧 바꿀 예정"(202)과 "이미 바꿈"(200)을 앱이 구분해야 화면에 대기 표시를 할 수 있다. 번역을 함수 하나로 모으면 시험이 CommandResult만 만들어 넣어 보면 된다. switch에 default가 없어 새 outcome이 생기면 컴파일러가 알려 준다.
빼면

8-6. E3·E4는 왜 v1.0 본문을 남겼나, 그리고 10g

  • E3(등록)·E4(삭제): 입력 오류(JSON·필드·검증)만 400 오류 봉투로 바꿨고, 성공·실패 본문은 v1.0 그대로다. 이유: DeviceManager::startCommissioning·removeDevice가 bool만 돌려줘서 "왜 실패했나(이미 등록됨 / 기기 응답 없음 / DB 오류)"를 핸들러가 모른다. 모르는 채로 상태 코드를 지어내면 거짓 응답이 된다. 반환 타입을 Result로 바꾸는 일은 12a(삭제)·13번(비동기 등록)에서 한다. "모르는 것은 추측하지 않는다"가 이유다.
  • 10g parseBindAddress: 환경 변수 값(nullptr·빈 문자열 = 미설정 → 0.0.0.0, 값이 있는데 IPv4가 아니면 실패)을 해석하는 함수가 RequestValidation에 하나 있고, HAC_HTTP_BIND와 HAC_TCP_BIND가 함께 쓴다. 형식 오류면 main이 서버를 시작하지 않는다(조용히 0.0.0.0으로 열면 의도보다 넓게 노출되므로 "실패가 안전한 쪽"). 시험은 127.0.0.1로 열었을 때 127.0.0.2 접속이 안 되는 것까지 확인한다.
주의 — 점이 들어간 deviceId: 새 라우트는 경로의 deviceId를 isValidDeviceId(영문·숫자·_·-, 64자 이하)로 먼저 검사하고 틀리면 404 NOT_FOUND를 돌려준다. 그런데 TCP 기기 ID는 "ARD_" + 클라이언트 IP(예 ARD_192.168.0.7)라 점(.)이 들어 있어 이 검사에 걸린다. 12b에서 ID 규칙을 정리하기 전까지 TCP 기기의 state·energy 경로는 404가 될 수 있다(알려진 임시 상태).

9-4. 용어 풀이

  • TOCTOU(Time Of Check, Time Of Use): 확인한 시점과 사용하는 시점 사이에 상황이 바뀌는 버그. 해결은 확인과 사용을 한 번에(원자적으로) 하는 것.
  • Result<T>: 성공 값 또는 오류(코드+문구)를 한 객체에 담아 돌려주는 반환형. "모름"과 "실패"를 구분하게 해 준다.
  • 전달(propagate): 아래 계층의 오류를 바꾸지 않고 위로 올려 보내는 것. 반대는 덮어쓰기(wrap/override).
  • detach: 스레드를 떼어 내 독립 실행시키는 일. 누가 언제 끝났는지 추적할 수 없어 객체 수명 문제가 생긴다.
  • use-after-free: 이미 해제한 메모리를 쓰는 오류.

할 일: src/HTTPServer.cpp의 핸들러들에서 getDevice(...) 뒤에 같은 id로 DeviceManager의 다른 함수를 또 부르는 곳을 찾는다(예: 전력·제어·삭제 경로). 코드는 고치지 않고 스케치만 쓴다.
고칠 파일(실제로 한다면): include/DeviceManager.hpp, src/DeviceManager.cpp, src/HTTPServer.cpp, 시험 tests/integration/*. 실제 수정은 새 브랜치나 learning/exercise-toctou/ 사본에서만, 시험은 build-dev ctest -R <이름>만.
완료 기준: (1) 찾은 "확인 → 사용" 위치와 그 사이에 일어날 수 있는 사건을 적었다 (2) 새 함수의 시그니처(반환 Result)와 실패 코드를 정했고, 코드를 만드는 계층과 전달하는 계층을 구분했다 (3) 먼저 실패해야 하는 시험 1개(예: 없는 id 요청이 404)를 적었다 (4) 락 안에서 할 일과 밖에서 할 일을 나눴다.

힌트E5의 before 코드를 그대로 본떠 찾는다. getDevice의 결과 Device 객체를 그 뒤에 쓰지 않고 존재 확인에만 썼다면 후보다. 통신은 락 밖(Q1)이라는 점도 지킨다.
정답 스케치(예) 전력 E6처럼 getDevice 뒤에 매니저 함수를 부르는 핸들러가 있다면: 매니저 함수 맨 앞에서 락을 잡고 devices_.find가 실패하면 failure(DeviceNotFound)를 돌려주고, 핸들러는 if (!r.ok()) return ApiResponse::error(r.error.code); 한 줄로 바꾼다. 선조회를 지우고 DeviceNotFound 매핑은 ErrorMapping 표(404)가 이미 있어 표는 안 바꾼다. 먼저 쓸 시험: 등록되지 않은 id로 해당 경로를 호출해 404 DEVICE_NOT_FOUND가 나오는지(E5의 시험을 본뜸). 이미 readEnergy가 이 형태라면 "이미 적용됨"이라고 쓰고 다른 경로를 찾는다.
