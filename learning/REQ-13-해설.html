REQ-13 해설: 숨김 삭제와 90일 보존 정리

기기를 지우면 곧바로 사라지게 하지 않고 "숨김"으로 표시한 뒤, 90일이 지나면 서버가 알아서 정리하는 변경 (3단계 2차 12a, 학습 강도: 균형).

1. 한눈에 보기

  • 무엇: removeDevice는 DB 행을 지우지 않고 deleted_at에 시각을 적는다(숨김). 같은 기기를 다시 등록하면 deleted_at이 지워져 통계·이력이 그대로 복원된다. 60초 점검 데몬이 하루에 한 번 90일 지난 이력·숨김 기기를 지운다.
  • 왜: 실수로 지운 기기를 되살릴 수 있게 하고, 이력이 무한히 쌓여 DB가 커지는 것을 막는다.
  • 위험 관리: 정리는 "되돌릴 수 없는 삭제"라서 시계가 틀렸을 때 이력이 몽땅 사라지지 않게 안전장치 2종과 한 트랜잭션을 쓴다.

3. 코드 해설

조각 1. removeDevice의 순서와 되돌리기

{ lock;  removedDevice = std::move(it->second);  devices_.erase(it); }   // 1
scheduler_.cancel(id, "삭제");                                           // 2
if (!db_.markDeleted(id, outcome.deletedAtUtc).ok()) {                    // 3
    lock;
    devices_.emplace(id, std::move(removedDevice));   // 실패 → 맵 복구
    return failure(Internal, ...);
}
outcome.unpaired = unpairQuietly(protocolDriver, id);   // 4, 락 밖
무엇 먼저 메모리에서 빼 "삭제 중인 기기"로 접근을 막고, 예약 명령을 취소한 뒤, DB에 숨김 표시를 한다. DB가 실패하면 메모리를 되돌려 "메모리엔 없는데 DB엔 활성"인 어긋남을 막는다. 왜 이 순서 DB를 먼저 하고 메모리를 나중에 하면 그 사이 제어 요청이 삭제될 기기로 가고, 기기 해제(unpair)를 먼저 하면 DB 실패 때 되돌릴 수 없다(실제 기기가 이미 풀림). 그래서 되돌릴 수 있는 일(메모리·DB) 먼저, 되돌릴 수 없는 일(기기 해제)은 맨 마지막이다. 왜 락 밖 unpair 드라이버는 소켓·파일 락을 쥐므로 맵 락을 든 채 부르면 교착 위험이 있다. emplace는 그 사이 같은 ID가 새로 등록됐다면 덮어쓰지 않는다. 빼면 cancel이 없으면 삭제된 기기에 45초 뒤 OFF가 간다.

조각 2. 복원: ON CONFLICT DO UPDATE

INSERT INTO devices (...) VALUES (?, ?, ?, ?, ?)
ON CONFLICT(device_id) DO UPDATE SET display_name = excluded.display_name, ...,
    deleted_at = NULL;
-- 예전: INSERT OR REPLACE  (행을 지우고 다시 넣어 ip 같은 다른 열이 NULL로 되돌아감)
무엇 같은 device_id가 이미 있으면(숨김 기기) 행을 지우지 않고 필요한 열만 갱신하며 숨김을 푼다. 왜 행 자체가 유지되므로 그 기기의 device_energy_stats·state_history_logs(device_id로 연결)가 그대로 이어진다. 빼면(REPLACE로 되돌리면) 다른 열이 초기화되고, 외래키가 있으면 연결된 기록이 사라질 수 있다. 반대로 markDeleted의 deleted_at IS NULL 조건은 이미 숨긴 기기의 숨김 시각이 덮어써져 90일 시계가 리셋되는 것을 막고, 변경 행이 0이면 "없거나 이미 숨김"으로 실패시킨다.

조각 3. purgeExpired: 한 트랜잭션 + 안전장치 2종

BEGIN IMMEDIATE;                               // 시작부터 쓰기 락. 중간에 다른 쓰기가 끼어들지 않음
auto result = purgeLocked(cutoffUtc, maxDeleteRatio);
const bool shouldCommit = result.ok() && !result.value->skipped;
if (shouldCommit && COMMIT) return result;
ROLLBACK;                                      // 건너뜀·실패는 아무것도 지우지 않은 채 되돌림

// purgeLocked 안
if (latest < cutoff)                    → skipped  // 1: 마지막 이력이 90일보다 오래됨 = 지금 시계가 앞서 있음
if (expiredLogs > ratio * totalLogs)    → skipped  // 2: 절반(0.5) 초과를 지우려 함
DELETE 오래된 이력 → 숨김 기기의 통계·이력 → 기기 행 → 고아 행
무엇 삭제 4~5개를 한 트랜잭션으로 묶어 중간 실패 시 전부 취소한다(예: 기기 행만 지워지고 이력은 남는 상태 방지). 왜 안전장치 서버 시계가 갑자기 미래로 가면 "90일 전"이 실제로는 최근이 되어 정상 이력이 몽땅 지워진다. 장치 1은 "가장 최신 이력이 기준일보다 오래됐다"는 모순으로 이를 감지하고, 장치 2는 어떤 이유로든 절반 이상을 지우려 하면 사람이 확인하도록 멈춘다(정확히 50%는 통과, 시험 ExactlyHalfIsNotSkipped). 건너뛴 경우 숨김 기기도 지우지 않는다(SkipDoesNotDeleteHiddenDevicesEither). 순서는 자식(통계·이력) → 부모(기기)로, 반대면 고아가 생긴다. 고아 정리는 기기 행이 이미 없는 통계·이력을 지우며, 시계와 무관하므로 비율 검사에서 뺀다. 빼면 시계 오류 한 번에 이력 전체 손실이 가능하다.

조각 4. shouldRunCleanup을 순수 함수로

constexpr long long kFirstCleanupTick = 60;       // 60초 x 60 = 1시간
constexpr long long kCleanupIntervalTicks = 1440; // 60초 x 1440 = 24시간

bool shouldRunCleanup(long long tickCount) {
    if (tickCount < kFirstCleanupTick) return false;
    return (tickCount - kFirstCleanupTick) % kCleanupIntervalTicks == 0;
}
// run() 안: ++tickCount; if (shouldRunCleanup(tickCount)) deviceManager_.runRetentionCleanup();
무엇 "지금이 정리할 때인가"를 숫자 하나로 판단한다. 왜 뺐나 루프 안에 if (tick % 1440 ...)로 두면 시험이 60초 x 60 = 1시간을 실제로 기다리거나 스레드를 흉내 내야 한다. 순수 함수면 shouldRunCleanup(59/60/61/1500)을 즉시 단언할 수 있다. 시작 직후가 아니라 1시간 뒤부터인 이유는 서버가 재시작을 반복해도 매번 정리하지 않고, 시계가 동기화될 시간을 주기 위해서다. 빼면 경계(60번째, 1500번째)가 틀려도 24시간 이상 지나야 발견된다.

4. 용어 풀이

  • 소프트 삭제(숨김): 행을 지우지 않고 deleted_at만 적어 둔 삭제. 복원이 가능하다.
  • UPSERT(ON CONFLICT DO UPDATE): 없으면 넣고 있으면 갱신. 기존 행을 유지한다.
  • 트랜잭션 / BEGIN IMMEDIATE: 여러 SQL을 "전부 성공 아니면 전부 취소"로 묶는 것. IMMEDIATE는 시작 때 쓰기 락을 먼저 잡는다.
  • ROLLBACK: 트랜잭션 안의 변경을 모두 버린다.
  • 고아 행(orphan): 부모(기기 행)가 없어진 자식 행(통계·이력).
  • 틱(tick): 헬스체크 루프가 한 번 도는 단위(60초).

5. 이해도 질문

Q1. removeDevice에서 unpair를 DB 숨김보다 먼저 하면 어떤 문제가 생기나?

정답DB 숨김이 실패하면 맵과 DB는 되돌릴 수 있지만 실제 기기는 이미 시스템에서 해제돼 있어 되돌릴 수 없다. "되돌릴 수 없는 일은 맨 마지막" 원칙에 어긋난다.

Q2. 서버 시계가 1년 앞당겨진 채로 정리가 돌면 안전장치 1·2는 각각 어떻게 동작하나?

정답기준일(= 지금 − 90일)이 실제로는 최근이 되고, 마지막 이력이 기준일보다 오래되면 장치 1이 건너뛴다. 설령 최신 이력이 기준일 뒤에 있는 어중간한 경우라도, 지울 이력이 전체의 50%를 넘으면 장치 2가 건너뛴다. 둘 다 ROLLBACK이라 아무것도 지워지지 않는다.

Q3. 고아 행 정리를 비율 검사(안전장치 2)에 포함하지 않은 이유는?

정답고아 행은 시계와 상관없이 부모가 이미 없는 쓰레기 데이터라서, 시계 오류로 잘못 지울 위험이 없다. 비율에 넣으면 고아가 많을 때 정당한 정리까지 막힌다.

실습 B (질문 + 작은 구현). 세 번째 안전장치

목표 "지울 기기 수가 전체 기기의 50%를 넘으면 건너뜀"을 추가할 위치와 코드를 설계한다. 고칠 파일(사본) DatabaseManager.cpp purgeLocked. 완료 기준 기기 2개 중 2개가 만료면 skipped=true, 아무것도 지워지지 않음(트랜잭션 ROLLBACK 확인).

힌트이력 비율 검사 바로 뒤, 어떤 DELETE보다 앞에 둔다. countLocked("SELECT COUNT(*) FROM devices;", nullptr)와 ... WHERE deleted_at < ?를 쓰고, skipped와 reason을 채워 Purge::success로 돌려주면 바깥 함수가 ROLLBACK한다.
정답
const auto totalDevices = countLocked("SELECT COUNT(*) FROM devices;", nullptr);
const auto expiredDevices = countLocked("SELECT COUNT(*) FROM devices WHERE deleted_at < ?;", &cutoffUtc);
if (!totalDevices || !expiredDevices) return fail("기기 개수 조회");
if (*totalDevices > 0 && (double)*expiredDevices > maxDeleteRatio * (double)*totalDevices) {
    PurgeResult skipped; skipped.skipped = true; skipped.reason = "지울 기기가 전체의 절반 초과";
    return Purge::success(skipped);   // DELETE보다 앞이어야 한다
}
