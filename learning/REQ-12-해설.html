REQ-12 해설: E7 전력 이력 조회와 집계

기기가 쌓아 둔 전력 기록(누적 mWh)을 "원본 목록" 또는 "일·주·월 사용량 표"로 돌려주는 기능 (3단계 2차 12a, 학습 강도: 균형).

1. 한눈에 보기

  • 무엇: GET /api/devices/{id}/energy/history. period가 없으면 원본 기록(최근 limit건), 있으면 현지 날짜 구간별 사용량(buckets)을 돌려준다.
  • 왜: 기록은 "지금까지 쓴 총량"(누적계)이라 그대로는 "이번 주에 얼마 썼나"를 알 수 없다. 구간 경계의 값 차이를 구해 더해야 한다. 날짜 계산은 한국 시간(+09:00)이어야 하는데 DB는 UTC로 저장한다.
  • 핵심: 달력·구간 분할·합산을 DB·HTTP와 분리한 순수 함수(EnergyAggregation)로 만들어 시험하기 쉽게 했다.

2. 흐름 그림

(a) 요청이 지나가는 길

(b) UTC와 현지 자정 (+09:00 고정)

한국은 서머타임이 없어 +09:00을 상수로 쓴다. 현지 날짜 D의 0시 = UTC로 "D 0시보다 9시간 이른 시각"이다(utcOfLocalMidnight).

3. 코드 해설

조각 1. 한 건 더 읽어 잘렸는지 알기 (queryHistory)

LIMIT limit  → 개수가 limit과 같으면 "딱 맞는지, 더 있는지" 알 수 없다
sqlite3_bind_int64(stmt, index, limit + 1);
page.truncated = page.logs.size() > limit;
if (page.truncated) page.logs.pop_back(); // 최신순이라 맨 뒤 = 가장 오래된 여분
std::reverse(page.logs.begin(), page.logs.end()); // 응답은 오래된 순
무엇 최신순으로 limit+1건을 읽고, limit 초과면 truncated=true로 하고 여분 1건을 버린다. 왜 별도 COUNT 질의 없이 한 번에 "더 있다"를 알 수 있다. 빼면 클라이언트가 목록이 잘렸는지 모르고 일부를 전체로 오해한다. limit<=0을 거부하는 것도 같은 이유다(SQLite는 LIMIT 음수를 "무제한"으로 본다).

조각 2. 날짜 계산: Hinnant의 civil-from-days

int64_t daysFromCivil(const CivilDate& d) {
    const int64_t y = d.month <= 2 ? d.year - 1 : d.year;   // 1~2월은 "전년의 13~14월"로 본다
    const int64_t era = (y >= 0 ? y : y - 399) / 400;        // 400년 = 146097일 주기
    ...
    return era * 146097 + dayOfEra - 719468;                 // 1970-01-01 = 0
}
무엇 (년,월,일) ↔ "1970-01-01부터 며칠째"를 정수 연산만으로 바꾼다(윤년 규칙 4·100·400 포함). 왜 표준 C++에 달력 라이브러리가 없고(localtime 등은 시스템 시간대·스레드 안전 문제), 일 수가 되면 "구간 = 정수 범위"가 되어 나눗셈·비교만으로 주·월을 다룰 수 있다. 빼면 윤년 2월 29일·연말 경계가 어긋난다(시험 KnownDayNumbers, FullLeapYearHas366DayBuckets가 지킨다).

월요일 시작 주: 1970-01-01은 목요일이므로 weekdayFromMonday = (days + 3) % 7(월=0). 구간 끝날은 start + (6 - 요일)인데 조회 범위 끝(lastDay)으로 잘라, 첫·끝 구간은 짧을 수 있다(11-01 일요일 → 첫 주는 하루).

조각 3. 누적계 차이 합산 (aggregate)

std::optional<int64_t> previousTotal;
for (const auto& sample : samples) {
    const auto day = localDayOf(sample.timestamp);
    if (!day || *day > lastDay) continue;
    if (*day >= firstDay) {
        EnergyBucket& bucket = buckets[bucketIndexOf(ranges, *day)];
        ++bucket.sampleCount;
        if (previousTotal && sample.total_mwh > *previousTotal)
            bucket.energyUsed_mWh += sample.total_mwh - *previousTotal;
    }
    previousTotal = sample.total_mwh;   // 범위 앞 기록도 "직전 값"으로 갱신
}
무엇 기록을 오래된 순으로 훑으며 "뒤 기록 − 앞 기록"을 뒤 기록이 속한 구간에 더한다. 범위 시작 직전 1건은 센 개수에는 안 들어가지만 previousTotal을 채워 첫 구간의 사용량을 정확하게 한다. 왜 양수 차이만 기기를 재설정하면 누적계가 0 근처로 돌아간다(100 → 50). 음수를 더하면 사용량이 줄어드는 말이 안 되는 결과가 나오므로 0으로 본다(50 → 80은 정상 30). 빼면 직전 1건이 없으면 첫 구간이 항상 0이 되고, 양수 조건이 없으면 리셋 날 사용량이 음수가 된다. bucketIndexOf는 이진 탐색(upper_bound)이라 기록이 많아도 빠르다.

4. 용어 풀이

  • 누적계(total_mwh): 기기가 켜진 뒤 지금까지 쓴 전력량 합. 구간 사용량 = 끝 값 − 시작 값.
  • 반개구간 [from, to): from은 포함, to는 미포함. 이어 붙여도 겹치거나 빠지는 기록이 없다.
  • truncated: 조건에 맞는 기록이 limit보다 더 있어 잘렸다는 표시.
  • civil date: 우리가 쓰는 달력 날짜(년·월·일). 일 수(days)와 서로 바꾸는 것이 Hinnant 알고리즘.
  • 순수 함수: 같은 입력이면 항상 같은 출력이고 DB·시계·파일을 건드리지 않는 함수. 시험하기 쉽다.
  • 버킷(bucket): 집계 구간 하나(일·주·월 단위 칸).

5. 이해도 질문

Q1. 첫 구간 계산에 "범위 직전 1건"을 포함하지 않으면 11-01 구간 사용량은 어떻게 되나?

정답범위 안 첫 기록 때는 previousTotal이 비어 있어 차이를 못 구하므로 그 기록이 가져올 사용량이 사라진다(예: 직전 1000, 첫 기록 1500이면 500이 빠짐). 그래서 첫 구간이 실제보다 작게 나온다.

Q2. UTC 14:59:59 기록과 15:00:00 기록이 서로 다른 날 구간에 들어가는 이유는?

정답+09:00 기준으로 UTC 15:00이 현지 자정이기 때문이다. localDayOf가 epoch초에 9시간을 더한 뒤 하루(86400초)로 내림 나눗셈해 날짜를 구한다. 시험 UtcFifteenOClockIsLocalMidnightBoundary.

Q3. 사용량을 "앞 기록이 속한 구간"이 아니라 "뒤 기록이 속한 구간"에 귀속하면 어떤 점이 좋은가?

정답구간 경계를 넘나드는 증가분이 정확히 한 구간에만 들어가 합계(전 구간 합 = 전체 증가분)가 맞고, 중복·누락이 없다. 직전 1건이 첫 구간에 기여하는 규칙과도 일관된다(UsageGoesToBucketOfTheLaterSample).
