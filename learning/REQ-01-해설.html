REQ-01 해설

"한 번에 락 하나, 락 안에서는 메모리만" 규칙을 코드에 적용한 변경 (3단계 5번, REQ-01·06, 학습 강도: 균형).

1. 한눈에 보기

  • 무엇: DeviceManager가 맵 락을 쥔 채 DB·드라이버를 부르던 곳을 모두 "락 안에서 복사 → 락 풀고 호출"로 바꿨다. 락이 하나도 없던 MatterController의 맵 3개와 등록 파일에 락을 붙였다.
  • 왜: 기기 삭제가 DeviceManager 락 → TCP 소켓 락 순서로, TCP 쪽은 반대 순서로 락을 잡을 수 있었다(교착). 또 느린 작업(DB, 소켓)이 락을 쥐면 다른 모든 요청이 기다린다.
  • 덤: 제어 결과(CommandResult.state)에 응답용 상태를 채워 HTTP가 기기를 다시 조회하지 않는다. 처리 못한 예외는 내부 정보 없이 500으로 답한다.

3. 코드 해설

3-1. removeDevice: 맵에서 먼저 빼고, 해제는 락 밖

-    std::lock_guard<std::mutex> lock(mutex_);   // 함수 끝까지 락
-    ... success = driverIt->second->unpairDevice(id);  // 락 안에서 소켓/파일 작업
-    devices_.erase(it);
-    db_.removeDevice(id);+    {
+        std::lock_guard<std::mutex> lock(mutex_);
+        ... protocolDriver = driverIt->second;    // 포인터만 복사
+        devices_.erase(it);                        // 먼저 숨김
+    }
+    success = protocolDriver->unpairDevice(id);   // 락 밖
+    db_.removeDevice(id);

순서가 "지우고 → 해제"로 바뀐 이유: 해제가 오래 걸리는 동안 들어온 제어 요청이 반쯤 지워진 기기를 건드리지 않고 "없는 기기"로 끝나게 하려고. 드라이버 객체는 main이 끝까지 소유하므로 포인터 복사가 안전하다.

3-2. updateDeviceState: 메모리만 락 안에

{
    std::lock_guard<std::mutex> lock(mutex_);
    if (it == devices_.end()) return false;
    if (it->second.state == newState) return true;
    it->second.state = newState;          // 메모리 변경
}
db_.updateDeviceState(id, isActive);      // DB는 락 밖 (DB는 자기 락을 따로 가짐)

3-3. MatterController: 상태 락과 파일 락을 분리

bool MatterController::isPairing(uint64_t nodeId) {
    std::lock_guard<std::mutex> stateLock(stateMutex_);
    return mPairingNodes.count(nodeId) > 0;
}

chip-tool(최대 수 초)은 어느 락도 쥐지 않고 실행한다. 등록 파일은 "읽기 → 걸러서 덮어쓰기" 전체를 fileMutex_ 하나로 묶어, 그 사이에 다른 기기 저장(saveDeviceRegistration)이 끼어 내용이 사라지는 일을 막는다.

3-4. HTTP 래퍼의 마지막 그물

try { handler(req, res); }
catch (const std::exception& e) { /* 로그: 메서드·경로·메시지 */ respondInternalError(res); }
catch (...) { respondInternalError(res); }

응답에는 예외 내용을 넣지 않는다(내부 정보 노출 방지). 테스트가 "fake sendCommand failure" 문자열이 본문에 없음을 확인한다.

3-5. 교착을 "시험"으로 잡는 법

가짜 드라이버의 onUnpair 훅에서 일부러 멈춘 뒤, 다른 스레드의 요청이 1초 안에 끝나는지 본다. 이전 코드(5524d7e)에서는 이 시험이 실패했다. 혹시 진짜 교착이 나도 테스트가 영원히 멈추지 않도록 DeadlockWatchdog가 제한 시간 뒤 프로세스를 끝낸다.

4. 용어 풀이

용어뜻
교착(deadlock)두 스레드가 서로 상대가 쥔 락을 기다려 둘 다 영원히 멈춤. 4조건 중 "순환 대기"를 없애면 생기지 않는다.
상태 락 / 자원 락상태 락은 메모리 자료구조 보호(짧게). 자원 락은 DB 연결·소켓·파일처럼 한 번에 하나만 써야 하는 자원의 입출력 직렬화.
스냅샷(copy-then-release)락 안에서 필요한 값만 복사하고 락을 푼 뒤 그 사본으로 일한다.
데이터 경쟁(data race)두 스레드가 같은 메모리를 동시에 접근하고 그중 하나가 쓰기인데 동기화가 없는 상태. C++에서는 미정의 동작.
TSan(ThreadSanitizer)컴파일러(-fsanitize=thread)가 메모리 접근을 기록해 실행 중 데이터 경쟁을 찾아 주는 도구. 실행된 경로만 검사한다.

5. 이해도 질문

Q1. removeDevice에서 devices_.erase를 unpair 뒤로 다시 옮기면(락은 여전히 밖) 어떤 문제가 생길 수 있나?

정답해제가 진행되는 동안 다른 요청이 그 기기를 여전히 "있음"으로 보고 제어·조회를 시도한다. 이미 끊긴 소켓에 명령을 보내 실패하고 상태를 OFFLINE으로 바꾸는 등, 지워질 기기에 쓸데없는 쓰기가 생긴다. 맵에서 빼고 지운 뒤 erase하려면 다시 락을 잡아야 해 코드도 복잡해진다.

Q2. TSan 테스트가 모두 통과했는데 MatterController에 데이터 경쟁이 없다고 말할 수 없는 이유는?

정답TSan은 실행된 코드만 검사한다. MatterController는 CHIP SDK 의존 때문에 TSan 빌드(HAC_BUILD_SERVER=OFF)에 포함되지 않아 한 번도 실행되지 않았다. 그래서 코드 검토와 dev 빌드 컴파일로만 확인했다. 8번(ChipToolRunner 분리) 뒤에 가짜 러너로 테스트할 수 있게 된다.

Q3. updateDeviceState를 두 스레드가 같은 기기에 "ON", "OFF"로 동시에 부르면 메모리와 DB가 달라질 수 있다. 왜 이것을 감수했나?

정답메모리와 DB를 한 락으로 묶으면 DB(자원 락)를 상태 락 안에서 부르게 되어 L-2를 어기고, 느린 DB가 모든 요청을 막는다. 어긋나는 값은 is_active 한 칸이고 60초 헬스체크가 실제 기기 상태로 다시 쓰므로 영향이 작다(ADR-002 "감수하는 단점").

5b. 리뷰 반영: 삭제 순서와 TOCTOU

1. 한눈에 보기 (5b)

  • 삭제 순서: "맵에서 꺼냄 → DB 삭제 → 기기 해제"로 바꿨다(5번에서는 해제가 DB보다 먼저였다).
  • Matter 해제: 시리얼로 노드 번호를 찾는 일과 명부에서 지우는 일을 한 락 블록에서 한다. 매핑이 없으면 0번 노드에 unpair를 보내지 않는다.
  • 테스트: 느린 제어·상태 읽기 중에도 다른 기기가 1초 안에 응답하는지, unpair가 예외를 던져도 DB에서 지워졌는지, 같은 ID를 동시에 지우고 등록한 뒤에도 다시 일치하는지 확인한다.

2. 왜 DB를 먼저 지우나

순서unpair가 실패·예외일 때DB 삭제가 실패할 때
해제 → DB (5번)예외면 DB 삭제가 실행되지 않음 → 메모리엔 없는데 DB엔 남음 → 재시작하면 지운 기기가 되살아남기기는 이미 해제됐는데 DB엔 남음 → 되돌릴 수 없음
DB → 해제 (5b, 설계 5.2)DB는 이미 지워짐 → 재시작해도 안 돌아옴. 기기 쪽 정리는 로그로 추적아직 해제 전이므로 맵에 되돌리고 false → 아무것도 바뀌지 않은 상태

원칙: 되돌리기 쉬운 단계(메모리, DB)를 먼저, 되돌릴 수 없는 단계(기기에 RESET·unpair 보내기)를 마지막에. 그래야 중간에 실패해도 "아무것도 안 됨" 아니면 "다 됨"에 가깝게 끝난다.

if (!db_.removeDevice(id)) {
    std::lock_guard<std::mutex> lock(mutex_);

    return false;

emplace는 키가 이미 있으면 아무것도 넣지 않는다. 복원하려는 사이에 다른 스레드가 같은 ID를 새로 등록했다면, 새 기기가 이긴다.

3. TOCTOU 예

TOCTOU(Time Of Check to Time Of Use): 확인한 시점과 사용하는 시점 사이에 상태가 바뀌는 문제. 각 단계가 따로 락을 잡으면, 단계마다 락이 있어도 생긴다.

-    uint64_t deviceId = getNodeId(serialNumber);   // 락 A 잡고 풀고 (확인)
-    {   std::lock_guard lock(stateMutex_);            // 락 A 다시 (사용)
-        mPairingNodes.erase(deviceId); ...  }        // 그 사이 매핑이 바뀌었을 수 있음, 없으면 0+    {   std::lock_guard lock(stateMutex_);
+        auto it = mSerialToNodeId.find(serialNumber);   // 확인과
+        if (it != mSerialToNodeId.end()) {
+            foundNodeId = it->second;                    // 사용을
+            mSerialToNodeId.erase(it); ...               // 한 블록에서
+        }
+    }
+    if (!foundNodeId) return true;                      // 0번 노드 unpair 방지

예: 스레드 1이 노드 번호 5를 읽고 락을 푼 사이에 스레드 2가 같은 기기를 지웠다. 스레드 1은 이미 사라진 5번을 지우려 하고, 매핑이 없을 때는 getNodeId가 0을 돌려줘 엉뚱한 0번 노드에 unpair를 보냈다.

4. 이해도 질문 (5b)

Q4. 같은 ID를 한 스레드는 계속 지우고 다른 스레드는 계속 등록하면, 반복 중간에 메모리와 DB가 어긋날 수 있다. 어떤 순서에서 그런가?

정답삭제 스레드가 맵에서 꺼냄 → 등록 스레드가 맵에 넣고 DB에 INSERT → 삭제 스레드가 DB DELETE. 결과적으로 메모리엔 있고 DB엔 없다. 맵과 DB를 한 락으로 묶지 않는 대가(ADR-002)이며, 다음 등록·삭제나 재등록이 바로잡는다. 테스트는 반복이 끝난 뒤 순차 삭제·등록으로 다시 일치하는지만 본다.

Q5. fileMutex_를 unique_lock + 수동 unlock() 대신 블록 안의 lock_guard로 바꾼 이유는?

정답수동 unlock은 그 전에 예외가 나거나, 나중에 누가 return을 끼워 넣으면 해제 위치가 흐려진다. 블록 lock_guard는 중괄호가 곧 임계 구역이라 범위가 눈에 보이고, 예외에도 RAII로 반드시 풀린다.
