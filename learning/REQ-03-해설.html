REQ-07 해설

싱글톤을 없애고 생성자 주입으로 바꾼 변경 (3단계 4a, 학습 강도: 균형). 4b가 끝나면 아래에 "4b" 절을 덧붙인다.

REQ-03 · REQ-04 해설

에너지 조회를 "확인 → 조회 → 성공할 때만 저장"으로 바꾸고 DB 오류 처리를 다듬은 변경 (3단계 6번, 학습 강도: 균형).

1. 한눈에 보기

  • B-02 이중 집계: 조회 실패를 0으로 저장하면, 다음 정상 조회 때 플러그 누적값 전체가 "증가분"으로 다시 더해졌다. 이제 실패는 저장하지 않는다.
  • REQ-04 / H6: 없는 ID나 TCP 기기로 E6를 부르면 통계 행이 생기고, TCP 기기는 Matter 드라이버에 물었다. 이제 존재를 먼저 확인하고 기기 자신의 드라이버에 묻는다.
  • DB 함수: 실패를 성공처럼 보이게 하던 곳(D4·D5·E7)을 고치고, NULL 열·닫힌 DB에도 죽지 않게 했다(D3·D6).

2. 흐름 그림: E6 전/후

3. 코드 해설

3-1. 성공한 값만 통계에

const auto reading = protocolDriver->readEnergy(deviceId);   // 락 밖
if (!reading.ok()) return Result<EnergySnapshot>::failure(reading.error.code, ...);
if (!db_.updateEnergyStat(deviceId, reading.value->cumulative_mWh, snapshot.totalEnergy_mWh))
    return Result<EnergySnapshot>::failure(ErrorCode::Internal, ...);

Result가 "값이 있다/없다"를 타입으로 구분하므로, 호출자가 0을 넣어 계속 진행하는 실수를 할 수 없다.

3-2. D4: "행 없음"과 "조회 실패"를 구분

const int stepResult = sqlite3_step(stmt);
if (stepResult == SQLITE_ROW) { ... exists = true; }
if (stepResult != SQLITE_ROW && stepResult != SQLITE_DONE) return rollback("조회");

예전에는 SELECT가 실패해도 "행 없음 = 최초 등록"으로 보고 real_total을 지금 값으로 덮었다. 누적값이 통째로 사라지는 오류다. SQLITE_DONE만이 진짜 "행 없음"이다.

3-3. D2: REPLACE 대신 UPSERT

INSERT INTO devices (...) VALUES (...)
ON CONFLICT(device_id) DO UPDATE SET display_name = excluded.display_name, ..., deleted_at = NULL;

INSERT OR REPLACE는 "지우고 새로 넣기"라 목록에 없는 열(ip)이 NULL이 된다. UPSERT는 적은 열만 바꾼다. excluded는 넣으려던 새 행을 가리킨다.

3-4. E7: 빈 목록과 오류를 구분

getEnergyHistory가 Result<vector>를 돌려준다. "기록이 0건"은 성공(빈 배열), "DB를 읽지 못함"은 실패다. v1.0 계약대로 실패도 HTTP 200 + {"error"}로 답하지만, 적어도 앱이 "기록 없음"으로 오해하지 않는다.

4. 용어 풀이

용어뜻
센티널 값(sentinel)"없음"을 0, -1 같은 특별한 값으로 표시하는 방식. 정상 값과 겹치면(전력 0) 구분이 안 돼 B-02 같은 버그가 생긴다. Result/optional이 대안.
UPSERTINSERT + UPDATE. 키가 겹치면 넣지 않고 기존 행을 갱신한다(SQLite 3.24+).
트랜잭션 롤백BEGIN 이후 바꾼 것을 모두 취소. 실패 경로마다 롤백해야 다음 BEGIN이 "이미 트랜잭션 중" 오류 없이 시작된다.
sqlite3_close_v2정리 안 된 문장이 남아 있어도 실패하지 않고, 마지막 문장이 정리될 때 연결을 닫는다.

5. 이해도 질문

Q1. 실시간 전력이 UNKNOWN일 때는 왜 0으로 보여 줘도 괜찮은가?

정답실시간 전력은 화면 표시용이고 DB 통계에 쓰이지 않는다. 틀려도 다음 조회 때 바로 바뀌고 누적되지 않는다. 반면 누적값은 last_plug_mwh에 저장돼 다음 증가분 계산의 기준이 되므로 0이 들어가면 오염이 남는다.

Q2. 존재 확인(①)과 통계 저장(③) 사이에 다른 스레드가 기기를 지우면 어떻게 되나?

정답저장은 이미 일어나 그 ID의 stats 행이 남을 수 있고, ④에서 기기가 없으므로 응답은 "등록되지 않은 기기"가 된다. 확인과 저장을 한 락으로 묶으면 막을 수 있지만 상태 락 안에서 DB를 부르게 되어 락 규칙(L-2)을 어긴다. 드물고 무해한 행이라 2차 정리(REQ-13)에서 지운다.

Q3. D4 테스트는 SELECT 실패를 어떻게 만들었나?

정답임시 파일 DB를 별도 연결로 열어 last_plug_mwh 열 이름을 바꿨다. 그러면 DatabaseManager의 SELECT 준비가 "no such column"으로 실패한다. 테스트 후 이름을 되돌려 롤백이 제대로 끝나 다음 트랜잭션이 성공하는지도 확인한다.

6b. 리뷰 반영: 역순 완료 · 백업 먼저

1. 역순 완료가 왜 이중 집계가 되나

같은 플러그를 헬스체크(A)와 앱 E6(B)가 거의 동시에 조회했다. A가 먼저 시작했지만 chip-tool이 늦게 끝났다.

왜 기기별인가: 전력 락 하나로 모든 기기를 묶으면, 플러그 하나의 chip-tool(최대 수 초)이 다른 플러그 E6까지 줄 세운다. 기기별 shared_ptr<mutex>를 작은 맵(energyLocksMutex_, 메모리만)에서 꺼내 쓴다.

락 규칙과의 관계: 이 락은 쥔 채로 드라이버·상태 락·DB 락을 차례로 잡는다. 그래서 L-7 순서의 맨 앞에 두고, "상태 락을 쥔 채 이 락을 잡지 않는다"를 지키면 순환 대기가 생기지 않는다.

const auto deviceEnergyLock = energyLockFor(deviceId);     // 맵 락: 꺼내고 바로 풂
std::lock_guard<std::mutex> energyLock(*deviceEnergyLock);  // 같은 기기만 대기
reading = driver->readEnergy(deviceId);
{ [mutex_] 아직 있나? 없으면 DeviceNotFound }                 // E10: 저장 전에 재확인
db_.updateEnergyStat(...);

2. 왜 백업을 먼저 하나

순서백업이 실패하면
테이블 생성 → 백업 (6번까지)이미 원본에 CREATE TABLE을 써 버렸다. "실패해서 아무것도 안 바꿨다"가 거짓이 된다.
버전 확인 → 백업 → 테이블 생성 → 마이그레이션 (6b)원본에는 읽기만 했으므로 파일이 바이트 단위로 그대로다(테스트로 확인).

원칙은 5b의 삭제 순서와 같다: 되돌리기 어려운 쓰기 전에, 되돌릴 수단(백업)을 먼저 확보한다. 운영 DB가 아직 v0이라 다음 서버 시작 때 바로 이 경로를 탄다.

덤(E5): "테이블이 있나?" 조회가 실패했을 때 "없다"로 보면 백업을 건너뛰고 마이그레이션해 버린다. 그래서 std::optional<bool>로 "있음/없음/모름"을 나눴다.

3. 이해도 질문 (6b)

Q4. 기기별 전력 락을 removeDevice에서도 잡으면 E10의 남은 틈이 완전히 닫힌다. 왜 지금은 그렇게 하지 않았나?

정답삭제 요청이 진행 중인 chip-tool 조회(최대 수 초)가 끝날 때까지 기다리게 된다. 남는 틈은 "재확인 직후 ~ 저장" 사이의 아주 짧은 구간이고, 결과도 무해한 통계 행 하나라 2차 정리(REQ-13)로 치우는 편이 응답성에 낫다.

정답CHIP SDK 없이 단위 테스트할 수 있다. OFFLINE·PAIRING·UNKNOWN·빈 값·비숫자·음수·64비트 값 같은 모든 분기를 chip-tool 없이 확인한다(TSan 빌드에도 포함됨).
