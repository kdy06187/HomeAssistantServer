REQ-10 · REQ-13 해설 (2차 13b)

기기 등록을 "기다리는 요청"에서 "작업 접수 → 상태 조회"로 바꾸고(비동기 작업 패턴), 등록 결과를 DB 상태에 맞게 판정하며, 같은 기기의 삭제·재등록이 엇갈리지 않게 줄 세운다 (3단계 2차 13b, 학습 강도: 균형).

1. 한눈에 보기

13b-1 DBfindDevice: 없음·활성·숨김(+숨긴 시각). purgeDeviceRecords: 숨김 행 하나의 기록을 한 트랜잭션으로 영구 삭제.
13b-2 등록 판정registerCommissioned: 활성이면 ALREADY_REGISTERED, 90일 안 숨김이면 복구(restored), 지났으면 새 기기. 같은 ID 삭제·등록은 ID별 락으로 차례로. 드라이버 확정 훅.
13b-3 작업 서비스CommissioningService: 작업 스레드 1개, 작업 표(메모리), 동시 1개, 취소·정지.
13b-4 HTTPE3 → 202 + jobId, E8 GET /api/commission/{jobId}, TCP 빈 payload = 앱이 접속한 서버 주소.

2. 흐름 그림: 접수 → 작업 스레드 → 조회

3. 코드 해설

① 등록 판정과 확정 훅 (DeviceManager::registerCommissioned)

const auto idLock = registrationLockFor(id);          // 같은 ID의 삭제(unpair까지)가 끝날 때까지 기다림
std::lock_guard<std::mutex> registrationLock(*idLock);
if (isShuttingDown_) return decline(Cancelled, ...);
switch (db_.findDevice(id).value->kind) {
case Active: return decline(AlreadyRegistered, ...);  // 덮어쓰지 않음
case Hidden: 90일 안이면 restored = true, 지났으면 purgeDeviceRecords
case None:   break;
}
if (!addDevice(...)) return decline(Internal, ...);    // DB 먼저 → 메모리
finalizeQuietly(driver, outcome, true);                // 여기서야 Matter 매핑 기록
무엇을커미셔닝 결과를 DB 상태로 판정하고, 결과를 드라이버에 "확정/거절"로 알린다.
왜예전에는 Matter가 commission 안에서 매핑을 먼저 썼다. 활성 기기를 다시 페어링하면 그 기기 매핑이 새 노드로 덮이고, 실패 정리 unpairDevice(시리얼)는 활성 기기 매핑까지 지웠다.
빼면ID 락을 빼면 삭제의 늦은 unpair가 방금 등록한 새 노드 매핑을 지운다(M4, 시험 SlowUnpairOfDeletedSerialDoesNotRemoveNewNode).

② Matter: 매핑 기록 시점 이동 (before/after)

// before: commission 안에서 시리얼을 읽자마자
mSerialToNodeId[serial] = nodeId; saveDeviceRegistration(serial, nodeId);// after: commission은 {serial, "", nodeId}만 돌려주고
void finalizeCommission(outcome, accepted) {
    if (accepted) { mSerialToNodeId[serial] = nodeId; saveDeviceRegistration(...); return; }
    runChipTool({"pairing", "unpair", 새 nodeId});      // 기존 매핑은 그대로
}

③ 작업 스레드 한 바퀴 (CommissioningService::workerLoop)

workAvailable_.wait(lock, [this]{ return stopping_ || pending_.has_value(); });
work = std::move(*pending_); pending_.reset();          // 비밀값을 서비스에 오래 두지 않음
jobs_[work.jobId].status.state = JobState::Running;
// --- 락 밖 ---
result = commissionOnce(devices_, driver, ..., cancelRequested_);
work.request = CommissionRequest{};                       // 다 쓴 요청 지움
// --- 락 안 ---
finishLocked(work.jobId, result);                        // SUCCEEDED / FAILED(code)
무엇을요청 스레드(HTTP)는 접수만, 오래 걸리는 일은 작업 스레드가 한다.
왜동기 E3는 최대 190초 동안 HTTP 스레드·앱 연결을 붙잡았다. 종료 때도 핸들러가 끝날 때까지 기다려야 했다.
빼면락 안에서 commissionOnce를 부르면 수십 초 동안 E8 조회가 모두 멈춘다(락 안에서는 메모리만).

④ jobId: 시작 시각 36진 + 순번

"c-" + base36(서비스 시작 시각 epoch초) + "-" + 순번   // 예: c-tk3q5s-1

날짜+순번(c-20261117-0001)이면 서버를 다시 켜면 순번이 1부터라, 옛 jobId를 폴링하던 앱이 다른 작업의 결과를 볼 수 있다. 시작 시각이 들어가면 재시작 뒤 겹치지 않는다.

4. 용어 풀이

용어뜻
비동기 작업 패턴요청은 바로 "접수됨(202)+작업 ID"로 답하고, 결과는 따로 조회하게 하는 방식.
작업 표(job table)작업 ID → 상태(대기·실행·성공·실패). 여기서는 메모리에만, 끝난 작업은 1시간 보관.
확정 훅(hook)앞 단계 결과가 정해진 뒤 불러 주는 함수. 드라이버가 "확정이면 기록, 거절이면 정리"를 고른다.
ID별 락기기 ID마다 따로 둔 뮤텍스. 같은 기기 작업만 줄 서고 다른 기기는 막지 않는다.
local_addr서버 쪽 소켓 주소 = 앱이 접속한 서버 IP. 기기에게 "여기로 접속해"라고 알려 줄 주소로 쓴다.

5. 이해도 질문

  1. finalizeCommission을 ID 락 밖(등록이 끝난 뒤)에서 부르면 어떤 순서에서 문제가 생기나?
  2. 작업 표에 요청 전체를 넣어 두면 편할 텐데 왜 넣지 않나? 넣으면 무엇이 위험한가?
  3. 같은 플러그를 "삭제 → 90일 안에 재등록"하면 E8의 restored는? 91일 뒤라면?
정답 보기
  1. 등록(메모리 추가)과 훅 사이에 같은 ID의 삭제가 끼면: 삭제가 매핑 없음으로 unpair를 건너뛰고 숨김 처리 → 그 뒤 훅이 숨긴 기기의 매핑을 기록해, 숨겨진 기기의 노드가 남는다.
  2. Wi-Fi 비밀번호·설정 코드가 1시간 동안 메모리에 남고, 조회 응답·로그·덤프로 샐 수 있다(S-08). 작업 상태에는 결과만 있으면 된다.
  3. 90일 안: true(통계·이력 이어받음). 91일 뒤(정리 작업 전이라 행이 남아 있어도): 기록을 지우고 새 기기, false.

실습 1: 작업 취소 API 흉내 — CommissioningService::cancelJob(jobId)

  • 목표: 대기(PENDING) 중인 작업만 취소해 FAILED/CANCELLED로 바꾸고, 실행 중이면 CommissionBusy를 돌려준다.
  • 고칠 파일: include/CommissioningService.hpp, src/CommissioningService.cpp, 시험 tests/integration/CommissioningServiceTest.cpp.
  • 완료 기준: start() 전에 submit → cancelJob → getJob이 Cancelled, 드라이버 호출 0회. TSan 경고 0.
힌트

stop()이 대기 작업을 취소하는 부분(pending_과 finishLocked)을 그대로 따라 하되, pending_->jobId == jobId일 때만. 모두 mutex_ 안에서 메모리만 다룬다.

정답 
Status CommissioningService::cancelJob(const std::string& jobId) {
    std::lock_guard<std::mutex> lock(mutex_);
    if (pending_ && pending_->jobId == jobId) {
        finishLocked(jobId, Result<RegisterOutcome>::failure(ErrorCode::Cancelled, "cancelled by user"));
        pending_.reset();
        return Status::success();
    }
    const auto it = jobs_.find(jobId);
    if (it == jobs_.end()) return Status::failure(ErrorCode::JobNotFound, "job not found");
    if (it->second.status.state == JobState::Running) return Status::failure(ErrorCode::CommissionBusy, "running");
    return Status::success();  // 이미 끝남: 아무것도 안 함
}

실습 2: 빈칸 — submit의 Busy 판정

submit에서 "진행 중 작업이 있으면 Busy" 반복문을 지우고 직접 다시 써 본다. 시험 SecondSubmitWhileInProgressIsBusyAndAllowedAfterFinish가 통과하면 완료.

힌트

끝난 작업(SUCCEEDED·FAILED)은 표에 남아 있어도 Busy가 아니다. 상태가 Pending 또는 Running인 것만 센다.
