(1) 역호출 제거: 결과를 돌려주고 호출자가 등록

  • 빼면: 사본 대신 매니저 참조를 다시 넘기면 순환 의존과 교착 위험이 되살아난다.

5. 이해도 질문

Q1. commission에 활성 ID의 "사본"을 넘기는 대신 DeviceManager&를 넘기면 어떤 문제가 생길까?

정답드라이버가 매니저를 다시 호출하는 순환 의존이 되살아난다. 커미셔닝 중 락을 쥔 채 매니저 락을 요청하는 경로가 생겨 교착 위험이 있고, 드라이버 테스트에도 진짜 매니저가 필요해진다.

Q2. 서비스 로케이터와 생성자 주입은 둘 다 "전역에서 꺼내 쓰지 않고 밖에서 준다"처럼 보인다. 무엇이 다를까?

정답로케이터는 클래스 내부에서 레지스트리를 불러 필요한 것을 꺼내므로 시그니처에 의존이 드러나지 않고, 테스트에서도 전역 레지스트리를 비워야 한다. 생성자 주입은 인자로 의존이 명시되고 테스트가 직접 가짜를 넘긴다.

Q3. PeriodicTasks::stop()에서 notify_all()을 빼면 어떻게 될까?

정답스레드는 최대 60초 후 타임아웃으로 깨어난 뒤에야 isRunning_이 false임을 보고 끝난다. 그동안 join이 블록되어 종료와 테스트가 최대 60초 멈춘다.

(1) 결과 값 패턴과 계층 경계의 번역 (N-01)

// before: bool 하나로 모든 걸 표현
bool executeCommand(...);   // 차단도, 지연도 true. 기기 무응답만 false(그마저 내부에서 삼킴)

std::string controlMessageFor(const CommandResult& result) {
    if (result.outcome != CommandOutcome::Failed) return "명령 성공!";
    return result.error.code == ErrorCode::CommandBlocked ? "명령 성공!" : "명령 실패!";
}
  • 무엇: 안쪽(DeviceManager)은 "무슨 일이 있었는지"를 풍부하게 기록하고, 바깥쪽(HTTP)은 v1.0 계약대로 문구 두 가지로만 좁힌다.
  • 왜: 번역을 경계 한 곳에 두면 내부를 더 자세히 바꿔도 앱과의 계약은 안 깨진다. 차단(CommandBlocked)은 v1.0 호환 때문에 성공 문구를 쓴다.
  • 빼면: bool로 돌아가면 "지연 실행 접수"와 "기기 무응답"을 구분할 수 없어, 화면·로그·테스트가 모두 추측에 의존한다. 매핑은 표 하나로 테스트되므로 계약 변경이 한눈에 보인다.

(2) addRoute 래퍼 = Decorator

svr.set_pre_routing_handler(...);   // 본문 읽기 전에 401 -> 연결 닫힘
svr.Get("/api/devices", handler);   // 라우트마다 직접 등록
void HTTPServer::addRoute(HttpMethod method, const std::string& pattern, RouteHandler handler) {
    auto guarded = [this, handler = std::move(handler)](const auto& req, auto& res) {
        if (!ApiAuth::isAuthorized(req.get_header_value("Authorization"), mApiToken)) {
            res.status = 401; ...; return;
        }
        handler(req, res);          // 인증을 통과한 요청만 도달
    };
    switch (method) { case HttpMethod::Get: svr.Get(pattern, guarded); break; ... }
}
// 마지막: 모든 메서드에 ".*" 라우트 -> 없는 경로도 토큰 틀리면 401, 맞으면 404
  • 무엇: 핸들러를 인증 코드로 "감싼" 함수를 등록한다(Decorator). svr.Get 등은 이 함수 안에서만 호출한다.
  • 왜: 새 라우트를 addRoute로 추가하면 인증이 자동으로 붙어, 인증 누락이 구조적으로 어렵다. 라우트 매칭이 끝난 뒤(본문 수신 후)에 실행되므로 N-03도 사라진다.
  • 빼면: 라우트를 svr.Get으로 직접 등록하는 순간 인증이 빠진다. 그래서 "등록 함수 하나만 쓴다"는 규칙과 테스트가 필요하다(규칙이 구조의 일부).

(3) 원시 소켓 테스트가 필요한 이유

TEST_F(HttpServerTest, RawSocketBadTokenWithSmallBodyGets401AndKeepAliveWorks)
TEST_F(HttpServerTest, RawSocketBadTokenWith8KiBBodyGets401AndKeepAliveWorks)
// 같은 TCP 연결로 요청 2개를 직접 보내, 둘 다 응답이 오는지 확인
  • 무엇: socket으로 HTTP 문장을 직접 보내 한 연결에서 두 번 요청한다.
  • 왜: httplib::Client는 연결이 끊기면 자동 재연결해서 성공으로 보이게 만든다. 앱(OkHttp)은 그렇지 않아 버그를 겪는다. 도구가 버그를 가리면 회귀 테스트가 아니다.
  • 빼면: 다시 pre-routing으로 되돌려도 기존 테스트는 전부 통과한다.

(4) 본문 상한과 종료 구조

svr.set_payload_max_length(16 * 1024);   // 인증 전에 읽게 됐으니 크기 상한

void HTTPServer::stop(){
    mIsRunning = false;
    while (!mHasRunFinished) { mServer->stop(); sleep 5ms; }   // listen 진입 전 stop은 무시되므로 반복
    mServerThread.join();
}
// main: for (;;) pause();   // 프로세스는 kill로 종료
  • 16KiB: 본문을 먼저 읽는 대가로 "인증 안 된 사용자가 큰 본문을 밀어 넣는" 길이 열렸다. 정상 앱은 이 크기를 안 넘으므로 상한으로 막는다(트레이드오프, ADR-009).
  • stop(): 예전엔 stop()이 서버를 멈추지 못했고(스레드가 계속 listen), 오히려 그 덕에 main 끝의 stop() 호출 후에도 서버가 살아 있었다. 진짜 멈추게 고치자 main이 곧바로 끝나 서버가 죽을 수 있어, 무한 대기(pause)로 의도를 드러냈다. 숨은 의존을 고치면 그 의존하던 쪽도 고쳐야 한다.

4. 용어 풀이 (4b)

  • 결과 값(Result) 패턴: 성공/실패와 이유를 한 객체로 돌려주는 방식. bool보다 정보가 많다.
  • Decorator(래퍼): 기존 함수를 감싸 앞뒤 일(인증 등)을 덧붙이는 패턴.
  • keep-alive: 응답 후에도 TCP 연결을 열어 두고 재사용하는 HTTP 기능. OkHttp는 연결 풀로 재사용한다.
  • RST: TCP가 연결을 즉시 끊을 때 보내는 신호.
  • EOF: 읽는 도중 상대가 연결을 닫아 데이터가 끝난 상태. 앱에서는 "unexpected end of stream".
  • 횡단 관심사: 인증·로깅처럼 여러 기능에 공통으로 걸리는 일.

5. 이해도 질문 (4b)

  1. controlMessageFor에서 차단(CommandBlocked)이 "명령 성공!"인 이유는? 이 매핑을 DeviceManager 안에 두면 무엇이 곤란한가?
  2. N-03을 고친 뒤에도 기존 httplib::Client 테스트만 있다면, 누가 인증을 다시 pre-routing으로 옮겨도 왜 모르는가?
  3. 새 라우트를 svr.Get으로 직접 등록하면 무슨 일이 생기는가? main의 pause()를 지우면?
정답
  1. v1.0 앱 계약이 차단을 성공 문구로 받기로 했기 때문(호환). 번역을 내부에 두면 HTTP 문구 변경이 도메인 코드를 건드리고, 내부 결과가 외부 계약에 묶인다. 경계(HTTP 계층)에서 번역해야 한다.
  2. httplib 클라이언트가 끊긴 연결에서 자동 재연결해 성공처럼 보이기 때문. 원시 소켓으로 한 연결에 두 요청을 보내야 EOF를 잡는다.
  3. 인증 없이 열린 라우트가 된다(유일한 등록 경로 규칙 위반). pause()를 지우면 stop()이 진짜 멈추게 됐으므로 main이 바로 끝나 서버가 종료된다.
