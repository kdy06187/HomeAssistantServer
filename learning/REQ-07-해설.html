3. 코드 해설

(1) 역호출 제거: 결과를 돌려주고 호출자가 등록

// before: 드라이버가 매니저를 들고 직접 등록
DeviceManager& mDeviceManager;
virtual bool commissionDevice(std::string name, std::string payload, ...) = 0;
// 내부에서 mDeviceManager.addDevice(...) / hasDevice(...)
// after: 결과만 반환
virtual Result<CommissionOutcome> commission(const CommissionRequest& request,
        const std::unordered_set<std::string>& activeDeviceIds) = 0;

// DeviceManager::startCommissioning (락 밖)
const auto outcome = driver->commission(CommissionRequest{...}, activeDeviceIds());
if (outcome.ok() && !outcome.value->deviceId.empty())
    addDevice(outcome.value->deviceId, name, type, driverTypes, ...);
  • 무엇을: 드라이버는 "누가 등록됐나"를 사본(activeDeviceIds)으로 받고, 새 기기 ID를 반환값으로 알린다.
  • 왜: 의존이 매니저 → 드라이버 한 방향이 된다. 커미셔닝은 수십 초라 락을 쥔 채 드라이버가 다시 매니저 락을 요청하는 경로(교착)가 있었는데, 그 경로가 없어진다. 사본이라 호출자 락과 무관하게 읽는다.
  • 빼면: 사본 대신 매니저 참조를 다시 넘기면 순환 의존과 교착 위험이 되살아난다.

(2) dynamic_cast를 가상 함수로

auto* matter = dynamic_cast<MatterController*>(driver);  // 구체 클래스를 알아야 함
virtual Result<EnergyReading> readEnergy(const std::string&) {
    return Result<EnergyReading>::failure(ErrorCode::UnsupportedOperation, "...");  // 기본: 미지원
}
  • 무엇을: 상위 계층(DeviceManager)이 구체 클래스가 아닌 인터페이스에만 의존한다(의존성 역전, DIP).
  • 왜: 가짜 드라이버도 같은 경로로 전력 조회를 흉내 낼 수 있다. 단, 에너지를 못 재는 TCP도 이 함수를 물려받아 ISP(쓰지 않는 메서드에 의존하지 않기)와 약간 어긋난다. 구현체가 하나뿐이라 별도 EnergyMeter는 과하다고 판단했다(ADR-001 단점 절).
  • 빼면: 새 프로토콜이 에너지를 지원할 때마다 DeviceManager에 cast 분기가 늘어난다.

(3) 자기 등록 제거 → main의 명시 등록

// PCDriver.cpp: 정적 DriverRegistrar로 프로그램 시작 때 "마법처럼" 등록
// main.cpp
deviceDrivers.registerDriver(DriverType::PC_DRIVER, [&tcpDriver](IMessageSender*) {
    return std::make_shared<PCDriver>(&tcpDriver);
});
  • 왜: 정적 객체는 초기화 순서가 불분명하고(전역 싱글톤이 아직 없을 수 있다), 정적 라이브러리면 링커가 "아무도 안 쓰는" 등록 객체를 빼 버린다. 등록 코드가 눈에 보이면 순서와 누락이 한눈에 보인다.
  • 서비스 로케이터와 차이: 로케이터는 클래스가 전역 레지스트리에서 필요한 것을 스스로 꺼낸다(의존이 숨음). DI는 생성자 인자로 밖에서 받는다(의존이 시그니처에 보임).

(4) PeriodicTasks: sleep 루프 → wait_for

while (running) { std::this_thread::sleep_for(1s); ...60번 셌다가 점검 }  // 정지에 최대 1초
std::unique_lock<std::mutex> lock(mutex_);
if (wakeUp_.wait_for(lock, interval, [this]{ return !isRunning_; })) return;  // 정지 신호면 즉시 종료
// (락 해제 후) deviceManager_.runHealthCheck();
  • 무엇을: stop()이 notify_all로 대기 중인 스레드를 바로 깨우고 join으로 끝까지 기다린다. 스레드는 PeriodicTasks가 소유하고 소멸자도 stop()을 부른다.
  • 왜: 종료가 즉시 되고, 테스트에서 객체를 지워도 스레드가 남지 않는다. 점검은 락 밖에서 해 stop이 막히지 않는다.
  • 빼면: join 없이 소멸하면 살아 있는 스레드가 이미 사라진 매니저를 참조한다.

  • 지금은 driverTypes를 커미셔닝 호출이 지역 변수로 들고 가 성공했을 때만 addDevice에 넘긴다. 상태가 남지 않으니 버그가 생길 자리가 없다.

5. 이해도 질문

Q1. commission에 활성 ID의 "사본"을 넘기는 대신 DeviceManager&를 넘기면 어떤 문제가 생길까?

정답드라이버가 매니저를 다시 호출하는 순환 의존이 되살아난다. 커미셔닝 중 락을 쥔 채 매니저 락을 요청하는 경로가 생겨 교착 위험이 있고, 드라이버 테스트에도 진짜 매니저가 필요해진다.

Q2. 서비스 로케이터와 생성자 주입은 둘 다 "전역에서 꺼내 쓰지 않고 밖에서 준다"처럼 보인다. 무엇이 다를까?

정답로케이터는 클래스 내부에서 레지스트리를 불러 필요한 것을 꺼내므로 시그니처에 의존이 드러나지 않고, 테스트에서도 전역 레지스트리를 비워야 한다. 생성자 주입은 인자로 의존이 명시되고 테스트가 직접 가짜를 넘긴다.

Q3. PeriodicTasks::stop()에서 notify_all()을 빼면 어떻게 될까?

정답스레드는 최대 60초 후 타임아웃으로 깨어난 뒤에야 isRunning_이 false임을 보고 끝난다. 그동안 join이 블록되어 종료와 테스트가 최대 60초 멈춘다.
