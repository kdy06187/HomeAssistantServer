3. 코드 해설

3-1. 실패를 값으로: Result<T>

template <typename T>
struct Result {
    std::optional<T> value;   // 성공이면 값이 들어 있음
    Error error;              // 실패면 코드 + 로그용 메시지
    bool ok() const { return value.has_value(); }
    static Result success(T v);
    static Result failure(ErrorCode c, std::string m);
};
  • 무엇: "값 또는 오류"를 한 객체로 돌려준다. std::optional은 "값이 있을 수도, 없을 수도 있다"를 나타내는 표준 타입이다. Status는 같은 구조에서 값이 없는 버전이다.
  • 왜: "OFFLINE"이 숫자 자리에 오는 것은 흔한 일이라 예상 가능한 실패다. 호출자가 ok()를 확인하게 강제하면 처리 누락이 눈에 보인다.
  • 빼면: 예외로 돌아가고, 누가 잡을지 호출 경로를 전부 추적해야 한다.
예외Result 값
적합한 경우예상 못 한 것(메모리 부족, 버그)예상 가능한 실패(잘못된 입력, 오프라인)
호출자 처리안 잡으면 위로 전파, 스레드 끝이면 종료반환 타입에 드러남, 확인 안 하면 코드에서 보임
제어 흐름코드에 안 보이는 점프평범한 if
비용던질 때 느림항상 약간의 객체 크기

스레드 규칙: 스레드 함수 밖으로 빠져나간 예외는 받는 곳이 없어 std::terminate가 호출된다. 부모 스레드의 try가 대신 잡아 주지 않는다.

3-2. 파서를 순수 함수로 분리하고 일부러 같은 의미로 유지

out_activePower_mW = std::stoi(activePowerStr);   // "OFFLINE"이면 예외
auto parsedPower = ChipToolOutputParser::parseInteger(activePowerStr);
if (!parsedPower.ok() || 범위 밖) { 로그; return false; }
  • 무엇: 문자열을 받아 문자열/값만 돌려주는 순수 함수다. 파일·프로세스·시간을 쓰지 않으니 chip-tool 없이 문자열만 넣어 테스트한다.
  • 왜 앞부분 규칙을 유지했나: stoll은 "12abc"를 12로 읽는다. 실기 출력에 숫자 뒤 문자가 붙을 수 있어 호환성을 위해 std::from_chars 위에 같은 규칙(앞 공백 무시, 부호, 뒤 문자 무시)을 일부러 재현했다. 테스트가 "12abc"→12를 고정한다. 이런 테스트를 특성화 테스트라 한다("옮겨도 같은 의미"를 증명).
  • 등록 파일 줄은 엄격: parseRegisteredDeviceLine은 노드 ID에 숫자만 허용한다. 손상된 파일을 느슨하게 읽으면 엉뚱한 노드로 명령이 나갈 수 있어서, 잘못된 줄은 번호만 로그에 남기고 건너뛴다.
  • 빼면: 파싱이 MatterController 안에 묶여 있어 단위 테스트가 불가능하다.

3-3. 방어 2단: 값 + 기기별 catch

for (const auto& device : devices) {
    try {
        ... getDeviceState, getDeviceEnergyInfo, DB 기록 ...
    } catch (const std::exception& e) { 로그 }
    catch (...) { 로그 }
}
  • 왜 둘 다: 파싱 실패 값은 "예상한 실패"만 막는다. DB 오류, 메모리 부족처럼 예상 못 한 예외는 값으로 안 돌아온다. 반대로 catch만 있으면 정상적인 실패마다 예외 비용과 모호한 로그가 생긴다.
  • 왜 기기별: 루프 전체를 감싸면 기기 한 대의 예외로 나머지 기기 점검이 건너뛰어진다.

3-4. Clock과 FakeClock

class Clock {
  virtual steady_clock::time_point steadyNow() const = 0;  // 경과 시간
  virtual system_clock::time_point utcNow() const = 0;     // 실제 시각
};
// 테스트: FakeClock clock; clock.advance(std::chrono::seconds(45));
  • 무엇/왜: 시간을 직접 읽지 않고 주입받으면 45초 쿨다운·90일 보관 같은 로직을 기다리지 않고 즉시 테스트한다.
  • steady vs system: steady는 시계 조정에 영향받지 않고 계속 증가해 간격 측정에 맞다. system은 사람이 읽는 실제 시각이며 NTP 등으로 뒤로 갈 수 있다.
  • 상태: 아직 사용처 없음. 4번 변경에서 주입한다.

4. 용어 풀이

  • std::terminate: 처리되지 않은 예외가 있을 때 프로그램을 즉시 끝내는 함수.
  • 순수 함수: 같은 입력이면 같은 출력, 파일·네트워크·시간 같은 바깥 상태를 건드리지 않는 함수.
  • 특성화 테스트: 새 동작을 정하는 대신 기존 동작을 그대로 고정해 리팩터링 안전망으로 쓰는 테스트.
  • std::from_chars: 문자열을 숫자로 바꾸는 예외 없는 표준 함수. 실패는 반환 코드로 알린다.
  • std::optional: 값이 있을 수도 없을 수도 있는 타입.
  • 주입(DI): 객체가 필요한 것을 직접 만들지 않고 바깥에서 넘겨받는 방식.

5. 이해도 질문

1) parseInteger("")이 실패인 것과 parseInteger("12abc")가 12인 것을 보고, 두 규칙이 왜 함께 있는지 설명해 보자.

정답숫자로 시작하지 않으면 값이 없으니 실패(stoll과 같음). 숫자로 시작하면 뒤는 무시해 기존 실기 출력과 같은 결과를 낸다. 옮겨도 의미가 같아야 해서다.

2) 기기별 try/catch를 지우고 파싱 실패 처리만 남기면 어떤 위험이 남는가?

정답파싱 외의 예상 못 한 예외(DB 오류, bad_alloc 등)가 나면 스레드 밖으로 전파되어 다시 std::terminate로 서버가 종료된다.

3) 등록 파일의 한 줄이 ABC,12x일 때 어떻게 되고, 왜 느슨하게 읽지 않는가?

정답노드 ID가 숫자만이 아니므로 실패, 그 줄은 번호만 로그에 남기고 건너뛴다. 12로 읽어 버리면 다른 기기 노드로 명령이 갈 수 있다.

실습 B. 응용: Voltage 추출 함수 설계

목표: chip-tool 출력에서 Voltage: 뒤의 값을 뽑는 extractVoltageText를 같은 패턴으로 추가한다. 고칠 파일: 파서 헤더·cpp, 테스트 파일(사본). 완료 기준: 정상, 키 없음, 값 비어 있음, 같은 키 두 줄(첫 줄 사용) 4개 케이스 통과.

힌트이미 있는 extractTrimmedValueAfterKey(output, "Voltage:")를 재사용하면 한 줄이다. 숫자로 바꿀 때는 parseInteger를 이어 쓴다.
정답
std::optional<std::string> extractVoltageText(const std::string& output) {
    return extractTrimmedValueAfterKey(output, "Voltage:");
}
TEST(ValueExtractTest, Voltage) {
    EXPECT_EQ(*extractVoltageText("x\n Voltage: 230000 \n"), "230000");
    EXPECT_EQ(extractVoltageText("none"), std::nullopt);
    EXPECT_EQ(*extractVoltageText("Voltage:   \n"), "");
    EXPECT_EQ(*extractVoltageText("Voltage: 1\nVoltage: 2"), "1");
}
