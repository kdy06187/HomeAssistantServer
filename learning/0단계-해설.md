# 0단계 해설: 이 서버는 이렇게 돌아간다

대상: HomeAssistantServer(C++17). 근거는 `analysis/as-is-설계.md`, `기능목록.md`, `문제점.md`와 `src/`의 해당 줄. 학습 강도: 균형.
용어는 처음 나올 때 풀이한다. 시각화는 `design/0단계-구조도.html`(별도 작성)을 함께 본다.

## 1. 큰 그림: 세 겹 구조

앱 -> **입구**(HTTPServer) -> **두뇌**(DeviceManager) -> **손발**(드라이버) -> 실제 기기

| 겹 | 클래스 | 한 줄 책임 |
|---|---|---|
| 입구 | `HTTPServer` | 토큰 확인, JSON을 읽고 쓰기. 기기 로직은 모름 |
| 두뇌 | `DeviceManager` | 기기 목록(메모리 맵) 소유, "명령 실행 순서" 결정, DB 저장 |
| 손발 1 | `ProtocolDriver` 구현체(`TCPDriver`, `MatterController`) | "어떤 통신 방식으로 기기에 말하나" |
| 손발 2 | `IDeviceDriver` 구현체(`PCDriver`) | "이 기기는 특별히 이렇게 다뤄라"(명령 전 끼어들기) |
| 창고 | `DatabaseManager`(SQLite) | 기기·전력 기록 저장 |

핵심 아이디어: 손발을 **두 종류로 나눴다**.
- 프로토콜 드라이버 = 통신 방법(TCP냐 Matter냐). 기기 종류와 무관.
- 기기 드라이버 = 기기 특성(PC는 바로 끄면 안 됨). 통신 방법과 무관.
이렇게 나누면 "Matter 플러그에 꽂힌 PC"처럼 (통신 방법 x 기기 특성) 조합을 클래스 폭발 없이 만들 수 있다.

## 2. 요청 하나 따라가기: PC 끄기

앱이 `POST /api/control {"deviceId":"...","command":"OFF"}`를 보낸다. 대상은 PC 드라이버가 부착된 Matter 플러그라고 하자.

1. **토큰 검사** (`HTTPServer.cpp:47-57`): 요청이 라우팅되기 전(pre-routing)에 Bearer 토큰을 확인. 틀리면 401.
2. **핸들러** `handleControlDevice` (`HTTPServer.cpp:146`): JSON 파싱 -> `isAllowedControlCommand`로 ON/OFF만 허용(화이트리스트) -> `DeviceManager::executeCommand` 호출.
3. **기기 복사** (`DeviceManager.cpp:100-108`): 락(mutex, 한 번에 한 스레드만 들어가게 하는 자물쇠)을 잡고 기기 정보를 **복사**한 뒤 락을 푼다. 이후 느린 작업을 락 밖에서 하려는 좋은 습관.
4. **기기 드라이버 실행** (`DriverManager::executeDriversForDevice`): 부착된 드라이버를 차례로 호출. `PCDriver::handleCommand`(`PCDriver.cpp:11-35`)가 OFF를 가로채 (a) TCP 기기들에 종료 메시지 전송, (b) `{proceed=true, delay=45}` 반환.
5. **분기** (`DeviceManager.cpp:113-139`):
   - `proceed=false`면 하드웨어 호출 없이 성공 반환.
   - `delay>0`이면 **detach 스레드**가 45초 자고 나서 하드웨어 명령. HTTP 응답은 즉시 나감.
   - 아니면 바로 `ProtocolDriver::sendCommand` -> 성공 시 `updateDeviceState`(메모리 + DB), 실패 시 OFFLINE.
6. **응답** (`HTTPServer.cpp:160-171`): 현재 state와 "명령 성공!". (하드웨어 실패와 무관하게 성공 문구가 나가는 한계가 있다. 문제점 B-03.)

그림으로 압축하면 이렇다.

```
앱 -> HTTPServer -> DeviceManager.executeCommand
                       |-> DriverManager -> PCDriver (종료 메시지 + "45초 미뤄")
                       '-> (45초 뒤) ProtocolDriver.sendCommand -> 플러그 OFF -> DB 갱신
```

의도: PC가 먼저 안전하게 종료되고 나서 전원을 끊는다. 즉 **"명령 전 훅 + 지연"** 이 PCDriver의 존재 이유다.

## 3. 사용된 설계 패턴과 실무 평가

| 패턴 | 어디 | 장점 | 단점/주의 |
|---|---|---|---|
| **싱글톤**(프로세스에 인스턴스 1개) | `DeviceManager`, `DriverManager`, `DatabaseManager` | 어디서든 접근, 기기 맵이 하나라 단순 | 전역 상태라 테스트에서 교체 어렵고(테스트 0개의 한 원인), 의존 관계가 코드에 안 보임. 실무에선 생성자로 주입(DI)하는 쪽 선호 |
| **전략(Strategy)** | `ProtocolDriver` 인터페이스 + `TCPDriver`/`MatterController` | `DeviceManager`가 통신 방식을 몰라도 됨. 새 프로토콜은 구현체만 추가 | 인터페이스에 없는 기능(에너지 조회)이 생기자 `dynamic_cast`로 구체 클래스를 직접 호출(`DeviceManager.cpp:270`). 추상화가 샌 예 |
| **플러그인 훅 / 책임 연쇄 비슷한 구조** | `IDeviceDriver` + `DriverResult` | 기기별 예외 처리를 핵심 흐름과 분리 | 결과가 `{진행 여부, 지연}` 두 값뿐이라 취소·재시도·결과 통지를 표현 못 함(B-06) |
| **레지스트라 + 팩토리** | `DriverRegistrar` 전역 객체가 `DriverManager`에 "타입 -> 생성 함수" 등록 | 새 드라이버 파일 하나만 추가하면 등록됨(프로그램 시작 전 자동) | 전역 객체 초기화 순서 문제 소지, main에서 PC_DRIVER를 **덮어써** 의존 주입을 하는 우회가 필요해짐(`main.cpp:50`) |
| **예약 후 부착(2단계 생성)** | `reserveDrivers` -> 커미셔닝 -> `addDevice`에서 attach | 커미셔닝 중엔 기기 ID를 모르므로 이름으로 미리 예약 | 키가 기기 **이름**이라 실패 시 잔존·충돌(N-08). 임시 키는 요청 ID처럼 유일해야 함 |
| **관찰자 대신 폴링** | 60초 헬스체크 스레드 | 구현 쉬움 | 변화 감지가 최대 60초 지연, 락 경합 원인 |

실무 관점 한 줄 평: 확장 구조(전략 + 플러그인)는 괜찮게 잡혔다. 약점은 "구조"보다 **동시성(락)과 오류 전파**(성공 거짓 보고, 예외 미처리)에 있다.

## 4. 문제점에서 배우는 개념 3가지

### 4-1. 교착 상태와 락 순서 역전 (N-01)

**교착(deadlock)**: 두 스레드가 서로가 가진 자물쇠를 기다리며 영원히 멈추는 상황.

이 코드의 상황 (락 A = `DeviceManager::mutex_`, 락 B = `TCPDriver::sockets_mutex_`):

| 스레드 1: 기기 삭제 | 스레드 2: TCP 커미셔닝 |
|---|---|
| `removeDevice`가 **A**를 잡음 (`DeviceManager.cpp:159`) | `commissionDevice`가 **B**를 잡음 (`TCPDriver.cpp:110`) |
| 안에서 `unpairDevice` 호출 -> **B**를 기다림 (`TCPDriver.cpp:230`) | 안에서 `hasDevice` 호출 -> **A**를 기다림 (`TCPDriver.cpp:114`) |
| A를 쥔 채 B 대기 | B를 쥔 채 A 대기 -> **서로 영원히 대기** |

**왜 생기나**: 락을 쥔 채로 "다른 객체의 함수"를 불렀기 때문. 그 함수가 내부에서 다른 락을 잡는지 호출자는 모른다.

**일반적 예방법**
1. **락을 쥔 채 외부 코드(콜백, 다른 모듈 함수, I/O)를 부르지 않는다.** 필요한 값만 복사하고 락을 풀고 나서 부른다. 이 코드의 `executeCommand`가 이미 그렇게 한다(3단계).
2. **락 순서 규칙**을 정하고 문서화한다(예: 항상 A -> B). 두 락이 꼭 필요하면 `std::scoped_lock(a, b)`로 한꺼번에 잡는다(순서 문제를 라이브러리가 해결).
3. 락 구간을 최소화하고, 느린 일(네트워크, chip-tool 실행)은 락 밖에서. B-07이 정확히 이 위반(chip-tool을 최대 10초 락 유지).
4. 검증: ThreadSanitizer(`-fsanitize=thread`)의 락 순서 검사, 스트레스 테스트.

이 서버의 고칠 방향: `removeDevice`는 락 안에서 기기 정보만 꺼내 erase, 락을 푼 뒤 `unpairDevice` 호출. 커미셔닝은 소켓 락 안에서 `hasDevice`를 부르지 않고 소켓 키 목록을 복사해 락 밖에서 판정.

### 4-2. 공유 데이터와 스레드 안전 (N-02, B-04, B-05)

**데이터 경쟁(data race)**: 두 스레드가 같은 변수를 동시에 읽고/쓰는데 최소 하나가 쓰기이고 보호가 없는 상태. C++에서는 "가끔 이상함"이 아니라 **정의되지 않은 동작**(크래시, 값 깨짐, 재현 불가 버그).

- `MatterController`의 맵 3개에 락이 없음: HTTP 스레드, 헬스체크, detach 스레드가 동시에 건드림.
- `SendCommandTo("ALL")`이 락 없이 맵을 순회하는 동안 다른 곳이 `erase`하면, 순회 중인 반복자가 무효화됨.

**일반적 대응**
- "이 데이터는 이 락이 보호한다"를 멤버 옆에 적고, 접근마다 `std::lock_guard`.
- 반복 중 수정이 필요하면 **스냅샷 복사 후 순회**.
- 더 나은 구조: 한 스레드만 데이터를 소유하고 나머지는 **작업 큐**로 요청(액터/이벤트 루프). 락 개수가 줄어 교착도 줄어든다.
- 수명 문제: `detach` 스레드가 `this`를 쓰면 객체 소멸 후 접근 가능(N-13). 대안은 스레드를 멤버로 들고 `join`, 또는 취소 가능한 타이머.

### 4-3. 오류를 정직하게 전달하기 (B-03, N-17, B-01)

세 가지가 같은 뿌리다.
- 실패해도 "명령 성공!"을 반환(B-03). 지연 경로는 응답을 낸 뒤에 실패하므로 구조상 알릴 수 없음.
- 본문에 `"error"` 문자열이 있으면 400(N-17): 오류 판정을 **문자열 검색**에 의존. 기기 이름에 error가 들어가도 오작동.
- 헬스체크 스레드에 `try/catch`가 없음(B-01): 예외가 스레드 밖으로 나가면 `std::terminate`로 프로세스 전체 종료.

**일반적 대응**
- 결과는 값으로: `Result{ok, 오류코드, 메시지}` 같은 타입 또는 enum을 반환하고, HTTP 상태코드는 이 값으로 결정(문자열 검색 금지).
- **비동기 작업은 접수 응답(202 Accepted) + 작업 ID + 상태 조회 API** 로. "지연 실행"을 성공으로 위장하지 않는다.
- 스레드의 최상위 루프에는 반드시 `try/catch(...)`로 로그 후 계속(또는 안전 종료).
- 잘못된 입력은 경계(HTTPServer)에서 검증하고 일관된 오류 형식 하나로 응답.

**A1.** 힌트: 락은 누구를 막나? / 부분: `mutex_`는 기기 목록을 보호하므로 락을 길게 쥐면 `GET /api/devices` 등 모든 요청이 기다린다. / 전체: 하드웨어 통신(TCP 1초 대기, chip-tool 5초)과 PC 종료 메시지 전송이 락 안에서 이뤄져 서버 전체가 그 시간만큼 정지한다. 또 `PCDriver`가 내부에서 `DeviceManager` 함수를 호출하는 구조가 되면 같은 스레드가 같은 락을 다시 잡으려 해서 자기 자신과 교착한다(재진입 불가 mutex). 지연 경로는 detach 스레드라 락과는 별개지만, 이 스레드도 락 없이 `drivers_`를 읽는다는 약점이 따로 있다(N-13). 이미 구현된 "복사 후 락 해제"가 올바른 패턴이다. 반면 B-07의 전력 조회는 이 원칙을 어기고 있다.

**A2.** 힌트: `DeviceManager`가 Matter만 알아야 하는 기능이 있다면? / 부분: 구조의 의존 방향이 위반된다(두뇌가 특정 손발에 의존). 새 프로토콜이 에너지를 지원해도 또 `dynamic_cast`가 늘어난다. / 전체: 에너지 조회를 인터페이스에 선택 기능으로 올린다. 예: `ProtocolDriver`에 `virtual std::optional<EnergyInfo> readEnergy(id)`(기본은 `nullopt` 반환), 또는 `IEnergyReader` 인터페이스를 따로 만들어 "지원하는 드라이버만 구현". 후자가 인터페이스 분리 원칙(ISP)에 더 맞는다.

**A3.** 힌트: CLAUDE.md "드라이버 추가"와 `PCDriver.cpp` 마지막 줄. / 부분: `DriverType`에 값을 **뒤에** 추가(정수가 DB에 저장되므로 기존 번호 변경 금지), `IDeviceDriver`를 구현한 새 `.cpp/.hpp`, `DriverRegistrar`로 등록, `CMakeLists.txt`의 `add_executable`에 파일 추가. / 전체: `HTTPServer`, `DeviceManager`, `DatabaseManager`, `MatterController`는 수정 불필요(클라이언트가 `driverTypes` 정수 배열로 선택). 이게 레지스트라+팩토리의 이점이다. 다만 "5초 뒤 끄기"는 `DriverResult{true,5}`로 가능하나 "홈 화면 먼저"를 보낼 `IMessageSender`가 필요하고, 주입이 필요하면 `main.cpp`의 PC_DRIVER 덮어쓰기와 같은 우회가 또 필요해진다(설계의 약점).

**A4.** 힌트: 락 안에서 `hasDevice`를 부르는 부분. / 부분: `hasDevice`가 `mutex_`를 잡으므로, 규칙대로면 `commissionDevice`는 `sockets_mutex_` **전에** `mutex_`를 먼저 잡아야 하는데, 그러면 BLE·소켓 대기 흐름 전체가 전역 락 안에 들어가 느려진다. / 전체: "락 안에서 외부 호출 금지"가 더 안전하다. 소켓 락 안에서는 소켓 맵의 ID 목록만 복사하고, 락을 푼 뒤 `hasDevice`로 판정하고, 정리할 ID만 다시 락을 잡아 지운다(그 사이 변화는 재확인). 순서 규칙은 사람이 지켜야 해서 깨지기 쉽고, 외부 호출 금지는 구조로 교착 가능성을 없앤다.

**A5.** 힌트: 취소 수단이 있나? / 부분: 없다(B-06). ON 요청은 그 즉시 하드웨어에 가고 state가 ON이 되지만, 45초가 지나면 detach 스레드가 저장해 둔 OFF를 그대로 실행한다. 사용자는 켰는데 꺼진다. / 전체: 지연 작업을 **ID로 식별하는 보류 작업 테이블**로 관리해야 한다. 예: `DriverResult`에 `cancel_key`(또는 작업 핸들)를 추가하고, `DeviceManager`가 `map<기기ID, 취소 가능 타이머>`를 보관. 새 명령이 오면 대기 중 작업을 취소하거나(ON이 우선) 무시(중복 OFF)한다. 타이머는 detach 스레드 대신 취소 플래그를 가진 스레드 또는 스케줄러로 만들고 종료 시 join.

</details>
