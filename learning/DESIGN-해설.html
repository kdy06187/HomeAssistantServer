2단계 설계 해설

home-assistant-core: 싱글톤·교착 구조를 3계층 + 생성자 주입으로 바꾸는 설계를 읽는 법. 학습 강도 균형(해설 + 질문 + 응용 실습). 기준 문서: docs/02_설계.md, ADR-001~010, docs/api-contract-v2.0-초안.md. 설계는 아직 사용자 승인 전 초안이다.

1. 한눈에 보기

  • 무엇을: 전역 싱글톤과 서로를 부르는 순환 구조를, main이 모두 만들어 넣어 주는 3계층 구조로 바꾼다.
  • 왜: 락 순서가 엇갈려 멈추는 교착, 느린 하드웨어 작업 중 전체가 멈춤, 가짜 드라이버로 시험할 수 없음을 한꺼번에 푼다.

2. As-Is → To-Be 구조 비교

왼쪽은 "누구나 전역에서 서로를 부르는" 구조, 오른쪽은 "위에서 아래로만, 조립은 main이 한 곳에서" 하는 구조다.

왜 이렇게 나눴나

  • HTTP 계층은 "바깥 요청을 안전하게 번역"만 한다. 기기 규칙은 모른다.
  • 응용 계층은 "기기 등록·제어·삭제 규칙"과 스레드 수명을 가진다. 이 규칙을 가짜 인프라로 시험할 수 있어야 하기 때문에 가운데에 둔다.
  • 인프라 계층은 TCP·chip-tool·SQLite·시계처럼 바뀌거나 느린 것을 인터페이스 뒤에 숨긴다. 새 기기 종류는 여기에 구현체 하나를 더하면 된다(NFR-05).

코드 해설: 순환 고리를 끊는 한 줄

// Before: 드라이버가 매니저를 들고 거꾸로 부른다
class ProtocolDriver { DeviceManager& mgr_;  /* mgr_.addDevice(...) */ };
// After: 드라이버는 결과만 돌려주고, 등록은 위층이 한다
virtual Result<CommissionOutcome> commission(const CommissionRequest&,
        const std::unordered_set<std::string>& activeDeviceIds,   // 복사본
        const std::atomic<bool>& cancelRequested) = 0;
  • 무엇을: 드라이버가 DeviceManager를 모르게 하고, 필요한 정보(활성 ID 목록)는 복사본으로 받는다.
  • 왜: 아래가 위를 부르지 않으면 "락 쥔 채 남의 락" 경로가 구조적으로 사라진다.
  • 빼면: 역호출이 남아 다시 교착 가능, 그리고 DeviceManager 없이는 드라이버를 시험할 수 없다.

3. 명령 흐름 (E2: POST /api/control)

요청 하나가 지나가는 길과, 각 출구가 어떤 HTTP 코드가 되는지 본다. 코드는 ErrorCode/CommandOutcome을 ErrorMapping 표 한 곳에서만 바꾼다(문자열 검사 없음).

결과HTTP뜻앱이 할 일
Succeeded200하드웨어까지 성공상태 표시
Accepted202지연 수락 (pendingCommand, delaySeconds)그 시간 뒤 E5로 확인
Failed(CommandBlocked)409기기 드라이버가 막음사유 표시
Failed(DeviceUnreachable)502기기·chip-tool 응답 없음오프라인 안내

코드 해설: bool 대신 값으로

// Before: 기기만 있으면 true. 하드웨어 실패·지연도 "명령 성공!"
bool executeCommand(const std::string& id, const std::string& cmd);
// After: 성공/수락/실패를 타입으로 구분
CommandResult executeCommand(const std::string& deviceId, Command command);
enum class CommandOutcome { Succeeded, Accepted, Failed };
  • 무엇을: 결과를 세 갈래로 나눠 에러코드를 담는다.
  • 왜: HTTP 코드는 "본문에 error 글자가 있나"가 아니라 타입으로 정한다. 예상 가능한 실패(기기 꺼짐)는 값, 예상 못 한 것만 예외로 둔다(Result 패턴).
  • 빼면: 앱이 실패를 성공으로 오해하고, 지연 수락(202)을 표현할 수 없다.
참고: 이 변경은 REST MAJOR 변경(계약 v2.0 초안 §6의 #3, #6)이다. 그래서 1차 릴리스는 내부 구조만 바꾸고 REST는 v1.0 그대로 두며, 2차에 한 번에 v2.0을 낸다. 앱 반영은 "호환되는 준비를 먼저, 전환은 한 번에, 서버 먼저 앱 나중"(§7)이다.

4. 락 규칙이 교착을 없애는 이유

교착(deadlock): 두 스레드가 서로가 쥔 락을 기다리며 영원히 멈추는 것. 조건은 "락을 쥔 채 다른 락을 기다리기(중첩)"와 "순서가 서로 반대"다.

As-Is: 실제로 있던 엇갈림 (N-01)

To-Be: 세 규칙

규칙내용왜 효과가 있나
L-1 락 하나만락을 쥔 채 다른 락을 잡는 함수를 부르지 않는다중첩이 없으면 "쥔 채 기다림"이 없어 순환 대기가 생길 수 없다
L-2 락 안은 메모리만DB·소켓·chip-tool·sleep·콜백 금지락은 마이크로초 안에 풀린다. chip-tool 10초 동안 모두가 멈추는 일이 없다
L-4 스냅샷 복사필요한 데이터를 락 안에서 복사, 푼 뒤 사용. 연결은 shared_ptr로 복사락 밖에서 느린 일을 해도 다른 요청이 안 막힌다. 순회 중 삭제돼도 객체가 살아 있다
  1. 스레드 A(삭제): [락] 기기를 맵에서 꺼내 복사 [해제]
  2. 스레드 A: 락 없이 unpair, DB 갱신 (느려도 B를 안 막음)
  3. 스레드 B(커미셔닝): [연결 맵 락] 등록 [해제] 후 락 없이 onConnected 콜백
  4. 두 스레드는 같은 순간에 락 하나씩만 쥐므로 서로 기다릴 일이 없다.
// Before: 락을 쥔 채 느리고 위험한 호출
std::lock_guard lk(mutex_);
driver->unpair(id);        // chip-tool 최대 10초 + 다른 컴포넌트 락
devices_.erase(id);
// After: 복사 -> 락 해제 -> 느린 일
Device snapshot;
{ std::lock_guard lk(mutex_); snapshot = devices_.at(id); devices_.erase(id); }  // 메모리만
db_.markDeleted(id, clock_.utcNow());   // 락 밖
protocolDriver.unpair(id);              // 락 밖
  • 빼면: 느린 호출이 락 안에 남아 NFR-02(응답 1초)가 깨지고, 규칙 위반을 사람이 일일이 찾아야 한다.
  • 대가: 메모리와 DB 갱신이 한 덩어리로 원자적이지 않다. 같은 기기의 두 상태 갱신이 DB에 역순으로 쓰일 수 있으나 60초 헬스체크가 바로잡으므로 감수한다(ADR-002). 락 종류는 두 가지: 상태 락(메모리만), 자원 락(한 자원의 입출력만, 예: 소켓 하나의 요청·응답 1쌍).

5.1 기기 하나의 일생 (TCP_DIY)

단계동작설계 이유
접속TCPDriver가 접속 IP로 MacResolver::resolve -> TCP_AABBCCDDEEFF펌웨어를 못 바꾸니 서버가 아는 정보(ARP)만 쓴다. 인터페이스라 시험은 FakeMacResolver

확인 필요: 이 설계는 "같은 기기는 항상 같은 MAC으로 보인다"를 전제한다. 실기 확인 C-1~C-3(공유기 MAC 변환, 펌웨어 MAC 변경 여부)이 통과해야 확정이다. 추측으로 단정하지 않는 것도 설계 태도다. 또 REQ-13 완료 기준("재등록 후 0에서 시작")이 사용자 결정(기록 잇기)과 반대라 R-1로 수정을 요청해 둔 상태다.

5.2 지연 명령 스케줄러

PC 종료 요청(OFF)은 "종료 메시지를 먼저 보내고 45초 뒤 전원 차단"이다. As-Is는 명령마다 detach 스레드가 sleep했다. To-Be는 스케줄러 1개(스레드 1개)가 대기 작업 표를 들고 있다.

  • 기기당 대기 작업 1개: 같은 OFF를 두 번 보내면 종료 메시지·타이머가 중복되지 않고 202 (남은 초)만 돌려준다.
  • 다른 명령(ON)이 오면 대기 중인 OFF를 취소하고 진행한다.
  • tick(now)를 공개 -> 테스트는 FakeClock으로 45초를 즉시 건너뛴다.
  • 작업은 락 밖에서 실행한다(L-5). 대신 만기 작업이 순차라 한 작업이 5초 걸리면 다음이 밀린다(감수).

5.3 SIGTERM 종료 순서 (5초 안, 종료 코드 0)

  • 왜 sigwait? 신호 처리기 안에서는 할 수 있는 일이 거의 없다. 모든 스레드에서 신호를 막고 main만 sigwait로 받으면 평범한 코드 흐름으로 종료를 진행한다(As-Is는 svr.stop()을 부르는 곳이 없어 종료 코드에 도달하지 못했다).
  • Fail-safe: 대기 중 지연 OFF는 실행하지 않고 취소한다. 서버를 껐다고 PC 전원이 갑자기 꺼지면 안 되기 때문이다.

7. 용어 풀이

  • Composition Root: 프로그램 시작점(main)에서 모든 객체를 만들고 연결하는 한 곳.
  • 교착(deadlock): 둘 이상이 서로가 가진 것을 기다리며 영원히 멈춤.
  • 스냅샷: 락 안에서 떠 둔 복사본. 락을 푼 뒤 안전하게 쓴다.
  • Fake / Mock: 시험용 가짜. Fake는 손으로 만든 간이 구현, Mock은 "몇 번 불렸나"를 검증하는 가짜(GoogleMock).
  • Soft delete: 행을 지우지 않고 "삭제됨" 표시만 하는 방식.
  • ARP 표: 같은 LAN에서 IP와 MAC 주소를 짝지은 커널 표(/proc/net/arp).
  • Fail-safe: 문제가 생기면 위험이 덜한 쪽으로 멈추는 설계.

8. 이해도 질문

먼저 스스로 답해 본 뒤 펼친다.

Q1. ProtocolDriver가 DeviceManager&를 들고 있으면 어떤 문제가 생기나? (ADR-001)

아래가 위를 거꾸로 부르는 순환 의존이 된다. (1) 락 쥔 채 남의 락을 잡는 경로가 생겨 교착 가능, (2) 드라이버를 시험하려면 진짜 DeviceManager가 필요해 가짜 주입이 어렵다. 해법은 결과만 반환하고 등록은 위층이 하게 하는 것.

Q2. "락 하나만 쓰기"가 락 순서 규칙(D안)보다 교착을 더 확실히 막는 이유는? 대가는?

순서 규칙은 중첩을 허용하고 순서를 사람이 지켜야 하지만, 중첩 금지는 "락 범위 안의 함수 호출"만 보면 위반을 찾는다. 중첩이 없으면 순환 대기가 구조적으로 불가능하다. 대가는 메모리와 DB 갱신이 원자적이지 않아 드문 경쟁 상태를 감수하는 것(헬스체크가 바로잡음).

Q3. 같은 OFF 명령을 45초 지연 중에 한 번 더 보내면 무슨 응답이 오고, 기기 드라이버는 몇 번 실행되나?

202(남은 초). 기기 드라이버는 다시 실행하지 않는다(종료 메시지·타이머 중복 방지). 반대로 대기 중 OFF에 ON이 오면 지연 명령을 취소하고 진행한다(설계 3.3의 단계 2·3).

Q4. 서버 종료 때 대기 중인 지연 OFF를 "실행"하지 않고 "취소"하는 이유는? 이 원칙의 이름은?

서버를 껐다는 이유로 PC 전원이 차단되면 안 되기 때문. Fail-safe(실패·종료 시 덜 위험한 쪽으로). 취소는 기기별 로그로 남긴다.

Q5. TCP 기기 ID를 IP가 아닌 MAC으로 정하면 무엇이 좋아지고, 무엇을 실기로 확인해야 하나?

IP가 바뀌어도 같은 기기로 인식해 통계·이력·숨김 복구가 이어진다. 공유기·중계기가 MAC을 바꿔 전달하는지(C-2), 펌웨어가 MAC을 바꾸거나 무작위화하는지(C-3), 접속 직후 ARP 표에 MAC이 있는지(C-1)를 확인해야 한다.

Q6. 모든 라우트를 addRoute 한 함수로만 등록하게 한 이유와 빼면 생기는 일은?

인증·예외 변환·오류 매핑을 한 곳에 강제하는 Decorator 구조라서. 래퍼를 거치지 않는 라우트가 생기면 인증이 누락된다. 그래서 마지막에 전체 경로(.*) 라우트도 래퍼로 등록하고 테스트로 확인한다. 또 본문을 먼저 읽은 뒤 인증하므로 POST 401이 끊기는 문제(N-03)가 사라진다.

9. 응용 실습

원본 src/·include/는 건드리지 않는다. 새 브랜치나 learning/exercise-<이름>/ 사본에서 한다. 아직 설계 단계라 컴파일 가능한 코드가 없을 수 있으니, 종이·문서(또는 스케치 헤더 파일)로 해도 된다.

실습 A. 가짜 드라이버로 "락 밖 느린 일" 시험 설계

  • 목표: 새 기기 종류(예: 스마트 전구 BulbDriver)를 ProtocolDriver 구현체로 추가한다고 가정하고, 실제 하드웨어 없이 DeviceManager를 시험하는 구조를 설계한다.
  • 고칠 파일: learning/exercise-fake-driver/FakeProtocolDriver.hpp(새 파일 스케치), 시험 목록 표.
  • 완료 기준: (1) sendCommand가 "5초 지연 / 실패 / 예외"를 선택해 재현하는 Fake 클래스 시그니처, (2) 시험 3개: 실패 시 502·상태 OFFLINE, 지연 중 다른 요청이 막히지 않음(락 밖 호출 검증), 존재하지 않는 기기 404, (3) 각 시험이 어떤 REQ에 대응하는지 한 줄.
힌트

설계 3.8의 "통합" 줄을 보라. DatabaseManager(":memory:"), FakeClock, FakeProtocolDriver를 DeviceManager 생성자에 넣는 모습을 먼저 그려 보라. 지연 시험에서는 한 스레드가 Fake의 sleep에 걸린 사이 다른 스레드가 listDevices()를 부르면 즉시 돌아와야 한다.

정답 예시 
struct FakeProtocolDriver : ProtocolDriver {
  enum class Mode { Ok, Fail, Slow, Throw } mode = Mode::Ok;
  std::chrono::milliseconds slowFor{0};
  Status sendCommand(const std::string&, Command) override {
    if (mode == Mode::Slow)  std::this_thread::sleep_for(slowFor);
    if (mode == Mode::Throw) throw std::runtime_error("boom");
    if (mode == Mode::Fail)  return {{ErrorCode::DeviceUnreachable, "fake"}};
    return {};
  }
  // readState / commission / unpair 도 같은 방식으로 스크립트
};
// 시험: Fail -> executeCommand == Failed(DeviceUnreachable), 상태 OFFLINE (502)
//       Slow(2초) 중 다른 스레드의 listDevices()가 100ms 안에 반환 (L-2 검증)
//       없는 ID -> Failed(DeviceNotFound) (404)

실습 B. 새 오류 코드를 단일 표에 추가해 보기

  • 목표: "기기가 점검 중이면 503"처럼 새 실패 종류를 추가할 때 몇 곳을 고치는지 세어 본다(단일 매핑의 장점 체감).
  • 고칠 파일: 문서 사본 learning/exercise-error-code/표.md(설계 3.2·3.5 복사).
  • 완료 기준: ErrorCode, ErrorMapping, 계약 §6/오류 표, 시험 표에서 각각 무엇을 추가하는지 적고, As-Is(본문 문자열 검사)였다면 어디를 더 고쳐야 했는지 비교.
힌트

핸들러는 ErrorCode만 돌려주고 상태코드는 ErrorMapping::toHttp가 정한다. 핸들러 쪽 수정이 필요한지 따져 보라.

정답 예시

(1) ErrorCode에 DeviceBusy 추가, (2) ErrorMapping 표에 DEVICE_BUSY / 503 한 줄, (3) 계약 문서 오류 표 한 줄, (4) 표 기반 시험에 한 줄. 핸들러 코드는 코드를 돌려주기만 하면 되어 수정 없음. As-Is는 본문에 "error"가 있는지로 코드를 정해 핸들러마다 응답 문자열과 HTTP 코드 지정을 같이 고쳐야 했다. 앱에는 새 MAJOR가 아닌 MINOR(코드 추가)로 알리되, 앱이 모르는 code를 만나면 message를 표시하도록 처리해야 한다.
