REQ-08 해설: 지연 명령 스케줄러

"PC 끄기"를 누르면 45초 뒤에 꺼지게 하는 일을, 위험한 분리 스레드 대신 스레드 1개짜리 스케줄러로 바꾼 변경 (3단계 2차 11번, 학습 강도: 균형).

1. 한눈에 보기

  • 무엇: 지연 명령을 들고 있다가 만기에 실행하는 DelayedCommandScheduler를 새로 만들고, DeviceManager가 이것을 쓰게 했다. 예전의 std::thread(...).detach()는 사라졌다.
  • 왜: 분리(detach)된 스레드는 아무도 기다려 주지 않아서, 서버가 종료·소멸되는 중에 이미 사라진 객체를 만질 수 있다(use-after-free). 또 같은 기기에 OFF를 두 번 누르거나, OFF 중에 ON을 누르거나, 기기를 지워도 45초 뒤 OFF가 그대로 실행됐다.
  • 효과: 대기 작업이 한 곳(표)에 있어서 조회·취소·일괄 취소가 되고, 종료 때 스레드를 join할 수 있다.

3. 코드 해설

조각 1. 조건변수로 "만기까지 자기"

void DelayedCommandScheduler::run() {
    while (true) {
        {
            std::unique_lock<std::mutex> lock(mutex_);
            if (isStopping_) return;
            const auto dueAt = earliestDueAtLocked();
            if (!dueAt) wakeUp_.wait(lock);              // 작업이 없으면 깨울 때까지
            else        wakeUp_.wait_until(lock, *dueAt); // 가장 이른 만기까지
            if (isStopping_) return;
        }
        tick(clock_.steadyNow());
    }
}
  • 무엇: 가장 이른 만기 시각까지 잔다. 그 전에 새 예약·취소·정지가 오면 notify_all로 깨어나 다시 계산한다.
  • 왜: 1초마다 확인하는 방식(폴링)보다 정확하고 CPU를 안 쓴다. 새 예약이 더 일찍 만기일 수 있어 schedule이 매번 깨운다.
  • 빼면: notify를 빼면 이미 45초를 자고 있는 스레드가 10초짜리 새 예약을 못 보고 늦게 실행한다. 깨어난 뒤 tick이 "정말 만기인가"를 다시 확인하므로, 가짜 깨움(spurious wakeup)이 와도 안전하다.

조각 2. 표는 락 안, 작업은 락 밖, 그리고 tick이 공개

void DelayedCommandScheduler::tick(std::chrono::steady_clock::time_point now) {
    while (true) {
        Task task; /* deviceId, command 도 */
        {
            std::lock_guard<std::mutex> lock(mutex_);
            if (isStopping_) return;
            auto earliest = ...;                 // 만기 지난 것 중 가장 이른 항목
            if (earliest == entries_.end()) return;
            task = std::move(earliest->second.task);
            entries_.erase(earliest);
            ++runningTasks_;
        }
        task();   // 락 밖
        { std::lock_guard<std::mutex> lock(mutex_); --runningTasks_; }
        idle_.notify_all();
    }
}
  • 무엇: 하나씩 꺼내 실행한다. 꺼내는 순간 표에서 지워지므로 "같은 작업이 두 번 실행"될 수 없다.
  • 왜: 작업은 chip-tool(최대 5초)을 부른다. 락을 쥔 채 실행하면 그동안 pending·cancel·HTTP 요청이 전부 멈춘다. 작업이 schedule을 다시 불러도(재진입) 교착하지 않는다.
  • 왜 tick을 공개했나: 테스트가 스레드·진짜 시간을 쓰지 않도록, FakeClock.advance(45초) 뒤 tick(now)을 직접 부르면 결정적으로 시험된다(흔들리는 sleep 테스트 없음).
  • 빼면: 락 안 실행 → 교착·지연. 꺼내기 전에 실행 → 같은 작업 중복 실행. runningTasks_를 빼면 종료가 "실행 중인 작업이 끝나기 전"에 지나가 버린다.

조각 3. executeCommand 3.3 단계 2·3·4 (전후 비교)

// before: 지연을 분리 스레드로
std::thread([this, id, command, ...] {
    std::this_thread::sleep_for(std::chrono::seconds(delay));
    executeHardware(...);          // 서버가 이미 소멸됐을 수 있음
}).detach();
// after
const auto pendingCommand = scheduler_.pending(id);
if (pendingCommand && pendingCommand->command == command)       // 단계 2
    return Accepted(남은 초);                                     // 기기 드라이버 안 부름
if (pendingCommand) scheduler_.cancel(id, "다른 명령");           // 단계 3
...
if (action.delay_seconds > 0) {                                  // 단계 4
    if (scheduler_.schedule(id, command, seconds(delay), task)) return Accepted(delay);
    ... // 동시에 먼저 예약됐으면 그 남은 초로 Accepted
}
  • 단계 2 (같은 명령 중복 방지): OFF를 두 번 눌러도 PC에 "종료 예고" 메시지는 한 번만 간다. 기기 드라이버를 아예 부르지 않고 남은 초만 돌려준다(202).
  • 단계 3 (다른 명령 취소): OFF 대기 중 ON이 오면 예약을 지운다. 사용자가 마음을 바꿨는데 45초 뒤 꺼지면 안 된다.
  • 단계 4: 지연 명령은 표에 넣고 바로 202를 돌려준다.
  • 빼면: 단계 3이 없으면 ON 뒤에도 OFF가 실행된다. 단계 2가 없으면 종료 메시지가 중복된다. 남은 약점: 두 요청이 정말 동시에 오면 둘 다 단계 2를 지나 종료 메시지가 2번 갈 수 있다(결정 D4로 수용, 결과는 OFF 1회로 같다).

조각 4. 삭제 시 취소와 unpair 동기화

// removeDevice: 맵에서 뺀 직후
scheduler_.cancel(id, "삭제");   // 삭제된 기기에 45초 뒤 OFF가 가지 않게

// MatterController::unpairDevice (11c)
std::thread([...]{ runner.run(unpair...); }).detach();
runner.run(unpair...);   // 호출한 스레드에서 바로(최대 10초)
  • 무엇/왜: 지운 기기에 명령이 가는 것을 막는다. unpair의 분리 스레드도 같은 이유(종료 때 MatterController가 소멸된 뒤 this를 씀)로 없앴다.
  • 대가: 삭제 응답이 Matter 오프라인 기기에서는 최대 10초 늦어진다. 앱의 읽기 제한 시간이 10초보다 짧으면 앱이 먼저 끊을 수 있다(총괄이 [App]에 확인할 항목).
  • 빼면: cancel이 없으면 삭제한 기기의 만기 작업이 실행되고, 작업은 복사해 둔 프로토콜 드라이버 포인터로 존재하지 않는 기기 ID에 명령을 보낸다.

왜 detach 스레드가 위험했나 (use-after-free)

이제 소멸 순서는 main 선언 순서(database → scheduler → manager)가 보장한다. 만기 작업이 this를 쓰지만, 스케줄러를 DeviceManager보다 먼저 멈추고(join) 나중에 소멸시키므로 안전하다.

4. 용어 풀이

  • 조건변수(condition_variable): "조건이 될 때까지 자고, 누가 깨우면 일어나 확인"하는 도구. wait_until은 시각 제한이 붙은 버전.
  • detach: 스레드를 부모와 떼어 놓는 것. 끝나기를 기다릴 방법이 사라진다(join 불가).
  • use-after-free: 이미 해제된 메모리를 쓰는 버그. 가끔만 터져서 찾기 어렵다.
  • FakeClock: 시험용 가짜 시계. advance로 시간을 마음대로 흘린다.
  • steady vs utc 시계: 타이머는 거꾸로 가지 않는 steadyNow, 로그의 시각은 사람용 utcNow.
  • 재진입(re-entrancy): 락을 쥔 코드가 다시 같은 락이 필요한 함수를 부르는 상황. 락 밖 실행으로 피한다.

5. 이해도 질문

Q1. 만기 작업을 mutex_를 쥔 채로 실행하면 무엇이 문제인가? 구체적인 요청 하나를 예로 들어라.

정답작업이 chip-tool을 최대 5초 부르는 동안 pending·cancel·schedule이 모두 같은 락에서 막혀, 그 사이 들어온 HTTP 제어 요청이 5초 멈춘다. 작업이 다시 schedule을 부르면 같은 스레드가 자기 락을 기다려 교착한다.

Q2. 10초 동안 OFF가 대기 중일 때 다시 OFF를 누르면 응답과 PC 쪽에 무슨 일이 생기나? ON을 누르면?

정답OFF 재요청: 기기 드라이버를 부르지 않으므로 종료 메시지는 추가로 가지 않고 202와 남은 초(35)가 돌아온다. ON: 예약이 취소되고 ON이 즉시 실행되어 45초 뒤에도 OFF가 가지 않는다.

Q3. "기기당 1개"로 제한하지 않고 여러 개를 허용하면 어떤 일이 생길 수 있나? 나라면 어디를 바꿔야 하나?

정답OFF, ON, OFF가 쌓여 순서·최종 상태가 불확실해지고, pending이 무엇을 돌려줄지 모호해진다. 표의 키를 id에서 (id, 명령) 또는 리스트로 바꾸고 pending·cancel 의미를 다시 정해야 한다. 기기당 1개는 "마지막 의도만 남긴다"는 정책이다.

Q4. 테스트가 start()로 스레드를 켜지 않고 tick만 부르는 이유는?

정답진짜 sleep·스레드 경합 없이 FakeClock으로 시간을 정확히 제어해 결정적이고 빠르게 시험하기 위해서다. 스레드 동작은 별도의 짧은 실시간 시험 1건과 TSan으로 확인한다.
