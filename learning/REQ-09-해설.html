1. 한눈에 보기

  • 무엇: MatterController의 chip-tool 호출 8곳이 모두 mRunner.run(인자 배열, stdin, 제한 시간, 가릴 비밀값) 하나로 모였다.

3. 셸 방식과의 차이

항목셸(popen("timeout 5 chip-tool … 2>&1"))러너(execv + 인자 배열)
인젝션문자열을 /bin/sh가 해석. 값에 ;·$( )·따옴표가 섞이면 다른 명령이 실행될 수 있다인자 하나하나가 그대로 전달. 해석하는 셸이 없다(테스트: "a; echo injected $(id)"가 글자 그대로 출력)
PATH셸이 timeout을 PATH에서 찾는다. 환경에 따라 다른 프로그램이 실행될 수 있다실행 파일 경로를 직접 지정. PATH를 보지 않는다
2>&1셸 문법으로 stderr를 stdout에 합침. 빠뜨리면(예전 누적 전력 조회) 오류 출력이 사라진다자식에서 dup2로 1·2번을 같은 파이프에 연결 — 모든 호출에 항상 적용
timeout외부 명령 timeout 5. 붙인 곳만 제한, 시리얼·unpair·페어링은 무제한러너가 마감 시각을 직접 셈(5/10/180초). 손자 프로세스까지 그룹째 종료
표준 입력·fd서버의 stdin과 CLOEXEC 아닌 fd를 물려받음stdin은 /dev/null(또는 지정 텍스트), 러너 fd는 모두 CLOEXEC
종료 때 정리방법 없음(popen 자식 pid를 모름)cancelAll() — 2차 11번 SIGTERM 정상 종료에서 사용
테스트실제 chip-tool 필요인터페이스라 가짜 러너로 교체(8b)

4. 코드 해설

4-1. fork 뒤 자식에서 하면 안 되는 것

// 부모에서 미리: argv 벡터 준비 (fork 뒤 malloc 금지)
pid = ::fork();
if (pid == 0) {
    ::setpgid(0, 0);
    ::dup2(childStdin, STDIN_FILENO);
    ::dup2(outputPipe[1], STDOUT_FILENO);
    ::dup2(outputPipe[1], STDERR_FILENO);
    ::execv(argv[0], argv.data());
    ::_exit(127);
}

멀티스레드 프로그램에서 fork하면 자식에는 fork한 스레드 하나만 남는다. 다른 스레드가 malloc 락을 쥔 순간이었다면 자식이 malloc을 부르는 순간 영원히 멈춘다. 그래서 자식에서는 신호 안전 함수(dup2, execv, _exit)만 쓴다.

4-2. 파이프에 쓰다 SIGPIPE로 죽지 않게

소켓은 MSG_NOSIGNAL이 있지만 파이프 write에는 없다. 프로세스 전체 신호 설정을 바꾸지 않고, 이 스레드에서만 pthread_sigmask로 SIGPIPE를 막은 뒤 생긴 신호를 sigtimedwait로 거둬들인다.

5. 용어 풀이

용어뜻
fork / execfork는 현재 프로세스를 복제, exec는 그 자리를 다른 프로그램으로 바꿈. 둘 사이에서 fd·그룹을 정리한다.
프로세스 그룹함께 신호를 받는 프로세스 묶음. kill(-pgid, sig)로 손자까지 한 번에.
좀비끝났지만 부모가 waitpid로 회수하지 않은 프로세스. 프로세스 표 자리를 차지한다.
WNOWAIT끝났는지 확인만 하고 회수는 미룸 → 그동안 pid가 재사용되지 않는다.
어댑터 패턴외부 프로그램(chip-tool)을 우리 인터페이스 뒤로 숨겨, 실제/가짜를 바꿔 끼울 수 있게 함.

6. 이해도 질문

Q1. timeout 5로 감싼 예전 방식에서 chip-tool이 자식 프로세스를 하나 더 띄웠다면, 시간 초과 때 무엇이 남을 수 있었나?

정답timeout은 직접 실행한 프로세스에만 신호를 보낸다(기본값). 손자는 남아 계속 돌 수 있다. 러너는 자식을 새 프로세스 그룹으로 만들고 그룹 전체에 신호를 보낸다(테스트: sleep 30 & 손자까지 사라짐).

Q2. 출력 파이프가 닫히면(EOF) 바로 waitpid를 막힌 채로 부르면 안 되는 이유는?

정답프로그램이 stdout·stderr를 닫고도 계속 실행될 수 있다. 그러면 waitpid가 끝없이 기다린다. 러너는 남은 제한 시간 안에서만 기다리고, 넘으면 종료 절차(SIGTERM → SIGKILL)로 넘어간다.

Q3. stdin 방식(비밀번호를 인자 대신 stdin으로)을 8번에 넣지 않은 이유는?

정답chip-tool interactive start가 파이프 입력에서 어떻게 동작하는지(프롬프트, 종료 감지, 공백·따옴표 처리)를 실기로 확인하지 않았다. 추측으로 만들면 틀릴 가능성이 높다(절대 규칙 4). 러너에 stdinText 칸은 만들어 /bin/cat으로 시험해 두었고, 실기 확인 뒤 2차 13번에서 쓴다.

8b. MatterController를 테스트 가능하게

1. 무엇이 막고 있었나

MatterController는 Matter SDK(CHIP) 헤더를 include해서, SDK가 없는 테스트·TSan 빌드에 넣을 수 없었다. 그런데 SDK를 실제로 쓰는 곳은 설정 코드 → PIN 해석 한 줄뿐이었다. 그 한 줄을 함수 주입으로 바꾸자 나머지 전부가 SDK 없이 빌드된다.

// MatterSetupCode.hpp (SDK 없음)
using SetupPinParser = std::function<Result<uint32_t>(const std::string&)>;
// main: MatterController matterController(chipToolRunner, parseManualSetupPin);   // 실제(SDK)
// 테스트: MatterController controller(fakeRunner, fakePinParser, "/fake/chip-tool", 임시파일);

원칙: 무거운 의존은 가장 작은 경계 하나로 몰아넣는다. 러너(8a)가 chip-tool을, 이 함수가 SDK를 막아 주므로 MatterController 본체는 순수 로직이 됐다.

3. E9: 실패하면 아무것도 남기지 않기

DB 저장에 실패한 기기를 메모리에만 두면, 앱 목록에는 보이는데 재시작하면 사라진다. 그래서 메모리 등록을 되돌리고(같은 ID가 있었으면 이전 값 복원) 커미셔닝 실패로 답한다. 대가: 기기는 이미 페어링돼 있어 다시 등록하면 새 노드 ID로 페어링된다(실기 절차서에 기록).

4. 이해도 질문 (8b)

Q4. 테스트 RunnerIsCalledWithoutHoldingControllerLocks는 러너 안에서 controller->isPairing()을 부른다. 이것으로 무엇을 확인하나?

정답MatterController가 stateMutex_를 쥔 채 러너(chip-tool, 최대 수 초)를 부른다면, 러너 안에서 같은 락을 다시 잡는 순간 같은 스레드가 자기 락을 기다려 멈춘다(감시자가 실패시킴). 멈추지 않는다는 것은 "chip-tool은 락 밖에서" 규칙(L-2)이 지켜졌다는 뜻이다.

Q5. 왜 MatterSetupCode.cpp는 테스트하지 못하나? 그 위험은 어떻게 줄였나?

정답Matter SDK가 필요해 테스트 빌드에 넣을 수 없다. 코드는 기존 것을 그대로 옮기기만 했고(로직 변경 없음), 실제 동작은 9번 실기 페어링으로 확인한다. 경계를 한 함수로 작게 만든 것 자체가 위험을 줄이는 방법이다.
