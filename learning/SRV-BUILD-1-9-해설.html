SRV-BUILD-1 9번 해설 — 실기 시험

자동 테스트 237개가 다 통과했는데 왜 실제 기기로 또 시험하나 (3단계 9번, 학습 강도: 균형). 절차서: docs/07_실기시험-1차.md

1. 왜 필요한가 — 가짜는 "우리가 믿은 것"만 흉내 낸다

8번까지의 테스트는 가짜 러너(FakeChipToolRunner)와 루프백 가짜 스위치를 썼다. 가짜는 우리가 정한 대로만 답한다. 그래서 다음은 테스트로 알 수 없다.

우리가 가정한 것틀리면절차서 항목
chip-tool은 성공하면 종료 코드 0멀쩡한 기기가 전부 OFFLINE으로 보임 → 결정 25로 그 명령만 출력 문구 판정 복귀2.1~2.6
5초·10초·180초면 충분느린 기기가 시간 초과로 실패2.0 걸린 시간
스위치는 모르는 메시지에도 답하거나, 서버가 닫으면 다시 접속PC 끄기 한 번에 스위치가 영영 오프라인4.1~4.3
스위치 MAC은 바뀌지 않음2차 12번 TCP_<MAC> ID 설계가 무너짐5.1

이것을 계약 테스트의 빈칸이라고 한다. 가짜와 진짜가 같은 계약을 지키는지는 진짜로만 확인할 수 있다. 실무에서는 이 결과를 다시 가짜에 반영해(예: "chip-tool은 성공해도 코드 1을 낸다") 자동 테스트를 현실에 맞춘다.

2. 어떻게 — 운영을 건드리지 않는 "그림자 환경"

서버는 파일을 ../config, ../db처럼 실행 위치 기준으로 연다. 실행 위치만 바꾸면 코드 수정 없이 다른 파일 세트를 쓰게 된다.

항목마다 준비 → 실행 → 기대 결과 → 확인 → 실패 시 → 결과 칸으로 쓴 이유: 다른 사람이 해도 같은 결과가 나와야(재현성) 시험이 증거가 된다. 기대 결과를 먼저 적어 두면 결과를 보고 해석을 바꾸는 일을 막는다.

3. 종료 코드는 어디서 보나

chip-tool 끝남 → ProcessResult{exitCode, timedOut, …}
  ok = 시작 성공 && 시간 초과 아님 && 취소 아님 && exitCode == 0
  exitCode != 0 이면 로그: [MatterController] chip-tool 비정상 종료 (코드 N)

서버는 0이 아닐 때만 로그를 남긴다. 그래서 "명령은 성공 + 그 로그 없음" = 0. 정확한 숫자와 시간이 필요하면 서버를 끄고 같은 인자로 직접 돌려 echo $?를 본다(KVS를 두 프로세스가 동시에 쓰지 않게).

실기에서 찾은 것 (2026-11-20)

가정 대부분은 맞았다. chip-tool은 성공하면 항상 종료 코드 0을 돌려줘서 결정 25로 되돌린 명령이 없고, 5초 안에 모두 끝났다. 가짜로는 볼 수 없던 것도 나왔다. ① 스위치는 SYSTEM 메시지에 답하지 않는다. 서버가 연결을 닫으면 곧바로 다시 접속하지만, 종료 메시지가 모든 연결에 가서 응답 없는 기기마다 1초씩 늦어진다(T5 → 2차 11번). ② 8080 바인딩이 실패해도 서버가 8000만 켠 채 계속 돈다(반쯤 켜진 상태 → 2차 10번). ③ chip-tool stdin 방식은 공백 든 값을 나누고 입력을 /tmp/chip_tool_history에 남긴다. 그래서 "ps 노출을 없애려다 파일 노출이 생기는" 트레이드오프가 된다(2차 13번). 실기는 이렇게 다음 설계의 입력이 된다.

4. 응용 실습

Q1. 2.1에서 켜기는 성공했는데 로그에 "비정상 종료 (코드 1)"이 있다. 무엇을 바꾸고, 무엇은 바꾸지 말아야 하나?

결정 25: 그 명령(onoff)만 종료 코드 대신 출력 문구 판정으로 되돌린다. 다른 명령(시리얼·페어링)은 실기에서 0이 확인됐으면 그대로 둔다. 그리고 FakeChipToolRunner 테스트에 "성공 출력 + 코드 1 → 성공" 경우를 추가해 현실을 고정한다.

Q2. 포트를 환경 변수로 바꿀 수 있게 하면 이 절차서의 무엇이 달라지나?

운영 서버를 끄지 않고 시험 서버를 8001·8081에 띄울 수 있다(승인 명령 하나가 줄어든다). 대신 스위치·앱이 시험 포트로 붙도록 설정을 바꿔야 해서 "실기와 운영이 같은 경로"라는 장점이 줄어든다 — 트레이드오프.

Q3. 직접 해 보기: 1번 마이그레이션 확인 SQL 중 "행 수 비교"가 왜 백업과 새 DB 두 파일에 같은 쿼리를 돌리는가?

마이그레이션은 열·인덱스만 추가해야 하고 데이터를 잃으면 안 된다. 백업(이전 상태)과 결과(이후 상태)를 같은 잣대로 재야 "줄어들지 않았다"를 보일 수 있다 — 이전/이후 비교(before/after diff)의 기본형.
