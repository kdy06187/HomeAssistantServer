2. 흐름 — 서버 시작 순서와 실패 지점

8080을 8000보다 먼저 여는 이유: httplib는 SO_REUSEPORT로 바인드해서 같은 계정의 두 번째 인스턴스도 8000을 열 수 있다. 8080(우리 코드, REUSEPORT 없음)에서 먼저 막혀야 두 번째 인스턴스가 8000에 끼어들지 않는다.

3. 테스트가 옛 동작을 "고정"하고 있었다

기존 테스트 HealthCheckUnknownStateZeroesDatabaseState는 "UNKNOWN이면 DB를 OFF로"라는 옛 버그를 기대값으로 갖고 있었다(4a에서 "동작 불변"을 지키려고 쓴 특성 테스트). 동작을 의도적으로 바꿀 때는 이런 테스트를 지우지 않고 기대를 뒤집고 이름을 바꿔 바뀐 규칙의 증거로 남긴다.

// 예전: EXPECT_EQ(dbState("FAKE_1"), "OFF");
// 지금: EXPECT_EQ(dbState("FAKE_1"), "ON");   // "모름"은 저장된 상태를 바꾸지 않는다

4. 응용 실습

Q1. readEnergy가 nodeId를 한 번만 읽게 바꾼 이유는? (V6)

예전엔 실시간 전력·누적 전력 조회가 각자 getNodeId를 불렀다. 두 조회 사이(최대 5초)에 기기가 삭제되면 두 번째 조회는 노드 0에 chip-tool을 실행한다. 값을 한 번 읽어 넘기면 두 조회가 같은 스냅샷을 쓴다 — TOCTOU(검사 시점과 사용 시점의 차이) 제거.

Q2. 삭제에서 unpair가 예외를 던지면 지금은 어떻게 되나? 바꾼다면 장단점은?

지금은 DB 삭제 뒤 예외가 위로 올라가 HTTP 500이 된다(실제로는 지워짐 — V3와 같은 불일치가 예외 경로에 남음). try/catch로 로그 후 true를 돌려주면 응답이 실제 상태와 맞지만, 예상 못 한 예외를 삼켜 버그를 감출 수 있다. 실무에서는 "알려진 실패는 결과값, 예외는 정말 예외"로 나누고, 삼킬 때는 반드시 로그·지표를 남긴다.

Q3. 직접 해 보기: umask(077)이 자식 chip-tool에도 적용되는 이유는?

umask는 프로세스 속성이고 fork로 상속되며 execv로 바뀌지 않는다. 그래서 서버 첫 줄에 한 번만 두면 서버가 만드는 DB·등록 파일과 chip-tool이 만드는 /tmp/chip_tool_*가 모두 600이 된다. 확인: 서버를 띄운 뒤 grep Umask /proc/$(pgrep -f '^./HomeAssistantCore')/status → 0077.
