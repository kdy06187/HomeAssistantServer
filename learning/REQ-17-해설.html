2. 흐름 그림 (의존 관계)

왜 hac_legacy가 있나? DeviceManager.cpp가 MatterController.hpp를 포함하고 dynamic_cast를 써서 아직 CHIP과 분리되지 않는다. 그래서 임시 묶음으로 두고, 이후 4·6번에서 인터페이스를 분리하며 해체한다. 노란 칸은 "빚"이라는 표시다.

3. 코드 해설

(a) OBJECT 라이브러리 — 자기 등록 패턴을 지킨다

- (이전) add_executable(HomeAssistantCore src/main.cpp ... src/PCDriver.cpp ...)
+ add_library(hac_core OBJECT src/ApiAuth.cpp src/DatabaseManager.cpp src/PCDriver.cpp)
+ target_link_libraries(HomeAssistantCore PRIVATE hac_core hac_legacy)

// src/PCDriver.cpp
namespace {
    const DriverRegistrar registrar(DriverType::PC_DRIVER, ...);  // 정적 객체
}
  • 무엇: PCDriver.cpp 맨 아래의 정적 DriverRegistrar는 프로그램이 시작될 때 생성자가 돌며 자신을 등록한다(자기 등록 패턴).
  • 왜 OBJECT: STATIC(.a)이면 링커는 "아무도 참조하지 않는 .o"를 통째로 뺀다. PCDriver.o를 아무도 직접 부르지 않으므로 등록 코드가 사라질 수 있다. OBJECT는 .o를 그대로 실행 파일에 넣어 이전 링크와 같다.
  • 빼면(STATIC으로 바꾸면): 컴파일·링크는 성공하는데 PC 드라이버가 등록되지 않는 조용한 버그가 된다.
  • 검증: nm으로 _GLOBAL__sub_I 심볼이 남았는지 확인하고, link.txt의 입력 227개가 이전과 같은지 비교했다.
nm -C build/HomeAssistantCore | grep _GLOBAL__sub_I | grep -i PCDriver

(b) 경고 옵션을 "우리 대상에만" — target 기반 CMake

- add_compile_options(-Wall -Wextra)   # 전역: googletest 등 모두에 적용됨
+ function(hac_apply_target_options target)
+     target_compile_options(${target} PRIVATE -Wall -Wextra)
+     if(HAC_ENABLE_TSAN)
+         target_compile_options(${target} PRIVATE -fsanitize=thread -g -O1)
+         target_link_options(${target} PRIVATE -fsanitize=thread)
+     endif()
+ endfunction()
  • 무엇: 옵션을 "대상(target)"에 붙인다. 모던 CMake의 핵심은 전역 변수 대신 대상마다 PRIVATE/PUBLIC으로 속성을 거는 것이다.
  • 왜: 전역으로 걸면 FetchContent로 받은 googletest에도 경고·TSan이 걸려 남의 코드 경고가 쏟아진다.
  • 빼면: 경고 옵션이 없어 N-15(경고 없음) 문제가 남는다.

(c) FetchContent + 커밋 해시 고정, TSan 강제 규칙

FetchContent_Declare(googletest
    GIT_REPOSITORY https://github.com/google/googletest.git
    GIT_TAG 063de7e9578f82b369302001269680b4b1553359 # v1.18.0
)

if(HAC_ENABLE_TSAN AND HAC_BUILD_SERVER)
    message(FATAL_ERROR "HAC_ENABLE_TSAN=ON은 -DHAC_BUILD_SERVER=OFF와 함께 사용하세요.")
endif()
  • 왜 해시: 태그는 옮겨질 수 있지만 커밋 해시는 불변이다. 누가 언제 빌드해도 같은 코드가 받아져 재현 가능한 빌드가 된다. 라이선스는 BSD-3(상업·학습 모두 사용 가능, 고지 의무).
  • 왜 FATAL_ERROR: CHIP 정적 라이브러리는 TSan으로 계측되지 않았다. 섞으면 데이터 레이스를 놓치거나(누락) 없는 레이스를 보고한다(오탐). 잘못된 조합은 아예 막는 편이 낫다.
  • 빼면: TSan 결과를 믿을 수 없게 된다.

(d) Test Double — MockMessageSender

class MockMessageSender : public IMessageSender {
public:
    MOCK_METHOD(void, SendCommandTo, (const std::string& target_id, const std::string& command), (override));
};

StrictMock<MockMessageSender> sender;
EXPECT_CALL(sender, SendCommandTo("ALL", HasSubstr("SHUTDOWN"))).Times(1);
PCDriver driver(&sender);
  • 무엇: 진짜 TCP 대신 "호출이 몇 번, 어떤 인자로 왔는지"만 기록·검증하는 가짜다. StrictMock은 예상 못한 호출이 오면 실패시킨다.
  • Mock vs Fake: Mock은 호출 검증이 목적이다(이번 사용). Fake(FakeProtocolDriver, FakeClock 등, 이후 단계)는 실제처럼 동작하는 단순 대역으로 상태·결과를 만든다.
  • 특성화 테스트: "옳은 동작"이 아니라 "지금 동작"을 먼저 고정한다. 소문자 off는 가로채지 않는다 같은 현재 동작도 포함한다. 이후 리팩터링 중 동작이 달라지면 테스트가 바로 알려 준다. 그래서 이 테스트가 "동작 불변"의 안전망이다.

4. 용어 풀이

  • OBJECT 라이브러리: 묶지 않은 .o 파일 모음. 링크할 때 전부 그대로 들어간다.
  • 모던(타깃 기반) CMake: 전역 설정 대신 대상별로 include·옵션·의존을 거는 방식.
  • FetchContent: 설정 단계에서 외부 저장소를 내려받아 빌드에 포함하는 CMake 기능.
  • Test Double: 테스트에서 실제 부품을 대신하는 가짜(Mock, Fake, Stub의 총칭).
  • 특성화 테스트: 기존 동작을 그대로 기록하는 테스트. 리팩터링 전 안전망.
  • ThreadSanitizer(TSan): 실행 중 스레드 데이터 레이스를 찾는 컴파일러 도구.

5. 실행 명령

# 서버 + 테스트 전체 빌드·실행 (이 서버 PC: CHIP 빌드 결과물 있음)
cmake -S . -B build-dev
cmake --build build-dev -j"$(nproc)"
ctest --test-dir build-dev --output-on-failure

# 테스트만 빌드·실행 (CHIP·BLE 없는 PC)
cmake -S . -B build-testonly -DHAC_BUILD_SERVER=OFF
cmake --build build-testonly -j"$(nproc)"
ctest --test-dir build-testonly --output-on-failure

# TSan 구성 (서버 OFF 필수)
cmake -S . -B build-tsan -DHAC_ENABLE_TSAN=ON -DHAC_BUILD_SERVER=OFF
cmake --build build-tsan -j"$(nproc)"
ctest --test-dir build-tsan --output-on-failure

# 잘못된 조합(FATAL_ERROR 확인용)
cmake -S . -B build-bad -DHAC_ENABLE_TSAN=ON

참고: HAC_BUILD_SERVER 기본값은 ON이라 CHIP 빌드 결과물이 필요하다. 없는 PC에서는 OFF로 테스트만 빌드한다.

6. 이해도 질문

Q1. hac_core를 OBJECT 대신 STATIC으로 바꾸면 왜 위험한가? 어떻게 알아챌까?

PCDriver.o를 직접 참조하는 곳이 없어 링커가 .o를 버리고, 정적 DriverRegistrar의 등록 코드가 사라질 수 있다. 빌드는 성공하므로 nm의 _GLOBAL__sub_I 확인이나 PC 드라이버 부착 동작 확인으로 알아챈다.

Q2. 전역 add_compile_options(-Wall -Wextra) 대신 hac_apply_target_options를 쓴 이유는?

FetchContent로 받은 googletest 등 서드파티에도 경고·TSan이 적용되는 것을 막고, 우리 코드의 경고만 보기 위해서다.

Q3. 특성화 테스트가 "소문자 off는 가로채지 않는다"까지 고정하는 이유는? 그 동작이 버그라면?

리팩터링이 동작을 바꾸지 않았음을 보장하려면 현재 동작 전체를 기록해야 한다. 버그라면 리팩터링이 끝난 뒤 별도 변경으로 테스트와 코드를 함께 고친다(리팩터링과 동작 변경을 섞지 않는다).

실습 A. 빈칸 구현 — "ON 명령은 SendCommandTo를 부르지 않는다"

  • 목표: EXPECT_CALL(...).Times(0) 사용법 익히기
  • 고칠 파일: tests/unit/PCDriverTest.cpp 사본
  • 완료 기준: 새 테스트가 ctest에서 통과하고, handleCommand가 ON에서도 전송하도록 임시로 바꾸면 실패한다.
TEST(PCDriverHandleCommand, OnCommandNeverSendsMessage) {
    StrictMock<MockMessageSender> sender;
    EXPECT_CALL(sender, SendCommandTo(____, ____)).Times(____);
    PCDriver driver(&sender);

    DriverResult result = driver.handleCommand(makeDeviceWithState("ON"), "____");

    EXPECT_TRUE(result.proceed_hardware);
}
힌트

인자를 무엇이든 받으려면 _를 쓴다. 횟수는 0번이다. 명령 문자열은 소문자가 아닌 대문자다.

정답 
EXPECT_CALL(sender, SendCommandTo(_, _)).Times(0);
...
driver.handleCommand(makeDeviceWithState("ON"), "ON");

참고: StrictMock이라 EXPECT_CALL이 없어도 호출 시 실패한다. Times(0)은 의도를 코드로 드러내는 용도다.

실습 B. 응용 과제 — 새 OBJECT 라이브러리 추가

  • 목표: src/Foo.cpp(CHIP 불필요)를 hac_core와 별도 hac_foo OBJECT 라이브러리로 추가하고, 서버와 테스트가 모두 쓰게 한다.
  • 고칠 파일: CMakeLists.txt(루트), tests/CMakeLists.txt
  • 완료 기준: 서버 OFF 구성에서 hac_tests가 빌드되고, 서버 ON 구성에서 HomeAssistantCore 링크 입력에 Foo.cpp.o가 있다.
힌트

hac_core 선언 3줄(add_library, include, link, 옵션 함수)을 본뜬다. 소비하는 쪽 target_link_libraries에 이름을 추가해야 한다. 서버 쪽은 if(HAC_BUILD_SERVER) 안의 링크 줄도 잊지 말 것.

정답 
add_library(hac_foo OBJECT src/Foo.cpp)
target_include_directories(hac_foo PUBLIC ${CMAKE_CURRENT_SOURCE_DIR}/include)
hac_apply_target_options(hac_foo)

# 서버: target_link_libraries(HomeAssistantCore PRIVATE hac_core hac_legacy hac_foo)
# 테스트: target_link_libraries(hac_tests PRIVATE hac_core hac_foo GTest::gmock_main)

Foo에 자기 등록 패턴이 없다면 STATIC도 가능하지만, 일관성과 기존 링크 보존을 위해 OBJECT를 쓴다.
